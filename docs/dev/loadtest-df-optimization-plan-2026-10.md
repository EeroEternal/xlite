# D/F 长流优化方案：xlite 对标 New API V88 单节点

- **状态**：P1（取消传播修复）已实施、带 5 项永久回归测试且现场认证通过（§5.4）；P2~P4 仍为待验证假设，尚未落地。包含已验证的诊断结果。
- **日期**：2026-10-09。
- **代码基线**：仓库 `9becccf` 的数据面与 HTTP/2 连接池实现。
- **目标**：提高长流持续完成速率，缩短请求完成时间，消除异常超时长尾，同时保住首字延迟和字节透传正确性。
- **范围**：取消传播、连接分布、运行时与台架观测；不修改生产默认值，不增加业务准入队列或主动过载 429。

### 2.2 分开报告三类速率

1. **整轮汇总速率**：k6 汇总中的请求速率，可能包含长时间排空。
2. **固定载荷窗口完成速率**：从日志累计完成迭代数计算，不混入排空。
3. **成功完整流完成速率**：窗口内成功且完整结束的响应数除以窗口时长。

```text
窗口完成速率 = [完成迭代数(t1) - 完成迭代数(t0)] / (t1 - t0)
```

现有进度计数包含失败迭代，无法直接得到第三项。不要将第二项标成精确的成功流吞吐。
现有脚本的 `[DONE]` 检查是采样的，出现 `[DONE]` 也不能单独证明内容块数和全部字节正确。
后续若需要第三项，应在两侧相同的压测端增加完成时间与完整性统计，并量化它对客户端压力的影响；
不要把 SSE 解析加入网关。

### 2.4 两个必须纠正的结论

- **D 的综合分与吞吐不是一回事**：报告综合分约54.8对45.2，xlite 获胜；
  可用区 AUC 为6.51M对3.46M，也不是 xlite 落后。同档完成速率仍有明显差距。
- **F@40,000 没有已证明的稳态吞吐断崖**：汇总速率约247.3次/秒，但窗口速率约375.2次/秒。
  该档10个传输超时拉长排空；F@45,000 有7个传输超时。D@40,000 有2个传输超时。
  这些档没有502/503，不能直接套用历史 HAProxy 503 溢出归因。

超时必须保留为可靠性问题，不能因拆开排空就将其从结果中删除。

### 2.5 相同 VU 不代表相同实际压力

闭式负载可粗略估计 HTTP 在途请求：

```text
HTTP 在途请求估计 ≈ VU × 平均 http_req_duration / 平均 iteration_duration
```

这包含首字前等待，不是 Mock 正在生成的流数，也不是瞬时观测值。
New API 的 F@45,000 平均 HTTP 时间约72秒、平均迭代约98秒，估计约3.3万 HTTP 请求在途；
xlite 两者几乎相同，估计约4.5万在途。
因此后续既要保留相同脚本、相同 VU 的用户体验比较，也要报告实际在途、字节率和客户端处理开销。
必要时另外做压力匹配诊断，不能把降低 xlite 的负载混进同档胜负结论。

`gateway_overhead_ms` 是接收时间减去采样 Mock 时间戳跨度，不是网关执行时间；
其增长本身不能区分 Mock 饥饿、网络背压和网关处理开销。

## 3. 当前实现与容量边界

### 3.1 先确认是否走 HTTP/2 路径

[`src/upstream.rs`](../../src/upstream.rs) 的 `post_stream`：

- 明文 HTTP 且 `XLITE_UPSTREAM_H2C` 开启：原生 HTTP/2 池。
- 明文 HTTP 且 H2C 关闭：原生 HTTP/1.1 池。
- HTTPS：reqwest 路径。

以下数据泵和流槽实验针对第一种。现场协议不明时，不得直接套用。
HTTP/1.1 应按一连接一请求的实际池状态诊断。

### 3.2 上限按上游地址计算

[`pool.rs`](../../crates/xlite-h2-pool/src/pool.rs) 的 `host_state` 按地址维护状态；
`acquire` 优先填充已有连接，全部满时在每地址连接上限内继续拨号，达到上限后等待。
有效流数受客户端配置和对端实时 SETTINGS 共同约束。

```text
每地址容量 = 每地址最大连接数 × min(客户端每连接流上限, 对端每连接流上限)
```

条件示例：若24个地址都通告250流、每地址32条连接，则每地址为8,000流，总上界为192,000流，
不是整台网关8,000流。总和不保证可达，流量偏斜、对端设置、CPU、内存和网络仍会限制实际能力。
若实际客户端 cap=50，则相同条件下总上界只有38,400流，结论会完全不同。
**必须取得有效配置，不能把当前默认值当现场实测值。**

### 3.3 数据泵与流控

当前网关创建池时固定 `pinned_poll=true`。
[`pump.rs`](../../crates/xlite-h2-pool/src/pump.rs) 将每连接驱动器与数据泵合在一个任务中；
每流输出通道容量16，注册通道容量256，累计8KiB后释放接收信用。
连接／流接收窗口已分别为5MiB／2MiB，见 `client_builder`，不是默认64KiB。

当前 `acquire` 对缓存命中、已有连接预留路径使用快照与原子计数，不能据旧文档直接宣称全程受大锁限制。
地址缓存未命中等路径仍需查实际性能采样，也不能反向宣称整个连接池完全无锁。

## 5. P1：取消感知的数据泵

### 5.1 已复现的问题

`pump_stream` 等待 `recv.next().await`，只在随后 `out.send` 失败时发现下游已经离开。
上游静默时，下游取消不能立即结束等待。
[`Lease::drop`](../../crates/xlite-h2-pool/src/lease.rs) 已减少本地 `in_flight`，
但数据泵仍可能持有上游接收流，计数下降不等于取消已经到达对端。

分析阶段用隔离的内存 HTTP/2 复现程序、仓库锁定依赖，连续三轮得到：

| 路径 | 上游静默时及时观察到取消 | 上游再次发送数据后观察到取消 |
| --- | --- | --- |
| 直接读取接收流 | 是 | 是 |
| 数据泵路径 | 否 | 是 |

该程序未纳入仓库，属于诊断证据，不是现有永久回归测试。
它证明当前代码的取消问题，不证明现场构建相同，也不证明最初600秒接收停顿的原因。

### 5.2 最小修复方向

等待上游数据时同时监听下游关闭。以下仅为设计示意，不是完整补丁：

```rust
let next = tokio::select! {
    _ = out.closed() => break,
    next = recv.next() => next,
};
```

保留现有错误／EOF传递、字节透传和信用释放逻辑。
核对取消后接收流释放、对端取消观察与本地 lease 计数最终收敛；
不要求远端确认与本地计数在同一瞬间发生，也不能只断言 `in_flight=0`。
通道已满、取消与数据同时就绪、注册阶段取消等情况需独立验证。

### 5.3 永久测试与验收

计划在 [`native_pool.rs`](../../crates/xlite-h2-pool/tests/native_pool.rs) 或新的池集成测试中覆盖：

1. 上游发送首块后静默；下游丢弃响应体，对端无需再发一块即可在有界等待内观察到取消。
2. 输出通道满时取消，任务不残留，计数最终收敛。
3. 单流取消不影响同连接其他流的字节和完成状态。
4. 正常结束、上游错误、对端 RST 均正确终止。
5. 超过信用释放阈值及不足阈值的尾部，均无信用泄漏或重复释放。

上界由测试显式超时限定，不能依靠无限等待；先运行修复前失败、修复后通过的测试。
修复主要收益是及时释放取消流，是否减少现场超时或提高吞吐另行测量。

### 5.4 现场认证（2026-10-09，实验室台架）

对 `ab25593`（修复后）与 `ab25593^`（修复前）各构建一个二进制（同一容器基座、仅差 `pump.rs`、MD5 对账），对同一 `mock-llm:h2c`（h2c 直连，通告 `SETTINGS_MAX_CONCURRENT_STREAMS=250`）做 A/B。上游配置为首块 50ms 后静默 1 小时（`ttft=50&out_tokens=2&token_interval=3600000`）；客户端收到首帧即以 TCP RST（SO_LINGER 0）断开。金标准：tcpdump 抓 h2c 明文 `RST_STREAM` 帧计时。

| 观测 | 修复前 | 修复后 |
| --- | --- | --- |
| 断开后 10s 观察窗内上游收到的 `RST_STREAM` | **0 帧**（未观察到取消到达） | **1 帧 `code=8`(CANCEL)，Δ = +0.0048s** |
| 无回归（完整流 ×3：924B / 6 帧 / `[DONE]`） | 通过 | 通过 |

**P1 取消传播**：修复后观察到及时取消（Δ = +0.0048s）；修复前 10s 观察窗内未观察到取消帧。与 §5.3 单测结论方向一致。

**第二个现象（归因未定）：顺序取消约 250 次后，原上游连接不再响应。** 单连接（`MAX_CONNS_PER_HOST=1`）顺序「请求 → 首块 → 断开」循环（任一时刻并发流 = 1），两臂均在**累计**第 250±1 次请求后该连接失效。帧级观察：

- **修复前**：10s 观察窗内无任何 `RST_STREAM`；失效请求（第 251 次）的 HEADERS **未出现在线上**。
- **修复后**：每个被取消的请求都观察到一帧 `RST_STREAM(CANCEL)`（共 251 帧 = 250 次取消 + 1 次超时流；**逐次 ABORT_T→RST 的 Δ 未测量**，上表 +0.0048s 仅为 phase 1 单次测量）；失效请求的 HEADERS **已上线**（帧级可见 `HEADERS sid=501`），但**原上游连接**对其不响应（无 HEADERS / RST / GOAWAY）；换一条新 h2c 连接后立即恢复（同 mock、独立网关探针通过，mock 的 HTTP/1.1 直连同时正常）。

**归因未定，不写成根因**：`SETTINGS_MAX_CONCURRENT_STREAMS=250` 是**并发流**上限，不是累计请求数上限——顺序请求并发恒为 1，累计 250 次后失效是**异常现象**，说明存在跨请求累计占用的状态，但本实验**未区分**下列机制：协议层流计数未随取消回收（发生在网关侧还是 mock 侧）、handler 并发额度、应用层未响应取消。同样，"修复前阻塞在连接池准入阶段"也只是推断——HEADERS 未上线只能定位到「未发出」，不能定位在哪一层被挡住。**该现象支持继续调查连接分布（P2），不能证明 P2 能改善真实 D/F。** 定位建议：绕过网关的直接 HTTP/2 客户端（同序列复放、直连 mock）做对照，即可切分网关侧 / mock 侧。

**边界**：本认证只证取消传播与上述两个观察，未测吞吐/TTFT/600s 停顿；mock 静默 1h 是实验配置（放大量级），不代表真实上游的滞留时长；自建 p1mock/p1gw/p1gw2 实验容器跑完即删，未动现场生产容器。**原始 pcap 未留存**（台架清理时删除）；构建指纹、命令与帧时间摘要见 §5.5，可据此复跑复核，但本节数字本身不可独立复核。

墙窗口帧序列（修复后，失效请求 = 第 251 次）：`HEADERS sid=501 + DATA` 于 1791553366.470 上线 → 原连接仅 ACK、无 h2 帧回应 → 5s 后网关对该流 `RST_STREAM(code=8)`。修复前同位置：`HEADERS sid=499` 序列止于 1791555955.376，第 251 次请求的 HEADERS 未出现，全程 `total_RST=0`。修复后失效段 `total_RST=251`（每次取消 1 帧；**各帧 Δ 未逐次记录**，仅 phase 1 有单次 Δ）。**复核口径**：本节数字来自跑测当时的 stdout/帧扫描转录，原始 pcap 已删，独立复核需按上述命令复跑。

## 6. P2：保持容量的连接分散实验

假设：优先填满少数连接可能形成连接驱动、调度或网络接收热点。
这是待验证假设，不是已证实的池容量耗尽。

仅在实际基线对端 cap=250、每地址32条连接时，使用下列矩阵：

| 实验 | 客户端每连接流上限 | 每地址最大连接数 | 每地址上界 | 24地址总上界 |
| --- | ---: | ---: | ---: | ---: |
| C0 | 250 | 32 | 8,000 | 192,000 |
| C1 | 125 | 64 | 8,000 | 192,000 |
| C2 | 64 | 128 | 8,192 | 196,608 |

C2 是近似容量匹配，比 C0 高2.4%，报告中必须披露。
以上是拨号上限，不代表一定建立这么多连接，也不是生产推荐值。
其他基线应按实际有效 cap 重算；增加连接会增加句柄、缓冲及 Mock 状态开销。
不能只降低 cap 而保留连接上限，再把减少负载或增加首字等待称为优化。

先筛选 D@30,000、F@40,000，再验证 D@20,000／30,000、F@35,000／40,000。
容量实验保持线程数、Mock、脚本和硬件不变；各方案都记录池等待及实际拨号数。
如果连接已充分分散、等待很低且吞吐不变，应停止继续增大连接上限。

## 7. P3／P4：由观测决定优化位置

| 现场观测 | 下一步 | 不应直接得出的结论 |
| --- | --- | --- |
| 某地址池持续满且等待增长 | 核对有效上限、路由偏斜、计数和对端限制 | 整台网关必然只有约一万流容量 |
| 网关单核热点、其他核空闲 | 比较连接分散、任务调度和4／8／16线程 | 线程越多越快 |
| 锁／跨核唤醒占比高 | 在真实生产路径定位具体锁与任务 | 立即改成线程局部池 |
| 软中断、丢包或重传先增长 | 检查网卡队列、CPU分布和链路容量 | 扩大HTTP/2窗口即可解决 |
| Mock CPU饱和或定时器输出变慢 | 隔离／扩展Mock，增加直连控制组 | 全部耗时增长都是网关执行时间 |
| k6处理体耗时增长 | 固定脚本与采样，量化客户端开销 | 同VU就是同压力 |
| 通道和下游写入成为CPU大头 | 试验已就绪块的批量处理 | 删除数据泵必然更快 |
| 有接收信用耗尽证据 | 独立试验窗口／释放节奏，检查内存 | 默认窗口仍是64KiB |

线程实验在连接分布方案筛选后进行，每次只改变一个因素。
已就绪块批量处理不得等待凑批、延迟首块或解析SSE；保持字节与结束状态不变。
没有性能采样证据时，不先实施线程局部池、动态池、连接预热或窗口扩容。

现有 [`pump_multiplex_bench.rs`](../../crates/xlite-h2-pool/tests/pump_multiplex_bench.rs)
使用208流、每流400块、每块200字节的内存链路。分析阶段三次重复中，数据泵比多任务直读快约62%～76%。
它不等同于生产中合并的驱动器／数据泵，也没有现场网络和Mock；
只能用作筛选证据，不能当作现场提升承诺，也不支持盲目删除数据泵。

## 8. 对照实验与验收

### 8.1 执行规则

- 两侧使用相同脚本、k6镜像、采样、`CHUNK_MAX`、Mock、超时、爬坡和排空设置。
- 对标保持 `MOCK_BATCH=1`；扩大Mock规模另作两侧相同的台架控制实验，不混入代码收益。
- 每方案至少三轮，交错运行基线与候选方案；完整排空并检查资源恢复后再开下一轮。
- 建议长流恒定载荷延长到1,800秒，预先固定观测窗口，例如相对运行时间300～1,800秒。
  必须以实际scenario为准，窗口不能跨入降载或排空。
- 同步采集网关、Mock、k6的各核CPU、内存、句柄、软中断、网络及池快照。
- 不缩短超时来“消灭”长尾，不混用采样降级重试；发生降级或OOM的轮次不能作为有效对标。

[`run_full_88_xg.sh`](../../deploy/v88/run_full_88_xg.sh) 已有 `--combo`、`--levels` 和
`STABLE_LONG`，可选择场景与档位。它包含Mock控制、网络请求和容器运行，
实施实验时需在隔离台架明确授权；本方案没有执行现场压测或重启部署。
两侧公平性规范见 [`v88-rig.md`](../manual/v88-rig.md)。

### 8.2 每轮必须报告

| 指标 | 目的 |
| --- | --- |
| 整轮汇总速率、固定窗口完成速率、可取得时的成功完整流速率 | 避免排空分母与失败混淆 |
| 窗口端点、累计计数、分段完成曲线 | 检查D的完成波动 |
| 首字p50／p90／p99、HTTP与迭代耗时 | 检查等待是否被转移 |
| 超时／状态码／中断迭代数、排空时长 | 保留可靠性与长尾 |
| 池等待、有效容量、实际连接数与在途 | 检查准入量与分布 |
| 各组件CPU、软中断、内存、句柄、字节率与重传 | 区分网关、Mock、客户端和网络瓶颈 |
| 完整性校验、实际脚本与构建指纹 | 保证协议正确与可复现 |

### 8.3 通过条件

验收分为两道门：

1. **正确性门**：P1永久测试通过；无新增字节损坏、跨流干扰、错误状态吞掉或取消残留。
2. **性能门**：在预先固定的窗口内，重复结果支持完成速率提升及完成时间缩短；
   同时首字、失败率、池等待和资源使用不发生不可接受的退化。

三轮仅用于初筛，不足以保证统计显著；若波动与收益同量级，增加轮次和窗口。
首字容忍幅度、资源预算及目标收益应在实验前结合基线波动约定，不能看完结果再改标准。
首字变差但吞吐变好只算有代价的折中，不能宣传为两者兼得。
不通过则保留结果、恢复实验配置，继续定位；不自动改生产默认值。
