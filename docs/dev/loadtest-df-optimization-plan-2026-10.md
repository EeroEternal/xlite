# D/F 长流优化方案：xlite 对标 New API V88 单节点

- **状态**：v0.5.4 已发版；§8.10 F 形寻优（24 首选）+ §8.11 **D 形/跨机完成**（D 瓶颈非 worker；**1GbE ≈57.5 万块/秒 = F 形 11.5k VU 上限**，F@40k 需 ≥5GbE）；待做：③perf 采样、④轻量诊断、⑤取消压力回归、D 形瓶颈归因。

- **目标**：提高长流持续完成速率，缩短请求完成时间，消除异常超时长尾，同时保住首字延迟和字节透传正确性。
- **范围**：取消传播、连接分布、运行时与台架观测；不修改生产默认值，不增加业务准入队列或主动过载 429。

### 2.2 分开报告三类速率

1. **整轮汇总速率**：k6 汇总中的请求速率，可能包含长时间排空。
2. **固定载荷窗口完成速率**：从日志累计完成迭代数计算，不混入排空。
3. **成功完整流完成速率**：窗口内成功且完整结束的响应数除以窗口时长。

```text
窗口完成速率 = [完成迭代数(t1) - 完成迭代数(t0)] / (t1 - t0)
```

现有进度计数包含失败迭代，无法直接得到第三项。不要将第二项标成精确的成功流吞吐。
现有脚本的 `[DONE]` 检查是采样的，出现 `[DONE]` 也不能单独证明内容块数和全部字节正确。
后续若需要第三项，应在两侧相同的压测端增加完成时间与完整性统计，并量化它对客户端压力的影响；
不要把 SSE 解析加入网关。

### 2.4 两个必须纠正的结论

- **D 的综合分与吞吐不是一回事**：报告综合分约54.8对45.2，xlite 获胜；
  可用区 AUC 为6.51M对3.46M，也不是 xlite 落后。同档完成速率仍有明显差距。
- **F@40,000 没有已证明的稳态吞吐断崖**：汇总速率约247.3次/秒，但窗口速率约375.2次/秒。
  该档10个传输超时拉长排空；F@45,000 有7个传输超时。D@40,000 有2个传输超时。
  这些档没有502/503，不能直接套用历史 HAProxy 503 溢出归因。

超时必须保留为可靠性问题，不能因拆开排空就将其从结果中删除。

### 2.5 相同 VU 不代表相同实际压力

闭式负载可粗略估计 HTTP 在途请求：

```text
HTTP 在途请求估计 ≈ VU × 平均 http_req_duration / 平均 iteration_duration
```

这包含首字前等待，不是 Mock 正在生成的流数，也不是瞬时观测值。
New API 的 F@45,000 平均 HTTP 时间约72秒、平均迭代约98秒，估计约3.3万 HTTP 请求在途；
xlite 两者几乎相同，估计约4.5万在途。
因此后续既要保留相同脚本、相同 VU 的用户体验比较，也要报告实际在途、字节率和客户端处理开销。
必要时另外做压力匹配诊断，不能把降低 xlite 的负载混进同档胜负结论。

`gateway_overhead_ms` 是接收时间减去采样 Mock 时间戳跨度，不是网关执行时间；
其增长本身不能区分 Mock 饥饿、网络背压和网关处理开销。

## 3. 当前实现与容量边界

### 3.1 先确认是否走 HTTP/2 路径

[`src/upstream.rs`](../../src/upstream.rs) 的 `post_stream`：

- 明文 HTTP 且 `XLITE_UPSTREAM_H2C` 开启：原生 HTTP/2 池。
- 明文 HTTP 且 H2C 关闭：原生 HTTP/1.1 池。
- HTTPS：reqwest 路径。

以下数据泵和流槽实验针对第一种。现场协议不明时，不得直接套用。
HTTP/1.1 应按一连接一请求的实际池状态诊断。

### 3.2 上限按上游地址计算

[`pool.rs`](../../crates/xlite-h2-pool/src/pool.rs) 的 `host_state` 按地址维护状态；
`acquire` 优先填充已有连接，全部满时在每地址连接上限内继续拨号，达到上限后等待。
有效流数受客户端配置和对端实时 SETTINGS 共同约束。

```text
每地址容量 = 每地址最大连接数 × min(客户端每连接流上限, 对端每连接流上限)
```

条件示例：若24个地址都通告250流、每地址32条连接，则每地址为8,000流，总上界为192,000流，
不是整台网关8,000流。总和不保证可达，流量偏斜、对端设置、CPU、内存和网络仍会限制实际能力。
若实际客户端 cap=50，则相同条件下总上界只有38,400流，结论会完全不同。
**必须取得有效配置，不能把当前默认值当现场实测值。**

### 3.3 数据泵与流控

当前网关创建池时固定 `pinned_poll=true`。
[`pump.rs`](../../crates/xlite-h2-pool/src/pump.rs) 将每连接驱动器与数据泵合在一个任务中；
每流输出通道容量16，注册通道容量256，累计8KiB后释放接收信用。
连接／流接收窗口已分别为5MiB／2MiB，见 `client_builder`，不是默认64KiB。

当前 `acquire` 对缓存命中、已有连接预留路径使用快照与原子计数，不能据旧文档直接宣称全程受大锁限制。
地址缓存未命中等路径仍需查实际性能采样，也不能反向宣称整个连接池完全无锁。

## 5. P1：取消感知的数据泵

### 5.1 已复现的问题

`pump_stream` 等待 `recv.next().await`，只在随后 `out.send` 失败时发现下游已经离开。
上游静默时，下游取消不能立即结束等待。
[`Lease::drop`](../../crates/xlite-h2-pool/src/lease.rs) 已减少本地 `in_flight`，
但数据泵仍可能持有上游接收流，计数下降不等于取消已经到达对端。

分析阶段用隔离的内存 HTTP/2 复现程序、仓库锁定依赖，连续三轮得到：

| 路径 | 上游静默时及时观察到取消 | 上游再次发送数据后观察到取消 |
| --- | --- | --- |
| 直接读取接收流 | 是 | 是 |
| 数据泵路径 | 否 | 是 |

该程序未纳入仓库，属于诊断证据，不是现有永久回归测试。
它证明当前代码的取消问题，不证明现场构建相同，也不证明最初600秒接收停顿的原因。

### 5.2 最小修复方向

等待上游数据时同时监听下游关闭。以下仅为设计示意，不是完整补丁：

```rust
let next = tokio::select! {
    _ = out.closed() => break,
    next = recv.next() => next,
};
```

保留现有错误／EOF传递、字节透传和信用释放逻辑。
核对取消后接收流释放、对端取消观察与本地 lease 计数最终收敛；
不要求远端确认与本地计数在同一瞬间发生，也不能只断言 `in_flight=0`。
通道已满、取消与数据同时就绪、注册阶段取消等情况需独立验证。

### 5.3 永久测试与验收

计划在 [`native_pool.rs`](../../crates/xlite-h2-pool/tests/native_pool.rs) 或新的池集成测试中覆盖：

1. 上游发送首块后静默；下游丢弃响应体，对端无需再发一块即可在有界等待内观察到取消。
2. 输出通道满时取消，任务不残留，计数最终收敛。
3. 单流取消不影响同连接其他流的字节和完成状态。
4. 正常结束、上游错误、对端 RST 均正确终止。
5. 超过信用释放阈值及不足阈值的尾部，均无信用泄漏或重复释放。

上界由测试显式超时限定，不能依靠无限等待；先运行修复前失败、修复后通过的测试。
修复主要收益是及时释放取消流，是否减少现场超时或提高吞吐另行测量。

### 5.4 现场认证（2026-10-09，实验室台架）

对 `ab25593`（修复后）与 `ab25593^`（修复前）各构建一个二进制（同一容器基座、仅差 `pump.rs`、MD5 对账），对同一 `mock-llm:h2c`（h2c 直连，通告 `SETTINGS_MAX_CONCURRENT_STREAMS=250`）做 A/B。上游配置为首块 50ms 后静默 1 小时（`ttft=50&out_tokens=2&token_interval=3600000`）；客户端收到首帧即以 TCP RST（SO_LINGER 0）断开。金标准：tcpdump 抓 h2c 明文 `RST_STREAM` 帧计时。

| 观测 | 修复前 | 修复后 |
| --- | --- | --- |
| 断开后 10s 观察窗内上游收到的 `RST_STREAM` | **0 帧**（未观察到取消到达） | **1 帧 `code=8`(CANCEL)，Δ = +0.0048s** |
| 无回归（完整流 ×3：924B / 6 帧 / `[DONE]`） | 通过 | 通过 |

**P1 取消传播**：修复后观察到及时取消（Δ = +0.0048s）；修复前 10s 观察窗内未观察到取消帧。与 §5.3 单测结论方向一致。

**第二个现象（归因未定）：顺序取消约 250 次后，原上游连接不再响应。** 单连接（`MAX_CONNS_PER_HOST=1`）顺序「请求 → 首块 → 断开」循环（任一时刻并发流 = 1），两臂均在**累计**第 250±1 次请求后该连接失效。帧级观察：

- **修复前**：10s 观察窗内无任何 `RST_STREAM`；失效请求（第 251 次）的 HEADERS **未出现在线上**。
- **修复后**：每个被取消的请求都观察到一帧 `RST_STREAM(CANCEL)`（共 251 帧 = 250 次取消 + 1 次超时流；**逐次 ABORT_T→RST 的 Δ 未测量**，上表 +0.0048s 仅为 phase 1 单次测量）；失效请求的 HEADERS **已上线**（帧级可见 `HEADERS sid=501`），但**原上游连接**对其不响应（无 HEADERS / RST / GOAWAY）；换一条新 h2c 连接后立即恢复（同 mock、独立网关探针通过，mock 的 HTTP/1.1 直连同时正常）。

**归因未定，不写成根因**：`SETTINGS_MAX_CONCURRENT_STREAMS=250` 是**并发流**上限，不是累计请求数上限——顺序请求并发恒为 1，累计 250 次后失效是**异常现象**，说明存在跨请求累计占用的状态，但本实验**未区分**下列机制：协议层流计数未随取消回收（发生在网关侧还是 mock 侧）、handler 并发额度、应用层未响应取消。同样，"修复前阻塞在连接池准入阶段"也只是推断——HEADERS 未上线只能定位到「未发出」，不能定位在哪一层被挡住。**该现象支持继续调查连接分布（P2），不能证明 P2 能改善真实 D/F。** 定位已执行（绕过网关的直连 HTTP/2 客户端对照）：见 §5.6——网关侧被排除，归属收窄到 Go mock 二进制，但其内部（应用代码 / Go HTTP/2 栈）未再切分。

**边界**：本认证只证取消传播与上述两个观察，未测吞吐/TTFT/600s 停顿；mock 静默 1h 是实验配置（放大量级），不代表真实上游的滞留时长；自建 p1mock/p1gw/p1gw2 实验容器跑完即删，未动现场生产容器。**原始 pcap 未留存**（台架清理时删除）；构建指纹、命令与帧时间摘要见 §5.5，可据此复跑复核，但本节数字本身不可独立复核。

### 5.6 250 墙切分实验：直连 HTTP/2 客户端对照（2026-10-09）

**方法**：`h2probe`——裸 `h2` 0.4 客户端（MD5 `70d2b39a997a89777bdadf51944cac53`），**不含任何池/泵/记账代码**；单连接顺序发起流，读到首块后 `RST_STREAM(CANCEL)`（或不取消收完）。四变体交叉 mock 实现 × handler 存活期 × 是否取消：

| 变体 | mock | handler 存活 | 取消 | 结果 |
| --- | --- | --- | --- | --- |
| V1 | Go `mock-llm:h2c` | 静默 1h（`token_interval=3600000`） | ✓ | **墙@第 251 流**（`stage=first-data` 5s 超时），250 个取消全部发出 |
| V2 | Go `mock-llm:h2c` | 快速（`token_interval=10`，~50ms 收尾） | ✓ | 无墙，260/260，RST×260 |
| V3 | Go `mock-llm:h2c` | 快速 | ✗ | 无墙，260/260 收完 |
| V4 | Rust `mock-llm`（同契约，MD5 `fc068becd29e7ffc428480eebf03b407`） | 静默 1h | ✓ | 无墙，260/260，RST×260 |

**观察（帧级）**：V1 墙窗与网关实验逐帧同形——`HEADERS sid=501 + DATA` 已上线（1791559749.350936），`ready()` 未阻塞，之后 mock 对该流永久沉默；V2/V4 各 260 帧 CANCEL 全部送达；V3 无 RST。

**排除（分层，只写排除掉了什么）**：

1. **xlite 池/泵/记账代码**：排除——V1 客户端没有这些代码仍复现同墙。
2. **客户端准入阻塞**：排除——V1 的 `ready()` 通过、HEADERS 上线，卡的是「发出后无回应」。
3. **累计完成流致墙**：排除——V3 无墙。
4. **h2c 协议/栈共性（"RST 不释放流额度"）**：排除——同为取消流，V2（Go mock，handler 结束即恢复）与 V4（Rust 栈立即恢复）都不墙。

**未切开的最后归属**：墙需要同时满足「Go `mock-llm:h2c` 二进制 × 流被取消时其 handler 仍存活」。剩余候选是该二进制的**应用代码或其所用 Go HTTP/2 栈**对"已重置但 handler 未收尾的流"不归还每连接额度——二者再切需要第二个 Go 服务端实现做对照，本轮未做。**因此本实验不宣称墙是"mock 应用 bug"还是"Go 栈行为"。**

**对 P2 / D/F 的含义**：实验台架的 4×24 mock 农场就是这个 Go 二进制；真实 D/F 配置下 handler 存活约 5~6s（`ttft=500,out=500,interval=10ms`），比 1h 短得多但非零——客户端中途取消时额度会被占用至 handler 收尾。真实 LLM 上游（vLLM 等）不共享此实现，是否有同类行为**未测**。建议 P2 的 C0/C1 对照记录各档取消率，必要时以 Rust `mock-llm` 重跑一组作对照臂。

**证据留存**：V1~V4 抓包与 `SHA256SUMS` 保留在台架 `~/p1/evidence/`（本次不删）；帧时间转录（V1 墙窗 1791559749.233~1791559749.350、V2/V4 RST 计数）在跑测 stdout 中。

构建 `ab25593`（含 P1 修复与 `GET /api/pool`），喂法与 capsweep v2 逐项相同（`k6-customer` + `~/v88t/k6.js`，16k VU / 60s + 30s 爬坡，24 路农场现役 config `ttft=500,out=500,interval=10ms`）：

**对 D/F 的含义**：连接分散轴的最大效果 ≈ +3.4% 完成速率（且以 TTFT 为代价），**远小于 D/F 差距（11%~55%）**——P2 不是 D/F 的主解，剩余差距需在 P3（资源观测）与 P4（数据泵）找。若以完成速率为目标，C1（125×64）是当前最优折中；若 TTFT 优先，维持 C0。
不能只降低 cap 而保留连接上限，再把减少负载或增加首字等待称为优化。

先筛选 D@30,000、F@40,000，再验证 D@20,000／30,000、F@35,000／40,000。
容量实验保持线程数、Mock、脚本和硬件不变；各方案都记录池等待及实际拨号数。
如果连接已充分分散、等待很低且吞吐不变，应停止继续增大连接上限。

## 7. P3／P4：由观测决定优化位置

| 现场观测 | 下一步 | 不应直接得出的结论 |
| --- | --- | --- |
| 某地址池持续满且等待增长 | 核对有效上限、路由偏斜、计数和对端限制 | 整台网关必然只有约一万流容量 |
| 网关单核热点、其他核空闲 | 比较连接分散、任务调度和4／8／16线程 | 线程越多越快 |
| 锁／跨核唤醒占比高 | 在真实生产路径定位具体锁与任务 | 立即改成线程局部池 |
| 软中断、丢包或重传先增长 | 检查网卡队列、CPU分布和链路容量 | 扩大HTTP/2窗口即可解决 |
| Mock CPU饱和或定时器输出变慢 | 隔离／扩展Mock，增加直连控制组 | 全部耗时增长都是网关执行时间 |
| k6处理体耗时增长 | 固定脚本与采样，量化客户端开销 | 同VU就是同压力 |
| 通道和下游写入成为CPU大头 | 试验已就绪块的批量处理 | 删除数据泵必然更快 |
| 有接收信用耗尽证据 | 独立试验窗口／释放节奏，检查内存 | 默认窗口仍是64KiB |

线程实验在连接分布方案筛选后进行，每次只改变一个因素。
已就绪块批量处理不得等待凑批、延迟首块或解析SSE；保持字节与结束状态不变。
没有性能采样证据时，不先实施线程局部池、动态池、连接预热或窗口扩容。

现有 [`pump_multiplex_bench.rs`](../../crates/xlite-h2-pool/tests/pump_multiplex_bench.rs)
使用208流、每流400块、每块200字节的内存链路。分析阶段三次重复中，数据泵比多任务直读快约62%～76%。
它不等同于生产中合并的驱动器／数据泵，也没有现场网络和Mock；
只能用作筛选证据，不能当作现场提升承诺，也不支持盲目删除数据泵。

### 7.1 P3 资源观测结果（2026-10-09，128 核 Xeon 6530 / 1TB，全链路回环）

方法：C0 配置（250×32）固定，喂法同 capsweep v2，8k/16k/32k VU 各 60s+30s 爬坡；1s 粒度采样 per-component CPU（网关进程+每线程、k6、24 mock）、软中断、回环字节、TCP 重传、`/api/pool`；另加 k6→单 mock 直连控制组（DM500/DM1000）与 perf 采样（活跃窗+尾窗）。容器均无 CPU 配额（补 P0 留白）。

**资源归因**（活跃窗均值，单位=核）：

| 档 | 网关 | k6 | mock 合计 | 单地址 in_flight 峰值 | 回环速率 |
| --- | --- | --- | --- | --- | --- |
| 8k VU | 7.8 | 19.8 | 38.4 | 394 | 244 MB/s |
| 16k VU | 7.9 | 16.8 | 51.6 | 778 | 309 MB/s |
| 32k VU | 7.9 | 16.4 | 51.6 | 1510 | 308 MB/s |

- **整机不饱和**：峰值 ~76/128 核忙碌；in_flight 1510/addr ≪ 8,000 额度（第三次确认额度不绑定）。
- **网关 8 个 tokio worker 各 ≈0.99 核即封顶**，且 CPU 不随吞吐变化（L8→L32 吞吐差 38% 而 CPU 纹丝不动）。perf 判明为**内核态每包实工**（活跃窗：数据拷贝 5.6%、自旋锁族 ~10%、nft/conntrack ~5%、TCP 查找/收发栈若干；用户态 Rust 占比很小，头名为 `mpsc::Sender::send` 1.8%）——**不是应用层自旋 bug**（早前假设被 perf 推翻）。
- mock 合计随吞吐走（38→52），单 mock ~2.2 核，直连对照下单 mock 可达 4.1 核/72k chunks/s——**mock 有余量**，非绑定。
- 侧写：回环 TCP 重传每档数万（缓冲压力旁证，~0.5% 段数）；netfilter/conntrack 每包 5~7% 开销（docker 规则挂在链路上）。

**线程曲线**（§7 规定的 4/8/16 单因子实验，16k VU 同喂法，外加 32/64 找平台）：

| `TOKIO_WORKER_THREADS` | 完成速率 | TTFT avg | duration avg |
| ---: | --- | --- | --- |
| 4 | 965/s | 612ms | 13.5s |
| **8（现场现值）** | **1503/s** | 550ms | 8.6s |
| 16 | 2006/s | 531ms | 6.5s |
| **32** | **2171/s** | **528ms** | **5.97s（=流自然时长，排队消失）** |
| 64 | 2094/s（回落） | 535ms | 6.2s |

**运行参数建议**：长流高压负载类（16k VU、500 chunk/流）取 **`TOKIO_WORKER_THREADS=32`**——相对现场现值 8，完成速率 +44%、duration 从 8.6s 塌回自然时长 5.97s、TTFT 亦改善；**64 回落，「线程越多越快」不成立**（§7 禁令的实验回应）。单轮差异（32 vs 16 为 +8%）未做重复，精度需要复测；netfilter 旁路与绑核是次级候选（未做）。

**对 D/F 的含义**：现场四网关均跑 `TOKIO_WORKER_THREADS=8`；若 10-07 基准同此配置，worker 欠配是 D/F 完成速率差距的**头号已证杠杆**（+44% 量级对 11%~55% 差距）。但 10-07 配置不可回填（§4.1），此关联是**假设**；验收实验是 §8 的对标复测（workers=32 vs New API），本轮不做。

## 8. 对照实验与验收

### 8.1 执行规则

- 两侧使用相同脚本、k6镜像、采样、`CHUNK_MAX`、Mock、超时、爬坡和排空设置。
- 对标保持 `MOCK_BATCH=1`；扩大Mock规模另作两侧相同的台架控制实验，不混入代码收益。

- 建议长流恒定载荷延长到1,800秒，预先固定观测窗口，例如相对运行时间300～1,800秒。
  必须以实际scenario为准，窗口不能跨入降载或排空。
- 同步采集网关、Mock、k6的各核CPU、内存、句柄、软中断、网络及池快照。
- 不缩短超时来“消灭”长尾，不混用采样降级重试；发生降级或OOM的轮次不能作为有效对标。

### 8.3 通过条件

验收分为两道门：

1. **正确性门**：P1永久测试通过；无新增字节损坏、跨流干扰、错误状态吞掉或取消残留。
2. **性能门**：在预先固定的窗口内，重复结果支持完成速率提升及完成时间缩短；
   同时首字、失败率、池等待和资源使用不发生不可接受的退化。

三轮仅用于初筛，不足以保证统计显著；若波动与收益同量级，增加轮次和窗口。
首字容忍幅度、资源预算及目标收益应在实验前结合基线波动约定，不能看完结果再改标准。
首字变差但吞吐变好只算有代价的折中，不能宣传为两者兼得。
不通过则保留结果、恢复实验配置，继续定位；不自动改生产默认值。

2. **性能门（候选 XL32 vs 基线 XL8）：不通过**——长流形速率 +0.0%、duration 相同。`TOKIO_WORKER_THREADS=32` 的收益是 **chunk 率绑定**的（短流形 +46%，长流形为零）；两形态下 32 均无害（TTFT/失败/资源同量级），部署建议应写成「高 chunk 率负载取 32，慢 chunk 率长流任意」。

**对 D/F 的回答**：在 125s 流 × 16k VU 下，**10-07 的差距不复现**——当前构建与 New API 成功吞吐持平、可靠性与资源占优。F 组 −12%~−14%（40k VU、0.5.x 时代构建、未知配置）**仍未解释**；嫌疑收窄到三个轴：**更高 VU（40k）**、**构建代差**（0.5.0 vs 当前含 P1 修复）、**流形细节**（10-07 精确配置不可回填，§4.1）。下一测试点：40k VU 档。

**边界**：16k VU 非 40k；125s 流为 F 类近似而非 10-07 精确流形；NA 失败分类仅取到 503（3.1k/16.4k，其余无状态类=超时/传输，未细分）；240,000 的精确重复源于场景每 VU 恰好完成 15 轮迭代（1830s ÷ 125.5s），成功口径由此对齐。

### 8.7 40k VU × 慢吐字流形探测（2026-10-10，探针口径；**勘误：非原始 F 形状**）

**形状勘误（GPT-6 复查）**：本节流形 = 500 块 × 250ms = **4 块/秒/流**，原始 F = **3,000 块 × 20ms = 50 块/秒/流**（§2.1）；同 40k VU 下吐字压力低 **12.5 倍**。本节**不能**代表 F@40k，「压力轴反转」降级为「慢吐字 40k 观察」，**D/F 调查不因此收口**。实验本体：125s 慢吐字流形 × 40k VU × 1 轮 × 3 臂（轮换）。判据跑前预注册：「压力差距出现」= XL 成功速率低于 NA 超 2%，或 XL 出现失败/TTFT 恶化。结果——**差距出现，但方向反转**：

| 臂 | 成功流数 | 固定窗速率 | TTFT avg | duration avg | 失败率 | 网关 CPU |
| --- | --- | --- | --- | --- | --- | --- |
| XL8 | **600,000**（=40k×15 满载） | **320.2/s**（=40k÷125s 理论满载） | 505ms | 2m5s（自然） | **0.00%** | 7.4 核 |
| New API | **246,760**（495,372 尝试 − 248,612 失败） | 266.9/s（含虚增） | **11.8s**（med 10.7s） | **2m29s**（med 2m41s） | **50.18%** | 23.9 核 |
| XL32 | **600,000** | 320.2/s | 505ms | 2m5s | **0.00%** | 12.0 核 |

**观察**：①XL 两臂在慢吐字 40k 下**满载**（成功数=需求上限、时延=自然值、0% 失败）；②**NA 在 40k 大幅劣化**：50.18% 失败（传输类 212,732 + 503 类 8,367 = 221,099 已分类，**27,513 未分类**——已列两类不足以排除客户端 / Mock / 资源配置限制，「连接层崩塌」定性**撤回**），TTFT 膨胀 23 倍、duration 膨胀 20%；**口径修正（§2.2）**：600,000÷246,760=2.43 与「0.41×」均为**整轮成功数比，不是速率比**——成功流吞吐须按同窗成功完成数÷窗口时长单列，本轮未做，**速率声明撤回**；③XL8=XL32 输出逐项相同，且 **XL32 比 XL8 多用约 62% CPU（12.0 vs 7.4 核）零完成收益**——该工作点支持 **8 线程**为优选（§7.1「32 无害」在此收窄：慢吐字长流工作点取 8）。

**预注册判定（按数比口径）：该流形下 XL 稳定性显著优**（成功数比 2.43、失败 0% vs 50.18%，远超 ±0.5% 噪声）；速率比未按同窗口径计算（见上）。1 轮口径，加轮条件视 F@40k 复跑结果再定。

**D/F 调查状态（勘误后）：未闭环**。已排除：①构建代差（§8.6）；②慢吐字流形 × 16k/40k（§8.5/本节）。**但原始 F 的吐字压力（50 块/秒/流）从未受测**——不能宣称原始 F 差距反转，也不能断言「只剩环境原因」。**归因范围修正（GPT-6 核对 ZIP）**：原始 D/F 参数、采样与超时**均有记录**（§2.1），仓库两份 k6 脚本 SHA256 与原始记录一致；**不可回填的仅是历史网关配置**；原始 mock 地址为 `10.56.88.24:8081-8104`（本文早前误记 `10.99.255.102:4101-4124`，以 ZIP 为准）——**「可以准确复跑原始 F」成立**。下一步：直接复跑 **F@40k（3,000 块 × 20ms，同哈希 k6 脚本 + 原始采样配置：`KEEP_BODY=true`、`CHUNK_MAX=64`、体分析采样 10%、`STREAM_TIMEOUT=600000`、`GRACEFUL_STOP=900s`、30s 爬坡、640s 恒定）**，不得再以 125s/4 块每秒替代。

**边界**：探针口径 1 轮/臂；NA 50% 失败使其速率须连失败率解读（成功口径已单列）；NA 轮 k6 采样器 PID 采集缺失（该轮 k6 CPU 未计）；传输类失败未再细分诊断（属 NA 侧容量问题，非本方案对象）。

**结论**：

1. **差距不复现，且大幅反转**：XL8 窗口完成速率反超 NA 18.8%（266.9 vs 224.6/s）；XL32 为 NA 的 **2.77×**。预注册判据（XL8 < NA 10%）**不成立**。NA 在忠实 F 形状下 80.11% 失败（**传输类 131,289 + 503 类 3,497 = 134,786 已分类，10,727 未分类**）、TTFT 均值 32.3s、全轮成功流仅 36,124。
2. **worker 杠杆在真 F 形状完全迁移**（勘误 §8.7 的「长流形不迁移」→ 该结论仅限慢吐字形）：8→32 完成速率 **+133%**（266.9→621.8/s），duration 从排队 2m21s 塌回自然 1m4s，XL32 达到 40k VU 需求满载；代价是网关 CPU 7.7→21.6 核。**CPU 效率（完成口径，勘误：此前 36k/0.95k 为算错）**：XL8 ≈ **2,082 次/核·分钟**（267.4×60÷7.7）、XL32 ≈ **1,727 次/核·分钟**（621.8×60÷21.6）——**XL32 买的是绝对吞吐，每核效率反而是 XL8 更高**；NA 同口径 224.2×60÷38.2 ≈ 352，但**含 80% 失败迭代**，成功口径效率无同窗成功计数不可得（§2.2），三方成功效率**不可直接比较**。
3. **与 10-07 记录的对照**：10-07 的 XG@F40k 窗口 375/s、汇总 247/s，NA 领先 12~14%；本台架忠实形状下 XL8 汇总 264.2/s（与 247 同量级）、窗口 266.9/s（与 375 差距或源于窗口定义/网关配置差异），**NA 一侧差距悬殊**（其 10-07 档为 `newapi_1002` 部署，本实验为 `new-api:v8-sentinel`）——环境/版本差异使两侧数字不可逐位对齐，但**本台架忠实 F 形状下的方向与幅度是明确的**。

**D/F 调查状态**：原始 F 形状已受测——**10-07 差距在本台架不复现**。剩余不可对齐项：历史网关配置（§4.1 唯一不可回填项）、New API 部署代差、mock 拓扑（本实验本机 24 路 vs 原始 `10.56.88.24:8081-8104`）。**部署建议（经 §8.9 交错复测确认）**：高吞吐吐字流（F 形）取 **32 线程**（§8.9：3×3 交错 +134.9%、±0.1%、TTFT/duration 同步改善、零失败）；慢吐字形（≤4 块/秒）取 8（§8.7，单轮证据，待复测）。线程对照的受控说明：两臂同为 `xlite-after`（MD5 `b488aab0…`）、同 env（H2C=1、250×32）与农场/脚本/机器，**仅 `TOKIO_WORKER_THREADS` 不同**；§8.8 执行序 f_xl8→f_na→f_xl32，轮间 90s 冷却 + 农场健康检查（资源恢复）。

**边界**：探针口径 1 轮/臂（差距 2.77× 与 80% vs 0% 失败无歧义，加轮条件未触发）；窗口=60~640s（原始窗口定义未记录）；`IN_TOKENS=100` 为脚本默认、mock `ttft=500` 为台架默认（原始值未记录）；窗口完成速率含失败迭代（§2.2 口径），成功完整流速率无同窗计数、只列全轮成功数。

### 8.9 XL8/XL32 交错复测（2026-10-11，GPT-6 指令：线程对照补强）

**受控单因子**：同构建（`xlite-after`，MD5 `b488aab0…`）、同池参数（H2C=1、250×32）、同农场配置（3,000 块×20ms）、同 k6 脚本/喂法（原始采样配置）、同机器；**仅 `TOKIO_WORKER_THREADS` 不同**（8 vs 32）。执行序严格交替：xl8→xl32→xl8→xl32→xl8→xl32；每轮 90s 冷却 + 农场健康检查（每轮 `farm_health=200`，资源恢复确认）；F 形 40k VU、30s 爬坡 + 640s 恒定。窗口实测边界（k6 进度行，可复算）：

| 轮 | XL8 窗口 (起点→终点) | XL8 速率 | XL32 窗口 (起点→终点) | XL32 速率 |
| --- | --- | --- | --- | --- |
| 1 | (60.0s,0)→(640.0s,153,161) | 264.1/s | (59.5s,0)→(639.5s,360,000) | 620.7/s |
| 2 | (60.1s,0)→(640.1s,153,173) | 264.1/s | (60.0s,0)→(640.0s,360,000) | 620.7/s |

配套指标（三轮一致）：**失败率两臂全程 0.00%**；TTFT avg XL8 676/676/677ms vs XL32 570/565/565ms；duration avg XL8 2m22s（排队）vs XL32 1m5~1m6s（自然时长 64s）；网关 CPU XL8 **7.7 核**（三轮恒定）vs XL32 **22.3/22.4/22.8 核**；mocksum 53.9~54.4 vs 55.7~57.7 核。CPU 效率（完成口径）：XL8 ≈ **2,058 次/核·分钟**、XL32 ≈ **1,655 次/核·分钟**——XL8 每核效率更高，**XL32 买的是绝对吞吐与时延**。

**判定（对 §8.8 预注册的候选确认）**：XL32 的 F 形收益 **+134.9%**（264.3→620.7/s）在 3×3 交错下 **±0.1% 波动内完全可复现**，且 TTFT（−16%）与 duration（−55%）同步改善、零失败、资源与恢复无异常——**候选确认成立（GPT-6 终审 SHIP）**：在本工作点（F 形 50 块/秒、40k VU、**本台架**）`TOKIO_WORKER_THREADS=32` 可作为**该负载档的部署建议**。**但这是有代价的优化，不是无成本优化**——网关 CPU 7.7→22.3~22.8 核（约 2.9×），换取 +134.9% 吞吐与 TTFT/duration 改善；每核效率反降（2,058→1,655 次/核·分钟），核预算紧张的场景须按 §8.9 的取舍表权衡。**限定**：不自动修改生产默认值（§8.3）；不外推至 D 组流形、其他硬件或其他压力档（慢吐字形 §8.7 仍支持 8 线程；他硬件需另证）。

**边界**：XL32 窗口 Δ=360,000 三轮恒定恰为需求满载（40k×9），故 620.7/s 是**需求受限下界**而非系统上界——系统真实容量 ≥ 此值；k6 采样 r1 两轮缺 k6 CPU（PID 采集时序），r2/r3 正常；整轮迭代数（XL8 204.7k~205.6k、XL32 404k~421k）随排空略有波动，故以窗口口径为准。

**下一步（GPT-6 序）**：③真 F 下 perf 采样（8 vs 24/32）；④轻量诊断；⑤取消压力回归。D 形本机瓶颈归因（mock 容量假设）待 mock CPU 采样验证。
