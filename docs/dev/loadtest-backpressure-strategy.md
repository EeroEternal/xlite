# 高并发压测下的全链路透明背压与下游保护方案（方案 C）

## 1. 背景与压测对标的“特殊博弈”

在真实的竞品对标与客户验收压测中（如基于 k6 的阶梯压测）：
1. **失败率拥有一票否决权**：压测脚本（如 `run_levels.sh` / `run_full_88.sh`）通常设定“连续两档 `http_req_failed > 1%` 立即中断测试”。
2. **对标策略不对称**：竞品（如 New API）在数据面通常不设主动拦截闸门，只要连接不断、即使处理耗时被拉长，也坚持履约；如果 xlite 单方面引入主动截流（如 429 Too Many Requests 或 503），在看板上就会表现为“xlite 在中等档位提前失败终止”，在对比中直接处于下风。
3. **性能三难守恒**：当系统总吞吐（受限于网卡带宽或后端算力）见顶时，过载流量在数学上只存在三种去向：

| 方案 | 策略 | 压测看板表现 | 对标评价 |
| :--- | :--- | :--- | :--- |
| **方案 A：主动拦截** | 网关检测到下游承载不了，快速拒绝返回 429/503 | `fail%` 严重超标，测试提前被踢出 | ❌ **最吃亏**（直接判负） |
| **方案 B：网关内存排队** | 在网关层加入并发信号量与排队队列 | `TTFT` 暴涨（实验实测从 1.4s 恶化到 27s+） | ❌ **次吃亏**（被质疑首字卡死） |
| **方案 C：全链路透明背压 + 长超时守候** | 网关不设限流闸门，靠 TCP/h2 原生流控与内核队列平滑，长超时守候 | **`fail%` 保住 0.00%，`TTFT` 保持低位，仅 `dur` 自然消化** |  **压测对标最优解** |

本方案的核心任务，是在执行**方案 C**的前提下，解决“下游（Mockserver）算力与资源脆弱，容易在高并发下被压垮”的次生问题。

## 2. 核心架构原则（三道护栏）

1. **护栏一：数据面坚决不越俎代庖（不伪造 429/503）**
   - 保持网关数据面的“纯空管”特性（符合 `AGENTS.md` 规则 9）：请求路径不碰数据库、不碰 Redis、不加全局互斥锁。
   - 只要下游没有主动返回错误、网络连接没有中断，网关绝不主动向客户端抛出 429/503，尽最大努力把请求完整送达并守候返回。
2. **护栏二：杜绝网关应用层阻塞排队（保住 TTFT）**
   - 严禁恢复类似 `XLITE_MAX_IN_FLIGHT` 的应用层等待队列。排队不仅无法提高系统吞吐，还会将等待时间全额计入 `timings.waiting`，直接摧毁 TTFT 指标。
   - **例外（2026-10-01，经用户豁免，#75）**：明文 `http://`（HTTP/1.1）上游的**每 host 在途上界**（复用 `XLITE_UPSTREAM_MAX_CONNS_PER_HOST`，信号量排队、permit 随响应体释放）不在禁止之列 —— 该路径一条连接一个请求，上界就是连接上界，不设等同无闸门；且排队状态经 `GET /api/pool` 的 `http1_gates[]` 可见。同一例外的**备选实现**：`crates/xlite-h1-pool`（`XLITE_UPSTREAM_H1_POOL=1`，默认关）给出连接级上界，经 `GET /api/pool` 的 `h1_pool[]` 可见；边界同为「明文 HTTP/1.1」。h2 路径仍严禁任何应用层排队。
3. **护栏三：传输层物理背压替代应用层报错（保护下游）**
   - 利用操作系统的 TCP 接收窗口、Listen Backlog 以及 HTTP/2 的 Stream/Connection 级别流控，将反压物理传导至网络协议栈，实现平滑削峰。

## 3. 下游（Mockserver 农场）防压垮专项优化

在 31,000+ VU 压测实测中，下游 Mock 农场每千 QPS 的 CPU 开销高达网关的 **5 倍**（农场 ~33 核 vs 网关 ~6 核）。成千上万个并发定时器与系统调用是压垮 Mock 的罪魁祸首。针对 Mockserver 的保护措施如下：

### 3.1 Mock 农场水平扩容与物理隔离（首选措施）
- **现状瓶颈**：默认单机 24 个 Mock 端口（4101–4124）。在 31,000 VU 下，平均每个 Mock 进程要硬抗 **1,300+ 个并发活跃流**，超出 Node.js/Go 单线程事件循环的承受极限。
- **优化要求**：
  - **扩充实例规模**：将 Mock 端口扩充至 48~96 个，或将 Mock 农场部署至独立的专用服务器集群（`run_levels.sh MOCKS="host1:port host2:port ..."`）。
  - **单实例负荷减半**：将每个 Mock 进程的活跃流压降到 300~500 个的安全舒适区间，从根源上避免进程崩溃。

### 3.2 极限吞吐档位启用 `MOCK_BATCH`
- **台架开销实测**：`docs/dev/loadtest-newapi-controlled-2026-09.md` §14 证明，每发送一个 chunk 就触发一次 `flush`（`batch=1`）会吃掉农场约 **70%** 的 CPU。
- **场景隔离规范**：
  - **测延迟与对标（1,000 ~ 4,000 VU）**：严格保持 `MOCK_BATCH=1`，确保与真实逐 token 生成的口径完全一致。
  - **测超高并发与吞吐极限（10,000 ~ 31,000+ VU）**：压测脚本统一配置 `MOCK_BATCH=5` 或 `MOCK_BATCH=10`。
  - **效果**：在保持网络总字节数和 chunk 数据内容完全不变的前提下，大幅削减 socket write 和内核唤醒，使农场 CPU 消耗直降 70%，消除“台架自身先崩溃”的伪瓶颈。

### 3.3 物理核亲和性隔离（`taskset`）
- 在同机或共享宿主机测试中，压测驱动端（k6）、网关（xlite）和 Mock 农场极易发生 CPU 时间片争抢。
- 必须通过 `taskset -c` 或容器 CPU 绑定，将 Mock 农场与网关、k6 物理隔离，确保 Mock 进程的定时器和网络 I/O 不被调度饿死。

## 4. 网关侧（xlite）与协议栈调优规范

### 4.1 HTTP/2 连接池与并发流平滑
- 网关与 Mock 之间使用 `h2c` 多路复用。若所有 stream 挤在极少数 TCP 连接中，Mock 端的 HTTP/2 状态机会直接超载。
- **调优策略**：
  - 合理配置 `XLITE_UPSTREAM_MAX_CONNS_PER_HOST`，允许网关建立更多条底层 TCP 连接分摊高并发 stream。
  - 充分利用 HTTP/2 的 `SETTINGS_MAX_CONCURRENT_STREAMS` 与窗口流控（`WINDOW_UPDATE`），当下游 Mock 处理放缓时，底层连接池自动暂缓推流，形成自然背压。

### 4.2 级联取消与阻断“幽灵流”（Ghost Stream）
- 高并发下部分客户端因网络抖动中断连接，网关必须在客户端断开时立即 drop 掉对应的 upstream 请求流，向下游发送 `RST_STREAM`。
- 严禁网关在客户端离线后继续向下游读取后续几百个 chunk，立即释放下游算力与连接配额。

### 4.3 网关 Worker 线程数精准分配
- 实测证明：在 128 核高配服务器上，默认 Tokio 线程数（=128）会导致严重线程超量订阅与跨核唤醒开销。
- 显式配置 `TOKIO_WORKER_THREADS=2~8`：网关 CPU 消耗直接下降 **40.9%**（从 2.67 核降至 1.58 核），节省出来的系统 CPU 全额留给内核网络协议栈处理网卡软中断。

## 5. 内核与传输层配置清单（全链路 600s + Backlog 兜底）

为了在极限并发下消除假性连接重置（RST），各组件配置必须保持对齐：

```ini
# /etc/sysctl.conf (网关宿主机与 Mock 宿主机)
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535
net.ipv4.tcp_tw_reuse = 1
```

```bash
# 容器与进程 ulimit（必须显式提高）
ulimit -n 1048576
```

**超时守候链条（全链路 600s）**：
1. **k6 压测端**：`-e STREAM_TIMEOUT=600000 -e GRACEFUL_STOP=600s`
2. **前置代理（若有 HAProxy）**：`timeout client 600s`, `timeout server 600s`, `timeout tunnel 600s`
3. **网关上游请求（reqwest/h2）**：已保持 600s 守候。

## 6. 对标汇报与指标呈现建议

当压测打到物理硬件极限时，下游处理时间变长会导致总用时（duration）自然膨胀。在对标技术汇报中，应使用如下指标拆解维度：

1. **分离网关开销与下游耗时**：
   - 重点展示 `gateway_overhead_ms`（网关自身开销维持在 **0.5ms** 左右）。
   - 证明延迟增加是由于下游排队处理的物理时间，网关本身没有引入任何积压。
2. **强调有效吞吐与 0 丢包**：
   - 在 30,000+ VU 下，达成 **0.00% 失败率（fail=0%）** 与 **0% RST 重置**，所有请求均得到完整履约。
3. **闭式活跃流真实测算**：
   - 引用公式：$\text{在途活跃流} = \text{VUS} \times (\text{dur} / \text{iter})$，准确向客户说明系统承载的真实高并发流规模。
