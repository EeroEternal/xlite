## 6. 结论

1. **高载能力（可下结论）**：短流组 xlite 的在途流是 New API 的 **1.6×–6.7×**（A 11,639→19,445、E 6,715→17,462、B 8,187→55,196），长流组能把 ~60k 在途流挂满且尾延迟更优。这与 `docs/dev/loadtest-report-2026-09-29.md` 的方向一致。
2. **S1 相对 S2（待归因）**：低载 TTFT 基线从 555/605ms 抬到 707ms（+100~150ms，B/D/E/F），同时长流高载的尾延迟与失败率大幅改善（D/F 稳定区上移 2~3 档）。**这是一个吞吐/稳定性的取舍，不是单向改进**。
3. **数据缺口**：`env.txt` 未记录网关构建与 mock `ttft/ti`，S1/S2 的基线差异无法归因。按 [`../manual/v88-rig.md`](../manual/v88-rig.md) §1.3 的契约，网关镜像 ID/版本与 mock 参数应当随结果目录落盘。

## 7. 后续动作

1. **补口径**：压测结果目录的 `env.txt` 增加网关镜像 digest/版本、`XLITE_*`、mock 的 `ttft/ti/out`；否则跨轮对比不可复现。
2. **归因那 +150ms**：确认 S1 与 S2 是否同一构建；若是，单独排查首字节路径（连接建立/预热）；但注意它同时换来了长流高载的稳定性，需要按目标场景取舍。
3. **对标口径**：对 New API 只用「在途流 + qps」，不用 `fail≤1%` 档位（S3 的 0% `fail` 来自未喂满）。

## 8. 复核：外部报告《xgateway-dual vs v88-dual 压测对比》的结论裁定

针对一份基于**同两批数据**（`20261006T112016Z` 记作 xgateway-dual、`newapi_1002/v88-dual` 记作 v88-dual）的对比报告的复核。**数字层面合格**（本文抽查其 A–F 逐档 TTFT/QPS/fail/chunk p99，与原始 `summary.json`/k6 日志一致），但**比较方法缺了并发归一化**，导致短流组结论写反。

### 8.1 致命点：按名义 VU 比 TTFT，而不是按在途并发

60k VU 时，v88-dual 的 HTTP 时长与迭代时长严重脱节（`iter − dur` 达 23–47s），即名义 VU 被折算掉，**实际只服务了 xg 的 1/1.7 ~ 1/6.7 并发**：

| 组 | v88@60k 在途流 | v88 TTFT p50 / p99 | xg 取**相同在途流**的档位 | xg 该档 TTFT p50 / p99 | xg@60k 在途流（对照） |
|---|---:|---|---|---:|
| A | 11,639 | 715 / 883 ms | xg@10k（在途 9,996） | **708 / 755 ms** | 19,445 |
| B | 8,187 | 750 / 11,815 ms | xg@8k（在途 7,996） | **722 / 1,293 ms** | 55,196 |
| E | 6,715 | 751 / 3,800 ms | xg@7k（在途 6,996） | **710 / 919 ms** | 17,462 |

**按在途并发对齐后，短流组 A/B/E 的 TTFT p50 与 p99 也都是 xg 更优**。报告的「短流下 v88 TTFT 更快、是真实优势」不成立——那是拿「半载」比「满载」。

### 8.2 机制：为什么会出现「5s / 60s 分界线」

分界线在数据里真实存在，但成因不是报告写的「v88 做了更激进的准入控制（少排队、低延迟）」——该说法无证据，且与其自身 C 组观察（v88 放任排队、p99 到 3×）自相矛盾。真实机制是 v88 的 `iter − dur` 开销把名义 VU 折算掉了：

| 组 | v88@60k `dur` p50 | `iter` p50 | `iter − dur` | 实际在途流 |
|---|---:|---:|---:|---:|
| A（5s 流） | 5.5s | 28.6s | **23.0s** | 11,639 |
| B（5s 流） | 6.1s | 44.9s | **38.7s** | 8,187 |
| E（5s 流） | 5.9s | 52.7s | **46.8s** | 6,715 |
| C（60s 流） | 128s | 128s | ~0 | 60,000 |
| D（60s 流） | 254s | 254s | ~0 | 30,000 |
| F（60s 流） | 268s | 268s | ~0 | 60,000 |

- **短流**：v88 每圈有 23–47s 花在 TTFT 与 `http_req_duration` 都看不到的地方（k6 等连接/建连，或未受限的 chunk `Trend.add`）。60k VU 只兑现 6.7k–11.6k 并发 ⇒ 上游农场未被压满 ⇒ TTFT 平。
- **长流**：HTTP 时长 60s+ 盖过该开销，`iter ≈ dur`，名义 VU ≈ 真实在途 ⇒ 这时才是**公平比较**，v88 的 TTFT 爆掉（C p50 886 vs 736ms、p99 5,606 vs 1,784ms @30k）。

⇒ 真正的分界线是「v88 的瓶颈会不会把名义 VU 折算成真实并发」，不是「流时长」。

| 报告结论 | 裁定 |

### 8.4 裁定

- **没有任何一组、任何维度上 v88-dual 优于 xg**；它看起来好的地方（短流 TTFT），都是它少干了活。修正后的一句话：峰值吞吐 xg 6/6 胜、D 组容量 2×、等并发下延迟 xg 全胜、长流尾延迟 xg 全胜。
- **报告的数据处理可信**（逐档数字与原始文件一致），缺的只是**并发归一化**这一步：任何 TTFT 对比都应附该档的**在途流或 qps**，不能只按名义 VU。

> **本节的边界**：v88 的 k6 脚本缺 `CHUNK_MAX` 采样（无 `chunk_samples_added`）、档位步进与 xg 不同（20 档 vs 60 档），这些影响**绝对 QPS**；但「等并发下 xg 仍赢」是算术结论，不受其影响。n=1、非同窗口交错，结论限于本次两批数据。
