# 受控对照：xlite vs New API 实验台复现（2026-09-25）

性质：一次对照实验的原始数据与能定性的结论，**不是**发版数据，也**不是**已交付的性能承诺。
喂法规则见 [`../manual/v88-rig.md`](../manual/v88-rig.md)。

目的：客户现场的 V88 日志里 New API `ttft p50 = 708ms`，实验室同喂法下 xlite `502ms`。
把这 206ms 拆开——是**网关差异**还是**环境差异**？做法是把客户的 New API 镜像搬到同一台
实验机、同一份 rig、同一批 mock、同一天跑。

## 2. 结果一（最重要）：低载下两者**没有差别**

| 网关 | TTFT p50 | TTFT p99 | dur p50 | fail | qps |
| --- | ---: | ---: | ---: | ---: | ---: |
| xlite 0.2.0 @1000 VU | **501.8ms** | 509.7 | 5.90s | **0.00%** | 160.1 |
| New API `v8-sentinel` @1000 VU | **504.2ms** | 535.7 | 5.84s | **0.00%** | 158.8 |

mock 自己的 `ttft = 500ms`。**xlite 加 2ms，New API 加 4ms。**

⇒ **客户日志里的 708ms 不是 New API 的网关开销。** 它是客户环境特有的（HAProxy 跳数 /
跨机 Postgres（host 22）/ 客户那代 k6 / 主机负载），本轮**没能定位**是哪一项。

⇒ **纯延迟上 xlite 没有可主张的优势。** 见 §4 的更正。

## 3. 结果二：New API 的请求路径每请求打一次 DB（4000 VU 起撞墙，归因待补 ledger）

| 档位 | xlite（TTFT / dur / fail） | New API · **客户配置** | New API · **放开 DB 连接** |
| --- | --- | --- | --- |
| 1000 VU | 501.8ms / 5.90s / **0.00%** | 504.2ms / 5.84s / 0.00% | 504.2ms / 5.83s / **0.00%** |
| 4000 VU | 502.2ms / 5.86s / **0.00%** | 505.6ms / 5.87s / **12.39%** | 505.3ms / 5.87s / **0.57%** |
| 10000 VU | 502.2ms / 5.85s / **0.00%** | 6487ms / 3m47s / **99.81%** | 1235ms / 1.23s / **99.99%** |
| 31000 VU | 507.3ms / 5.90s / **0.00%** | 100%（快失败） | 83%（300s 只完成 **6** 个请求） |

- **客户配置** = `SQL_MAX_OPEN_CONNS=2000` + PG `max_connections=2000`（`init-db.sh` 与文档记录的现场值）。
- **放开 DB 连接** = `SQL_MAX_OPEN_CONNS=8000` + PG `max_connections=10000`，两者都加 `--ulimit nofile=1048576`。

### 3.1 因果链（压测期间实测采样）

| 档位 | pg 连接数 | New API CPU | **PG CPU** | fail |
| --- | ---: | ---: | ---: | ---: |
| 1000 VU | 12–39 | ~10 核 | 35–49% | 0.00% |
| 4000 VU | 29 → **3919** | 10–29 核 | 100% → **1881%** | **0.57%** |
| 10000 VU | ~2900 | 1.3–7.6 核 | **7370%**（74 核） | 99.99% |
| 31000 VU | ~2600 | 0.2–10.9 核 | 1500–2400% | PG 直接失联 |

1. **4000 VU 那堵墙与 DB 连接数有关，但「缺的就是连接数」这条因果链尚未成立。**
   单次观测：PG `max_connections` 2000 → 4000 → 10000 时 fail = 23.33% → 12.39% → 0.57%；
   但**放开后的同一配置（10000 / 8000）在多次运行里又出现过 12.4% 与 12.98%**（见 §10.4）——
   波动 20×，与配置差异同量级。**⇒ 这一档不能用来归因，也不能用来推 New API 的容量。**
   要把它变成结论，先补 **run ledger**：每次运行记 `时间 / PG max_connections /
   SQL_MAX_OPEN_CONNS / 4000 VU fail% / dur / note`。没有 ledger，本节与 §10.4 互相矛盾，
   `changelog` 与 `../manual/v88-rig.md` §8 里那句「主要是 DB 连接数配置」也不成立。
2. **放开连接数之后瓶颈上移到 Postgres 的 CPU**：10000 VU 时 PG 吃满 **74 核**，New API 只剩 1–7 核可干；
   错误分布变成 `failed to connect to postgres` ×**12207**。根因是架构性的：**New API 每个请求的结算
   （billing settlement）都要和 Postgres 往返一次**，所以它的吞吐天花板 = DB 层的吞吐天花板，而不是网关自身的转发能力。
   这一条（每请求打 DB）由失败签名与 `pg_stat_activity` 直接支持，不依赖第 1 条的因果。
3. 31000 VU 时 PG 直接不响应（`server closed the connection unexpectedly`），整个栈挂死。

### 3.2 能说与不能说

- **能说**：New API 的请求路径**每个请求都要打一次 DB**（结算），并发天花板因此由 Postgres 层决定；
  xlite 的请求路径完全不碰 DB/Redis。这是架构差异，可现场验证。
- **不能说**：「New API 在 10k 并发下不行」。本轮 PG 与网关共处一机、被 10000 条并发连接拖垮；
  客户现场 PG 是**独占 host 22**，结论可能完全不同。
- **不能说**：「放开连接数后 4000 VU 就只剩 0.57%」——同一配置复跑出现过 12.4% / 12.98%（§10.4），
  波动 20×。要用这个数必须先补 §3.1 的 run ledger。
- **要验**：客户 New API 的 Postgres 在两轮 v88 压测里的 `pg_stat_activity` 峰值与 CPU。
  若峰值贴着 `max_connections=2000`，他们那套「60000 VU 无失败」也可能同样是在 DB 墙前面停住的
  （客户 rig 的真实活跃流是 3000–4000，见 [`../manual/v88-rig.md`](../manual/v88-rig.md) §2）。

## 4. 更正：此前「xlite TTFT 领先 206ms（−29%）」的结论作废

该结论来自「**实验室 xlite 502ms** vs **客户历史日志 New API 708ms**」—— 未控制 k6 版本、
主机负载、HAProxy 跳数、Postgres 拓扑。§2 的受控实验证明：**同条件下 New API 也是 504ms**。

⇒ 对客户**不要主张延迟优势**。客户只要在自己机器上原样跑一次 xlite 就会发现是平局。

## 5. New API 实验台部署配方（可复现，含踩过的坑）

```bash
# 1) 镜像（客户给的 OCI tar）
scp new-api-v8.tar.gz bodesi@101:~/
docker load -i ~/new-api-v8.tar.gz          # → new-api:v8-sentinel

# 2) 依赖
docker run -d --name postgres-bench --network host \
  -e POSTGRES_USER=root -e POSTGRES_PASSWORD=123456 -e POSTGRES_DB=new-api \
  postgres:16-alpine -c port=8007 -c max_connections=4000 -c shared_buffers=8GB -c work_mem=16MB
docker run -d --name newapi-redis --network host \
  redis:7-alpine redis-server --port 6380 --save "" --appendonly no

# 3) 网关（--ulimit 必加！）
docker run -d --name newapi-bench --network host --ulimit nofile=1048576 \
  -e SQL_DSN="postgresql://root:123456@127.0.0.1:8007/new-api" \
  -e REDIS_CONN_STRING="redis://127.0.0.1:6380" \
  -e PORT=13000 -e GIN_MODE=release -e TZ=Asia/Shanghai \
  -e SQL_MAX_OPEN_CONNS=2000 -e RELAY_MAX_IDLE_CONNS=100000 \
  -e RELAY_MAX_IDLE_CONNS_PER_HOST=50000 -e STREAM_FLUSH_EVERY=1 \
  -e SESSION_SECRET=benchsecret -e CRYPTO_SECRET=benchsecret \
  new-api:v8-sentinel

# 4) 首次启动建表 → 用 adapt 过的 init-db.sh 灌 24 条 channel（指向 10.99.255.102:4101-4124）→ 重启
```

坑（每一个都真实踩到过）：

| 坑 | 现象 | 处置 |
| --- | --- | --- |
| **容器 `ulimit -n` 默认 1024** | 1000 VU 还能过，4000 VU 起大面积失败 | `docker run --ulimit nofile=1048576`。**两侧必须一致**，否则比的是 fd 上限 |
| **`docker rm postgres` 丢数据** | 重建容器后 channels 归零 → 100% 快失败（14k qps 重试风暴） | 重建后必须重跑 `init-db.sh`；或挂 volume |
| **`max_connections` 打满** | `error settling billing: failed to connect` | 抬高 PG `max_connections`；根治要看 §3 的结论 |
| **101 的 `:3000` 已被占用**（k8s NodePort 上另有一个 New API） | `bind: address already in use`，容器起来又退 | 换 `PORT=13000` |
| **`latest` 未钉版本** | 实验台拉到 `k6 v2.3.0`（镜像建于 09-21），客户 09-18 那轮是更老的 | 比 qps 时要么钉 digest，要么两侧同版本 |

## 6. 未做与边界（这些都不能从本文外推）

- New API 只跑 **1 副本、无 HAProxy**；客户是 2 副本 + HAProxy。§3 的高载结论**不可外推**。
- k6 用 `grafana/k6:latest`（跑时已是 **v2.3.0**）。同一 xlite、同一档位、只换 k6 版本
  （v2.3.0 vs v0.57.0），**TTFT 不变**（502.2 vs 502.9ms），**qps 变**（318.8 vs 390.5）——
  即 qps 一列对 rig 版本敏感，延迟一列不敏感。
- 实验台 102 上有别人的 Prometheus（617% CPU、load 15–35），**绝对值不可与客户机器比**。
- 未测：两侧在同机 10/25 GbE 或 loopback 下的真实并发上限；New API 2 副本下的表现。

## 8. 可观测的边界：为什么 `x-xgateway-*` 那两个头不进对标表

曾提议给 xlite 加 `x-xgateway-queue-wait-ms` / `x-xgateway-upstream-ttft-ms` 以便对标。
结论：**不进对标表，只作自家归因工具（P3）**。先把归属钉死——这一条容易记错：

| 事实 | 证据 |
| --- | --- |
| 这两个头是 **xgateway（xrouter）自己的**约定，不是对标 rig 的一部分 | `src/adapter/generic/{stream_handler,byte_forward,nonstream,dashscope}.rs` 里的 `.header("x-xgateway-queue-wait-ms", …)` |
| **客户原版脚本不读任何响应头** | 包里两份（`bench/0924/deploy_origin/loadtest/k6/k6.js` 采样版、`deploy_origin/deploy88/k6.js` 无采样版）对 `x-xgateway` / `ERR_SAMPLE` / `queue_wait_ms` **0 命中** |
| 读这两个头的是 **XG 侧我们自己后来加的那版** | `xrouter/scripts/loadtest/k6/k6.js`（含 `ERR_SAMPLE` + header 采集；xlite 侧同源：`scripts/loadtest/k6/k6.js`）。`xg-dual` 日志头部写的就是它：`ERR_SAMPLE=0.01 | k6=/root/loadtest_xg/k6/k6.js` |
| New API **没有任何计时头** | 其 71 MB 二进制里 `x-*-ms` 形态 **0 命中**（只有 `X-Accel-Buffering`，其余全是 AWS S3 SDK 的头） |
| 因此两侧日志里这两列都是空的 | `xg-dual`：`qw p50=- p99=- \| uttft p50=- p99=-`；`v88-single` 连这两列都没有（老脚本） |

**三条推论：**

1. **不能进对标表**：客户原版 rig 读不到；即便是我们自己那版 rig，New API 也不发 → 只能是单边列，客户第一句就会问「为什么只有你有」。
2. **加它不会让任何可比指标变好**：rig 里 `ttftMs.add(res.timings.waiting)` 与 `addHeaderTrend(...)` 是两条独立路径，头只往两个新 Trend 塞样本，**不参与 `ttft / dur / fail / qps` 的计算**。纯增量诊断，不存在「用头刷分」。
3. **`queue-wait-ms` 对 xlite 是死列**（没有准入闸门 → 恒 0）。只有 `upstream-ttft-ms` 有信息量：用来回答「31000 VU 下 TTFT 从 502ms 涨到 1598ms，那 1.1s 是在上游还是网关」。

### 对标表不需要它

三段分解用现有列就能做，`v88-rig.md` §4 那几列已经够：

```
首字前开销 = ttft p50 − mock_ttft（B 组 500ms）
首字后膨胀 = dur p50 − ttft p50 − 流式理想（500 × ti）
rig 侧空档 = iteration p50 − dur p50
```

B 组 @1000 VU 代入本文 §2 的受控数据：

| | 首字前开销 | 首字后膨胀 | rig 侧空档 |
| --- | ---: | ---: | ---: |
| xlite | **+1.8ms** | +398ms | +10ms |
| New API | **+4.2ms** | +336ms | +20ms |

首字前开销 **1.8ms 对 4.2ms** 就是 §2「低载平局」的全部依据——没用一个额外的头。

> 顺带一条待复核的观察：首字后膨胀 xlite 比 New API 高约 **60ms**（+398 vs +336，≈8% vs 6.7%）。量级在噪声边缘，但若可复现，那就是「每 chunk 成本」这条 P1 的直接证据。

## 9. 链路上的三个瓶颈，与「最高上限」该怎么取

整条链路上有三个可能的瓶颈（**链路 / mock 农场 / 网关**），前几节只量化了链路与网关。
把农场单独测出来：k6 直连 24 台 mock（loopback，绕开网关与链路），B 组配置。

| 流数 | dur p50 | dur p90 | fail | TTFT p50 | wire | 农场 CPU（24 容器合计） |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4000 | 5.81s | 5.82s | 0.00% | 501.5ms | 63 MB/s | ~13 核 |
| 8000 | 5.94s | 6.01s | 0.00% | 511.0ms | 124 MB/s | ~42 核 |
| 16000 | 6.21s | 9.54s | 0.00% | 515.5ms | 198 MB/s | 47–115 核 |
| **31000** | **8.99s** | 10.3s | **0.00%** | 547.6ms | **303 MB/s** | **~113 核**（宿主 100% busy） |

对照过网关（xlite，1 GbE，同 B 组）：

| 流数 | 过网关 dur p50 | **直连农场 dur p50** | 差异来自 |
| ---: | ---: | ---: | --- |
| 4000 | 5.86s | 5.81s | ≈ 0 |
| 8000 | 7.12s | 5.94s | 链路 |
| 16000 | 11.99s | 6.21s | 链路 |
| 31000 | **31.38s** | **8.99s** | **链路（22.4s）** |

**结论一：1 GbE 台架上先绑的是链路，不是农场也不是网关。** 直连农场的 31000 流只到 1.63×，
而它要 303 MB/s —— 1 GbE 实用上限约 112 MB/s。

**结论二：农场有自己的软天花板**——从 16000 流起 dur 由 6.21s 抬到 8.99s，CPU 到 ~113 核。

| 链路 | B 组链路容量 | 农场软天花板 | **先绑的是** |
| --- | ---: | ---: | --- |
| 1 GbE（客户现在） | **~5900 流**（算法与实测锚点见 [`../manual/v88-rig.md`](../manual/v88-rig.md) §2） | ~16k–31k 流 | **链路** |
| 10 GbE（升级后） | ~45000 流 | ~16k–31k 流 | **农场** |

⇒ **`cap = min(链路, 农场, 网关)`，三个数都必须实测。** 客户的「3 万并发」在 10 GbE 上会先撞**农场**。

### 9.1 「设一个最高上限」的三条硬约束

1. **值必须实测，不能拍脑袋。** 上一轮 cap=6000 而 1 GbE 的 B 组容量约 **5900 流**
   （[`../manual/v88-rig.md`](../manual/v88-rig.md) §2）→ cap 与容量同量级，根本没起到保护作用
   （实测 TTFT 1.6s → 27.7s，`dur` 未改善）。
2. **cap 不提高吞吐。** 四臂实测 goodput 恒定 **676–894 req/s**；cap 只决定难看在哪个指标上：
   不设闸 → `dur` 难看；设闸+无限等 → `TTFT` 难看；设闸+有界预算 → `fail%` 难看。
3. **只有一侧设闸 = 对设闸方不利。** 同一负载下设闸方的 `fail%` 高、不设闸方是 0%
   （New API 没有闸门）。**要设就两侧同策略**，或把「过载语义」写进规格与客户约定。

**诚实版「不至于很难看」**：`cap = 下游容量`；超额 **429 + Retry-After**（不是排队）；
延迟分位**只在成功请求上统计**，`fail%` 单独如实报；且两侧同口径。

### 9.2 边界

- 农场那组在**共享宿主**上测（k6 + prometheus + 24 mock 同机），宿主在 31000 流时已 100% busy；
  `docker stats` 逐容器 CPU 有噪声，**绝对值需在 mocks 独占 / k6 `taskset` 隔离后复测**。
- 直连用的是 HTTP/1.1（每 VU 一条连接），网关到 mock 走 **h2c**（多路复用）。两者的
  **每 chunk 发射成本相同**，但连接管理成本不同，所以这组只能给农场的**量级**，不能当精确容量。

## 10. 共享约束下的对标：能分胜负的只有两个指标

对标的前提是**双方共用同一条链路、同一批 mock** —— 所以 `C = min(C_链路, C_农场)` 是**共享的**，
`VU > C` 的档位对两个网关**没有区分度**（双方一起进入链路受限区）。能分胜负的只剩网关自身两项：

1. **TTFT p50**（首字前）
2. **`gateway_overhead_ms`**（首字后；用 mock 自己的 `ts` 抵消 mock 定时抖动）

### 10.1 受控对照（同机 / 同 24 mock / 同 k6 镜像 / 同脚本 / 同档）

B 组 @1000 VU，两侧 `checks/请求` 均 **2.00**（同口径），`KEEP_BODY=true` + `KEEP_SAMPLE=1`，
k6 用**客户自己的镜像 v2.2.0**：

| 指标 | **xlite 0.2.0** | **New API v8-sentinel** | 差 |
| --- | ---: | ---: | --- |
| `chunk_interval_ms` p50/p90/p95/p99 | 11/11/11/12 | 11/11/11/12 | 相同 |

**关于那 70ms 的 `dur` 差异**：它来自 **mock 自身的定时抖动**（同一份 mock，两次跑的平均 chunk 间隔
10.798ms vs 10.676ms，×500 块 = 61ms）。而 `gw_oh`（`receiving − ts 跨度`）**恰好抵消这个抖动**，
所以在那个指标上 xlite 反而是领先的。**`dur` 不能用来比网关；`gw_oh` 才能。**

### 10.2 客户环境里的 ~205ms 不是 New API 的代码

v88 日志里 New API `TTFT p50 = 708ms`（= mock 500 + **208ms**）且 `gw_oh p50 = −205ms`。
这两者是**同一个延迟的两面**：网关若把客户端可见的流起点推迟 D，则 TTFT `+D`、`receiving` `−D`。

但**同一镜像、同一 k6、同一 mock 配置**在我的实验台上，New API 只有 `TTFT +4.2ms` / `gw_oh +4.2ms`。

⇒ **那 ~205ms 来自客户现场的路径（HAProxy 跳 / 网络），不是 New API 的转发实现。**
⇒ **未验证的推论**：若它是路径上的**常量**延迟，则两侧同加、不影响相对比较；若它与「该网关首块的发送方式」
耦合（HAProxy 缓冲 / 首块 flush 时机），就**不一定**同加。要钉死这一点，只能把 xlite 也放到客户那条路径上测
`gw_oh`（或在实验台上复现同一条 HAProxy 跳），不能靠推断。

### 10.4 关于 New API 容量的边界

同配置（PG `max_connections=10000` / `SQL_MAX_OPEN_CONNS=8000`）下，4000 VU 的 fail 在多次运行中

>    分开（单轮 A / 单轮 B 看不出来，正好印证 §9.1 的判读纪律）。

#### 关键结论：两项贡献在分布上**互补且不重叠**

| 归因对象 | 隔离质量 | 作用面 | 证据 |
| --- | --- | --- | --- |
| **`TCP_NODELAY`（A0→A1）** | ✅ 单项（diff 恰 2 行） | **只动中位数**：p50、p90 | p50 −6.6% / p90 −16.7% 完全分离；**p95、p99 与 A0 重叠（p99 仅 −1.1%，等于零）** |
| **「0.3.0 其余 13 项」（A1→A2）** | ⚠️ **整体，不可拆** | **只动尾部**：p90、p95、p99 | 三档全部完全分离（−9.2% / −13.0% / −10.4%）；**p50 无变化（+0.3%）** |

旁证（`min`/`max` 的离散度）：A2 的极值三臂中最紧 —— `min` **−32.4 / −26.6 / −34.5**，
而 A0 为 **−282.9 / −129.2 / −31.9**、A1 为 **−185.3 / −28.6 / −77.0**；
`max` A2 **63.7 / 94.2 / 34.2** vs A0 **308.7 / 123.8 / 124.2**。
即 A2 把**大离群值**压掉了 —— 与「尾部收益」定性一致。

**一个必须记录的混淆项**：若 A2 运行时 `XLITE_CATALOG_RELOAD_SECS` 取默认 **5**（而非 0），
则 `#13` 的写锁会在**每次路由变化**时取一次（reload 循环每 5s 只检查一次）；本轮目录冻结、路由没变 ⇒ 一次都没取（§12.6）。**本轮未记录该环境变量**
（见 §11.6 待办），因此不能排除它。

~~**全部未跑**~~ → **D 臂已跑（见 §11.7）**；而「0.3.0 相对 0.2.0 把尾部压低了约 10–13%」这句

先验倾向（**未实测，不作为结论**）：平推 1000 VU 时 k6 按 VU 复用连接，建连集中在开跑瞬间的

`#1` backlog 128 大概率不触顶；热路径 CPU 那 8 项（`#4/5/8/9/11/12/14`）
更可能解释尾部。但本机 `TcpExtListenOverflows` 累计 **576574**、`TcpExtTCPSynRetrans` 累计 **429232**

### 11.7 口径修正 + D 臂（隔离 backlog）

#### 11.7.1 修正：活跃流公式**系统性低报 42%**

`report.py` 原先用

```
活跃流 = qps × dur_p50          ← 旧（错）
```

`qps` 是**整轮**平均（含 ramp-up 与 gracefulStop 排空段），排空段把稳态速率拉低，
于是这个乘积**系统性低报**并发。k6 是闭式负载，一个 VU 同一时刻只有一个请求在飞，正解是

```
活跃流 = VUS × (dur / iter)     ← 新（闭式）
```

实测差距很大：**4000 VU 档，闭式 2670 vs 稀释式 1557 —— 低报 42%**。
影响面：凡是用旧公式判 `LINK-BOUND` 的对标结论都**偏乐观**（低估占用带宽）。
现在链路预算一律用闭式；`qps × dur` 只留作对照列 `active_streams_diluted`。
从**对方日志**反推、拿不到 `iteration_duration` 时才退回稀释式，且必须标为**下界**
（本仓 `v88-rig.md` §2 里那组 3000–4000 就属这类，已加注）。

#### 11.7.2 run ledger 新增列（已合入 `scripts/loadtest/`）

| 列 | 为什么必须记 |
| --- | --- |
| `GATEWAY_BACKLOG` + `GATEWAY_BACKLOG_SOURCE` | 监听套接字**自己的** `Send-Q`，**不是**内核 `net.core.somaxconn` —— libc `SOMAXCONN` 默认 128，会把 `TcpListener::bind` 的 backlog 压到 128 |
| `<LEVEL>.acceptq` | 每档 accept 队列（`ss` 的 `Recv-Q`）**峰值**。逼近 backlog 即判**触顶**，是「backlog 是否成为瓶颈」的直接证据，与负载高低无关 |
| `XLITE_CATALOG_RELOAD_SECS` | §11.4 的混淆项 `#13`。不记录，「reload 尾刺」就永远只能停在推断 |
| `K6_IMAGE_ID` / `K6_VERSION` | tag 会漂（`grafana/k6:latest` 已知会改 qps 一列），镜像 ID 才是实际跑到的那个 |
| `K6_SCRIPT_SHA256` | 与 md5 并列；跨机核对「跑的是哪份脚本」的强指纹 |

跨机时（网关不在 k6 同机）`ss` 观测不到网关，必须显式传 `GATEWAY_BACKLOG=<n>`，否则报告记 `unknown`
并在 `report.py` 里告警。**D 臂实验即为跨机场景的实例**（k6 在 102、网关在 101）。

`gateway_overhead_ms`（ms）：

**① backlog 零贡献 —— 有直接证据**

accept 队列峰值 ≈ backlog 的 **12%**，且与 backlog 设多少**无关**：

| 对比（同窗口） | p50 | p90 | p95 | p99 |

> ⚠️ **本条只对 ≤1000 VU 成立。** §12.3 在 **4000 VU** 复测时发现 backlog 128 → **34.6% 失败**，
> backlog 65535 → 0.00% —— 它不是延迟杠杆，但**是并发上限杠杆**。下面这句话的"低载"限定词必须保留：

⇒ **1000 VU 平推下 backlog 从来不是瓶颈**。§11.4 枚举里的 `#1` 只在**建连突发**
（客户 1000→31000 爬坡、`0.2.0` 现场丢 SYN 那类）才有意义，**不是低载延迟手段**。
`D→A2`（其余 12 项）同样四个分位全部重叠（+1.2% / +1.1% / +1.7% / −2.3%）。

**② ab4 的 `A1→A2` 尾部收益没有复现**

| 分位 | ab4 结论 | ab7 结论 |
| --- | --- | --- |
| p90 | −9.2% 完全分离（p=0.05） | **+1.1% 重叠** |
| p95 | −13.0% 完全分离 | **+1.7% 重叠** |
| p99 | −10.4% 完全分离 | **−2.3% 重叠** |
| p50 | +0.3% 重叠 | +1.2% 重叠 |

⇒ ab4 那一档是**假阳性**，§11.5 第 4 条已撤回。

**③ 原因：窗口漂移比被测效应还大**

同一个 `A1` 二进制，跨两个窗口（相隔约 45 分钟）**四个分位全部完全分离**：

| ab4 `A1` 范围 | ab7 `A1` 范围 | 变化 |
| --- | --- | ---: |
| p50 [0.4654, 0.4803] | [0.4525, 0.4604] | −3.0% |
| p90 [2.0530, 2.2348] | [1.9560, 2.0100] | −6.8% |
| p95 [5.0261, 5.5967] | [4.5870, 4.9100] | −9.8% |
| p99 [11.7599, 12.8349] | [10.8450, 11.3400] | −9.1% |

**三条方法学后果**（比任何单点数字都重要）：

1. **不可跨窗口合并样本。** 合并会凭空造出「完全分离」—— 把 ab4 的 `A1` 与 ab4 的 `A2` 拼一起，
   p90 会看似分离，实际只是漂移。
2. **n=3 的「完全分离」是弱证据。** 零假设下 3×3 完全分离的概率 = `1/C(6,3)` = **5%**；4×3 = 2.9%。
   这正是 ab4 骗过我们的机制。**必须换窗口复现才算数。**
3. 要下 **<10%** 的结论，必须**同窗口交错 ≥3 轮**，最好 ≥5 轮；窗口漂移本身就有 −3% ~ −10%。

**④ 复现了的那个：`TCP_NODELAY`**

把 `A0` 的 4 次（ab4×3 + ab6×1）与 ab7 的 `A1`/`A2` 比。这是**跨窗口**比较，本不该做 ——
但效应（7–22%）远大于漂移（3%），且 `A0` 自身 range 极窄，所以成立：

| 对比 | p50 | p90 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: |
| `A0`(4) → `A1`(3) | **−9.3%** ✅ p=2.9% | **−21.5%** ✅ | **−18.3%** ✅ | **−11.6%** ✅ |
| `A0`(4) → `A2`(3) | **−7.3%** ✅ p=2.9% | **−17.3%** ✅ | **−13.3%** ✅ | −12.9% 重叠 |

`A0` 的 p50 range = [0.5014, 0.5078]（spread **1.3%**），与 `A1`/`A2` 的差距 **7–22%** —— 远大于 3% 漂移。

> ⚠️ 这条**同时修正 §11.4**：那里说「`TCP_NODELAY` 只动中位数、对 p95/p99 无效」，
> 是 n=3 窗口内比较的产物；补上第 4 个 `A0` 样本并换窗口后，
> **NODELAY 对整个分布都有效（−9% ~ −22%）**。

**⑤ 结论修正表**

| 结论 | 状态 |
| --- | --- |
| **`TCP_NODELAY` 是 xlite 低载延迟的主要立足点（−9% ~ −22%，全分位）** | ✅ **复现，可承诺** |
| **backlog 65535 在 ≤1000 VU 无延迟贡献**（accept 队列峰值 17 / 128） | ✅ 直接证据；**但 4000 VU 下它从 34.6% 失败救到 0.00%**（§12.3）—— 是并发上限杠杆，不是延迟杠杆 |
| **其余 12 项（零拷贝 / 热路径 CPU）在 1000 VU 无可测收益** | ✅ 两窗口一致为零 |
| 「0.3.0 相对 0.2.0 把尾部压低 10–13%」 | ❌ **撤回**（§11.4 / §11.5 已标） |
| `TCP_NODELAY` 只动中位数、对 p95/p99 无效 | ❌ **修正**：全分位有效 |

**⑥ 台架侧的一个坑（记录以免重踩）**

ab6 那轮有 **15 个请求挂满 600s**（`ttft max=600000ms`，上游静默无响应），
因 `GRACEFUL_STOP` 默认 600s，k6 一直等它们，把每轮从 4 分钟拖到 **10.5 分钟**。
加 `GRACEFUL_STOP=30s` 后回到 4m02s。**做多轮对照务必给 `GRACEFUL_STOP` 封顶**，
否则个别挂死请求会让整轮时长失控（本轮 12 轮改成 9 轮、耗时约 37 分钟）。

## 12. 产能落脚点：每千活跃流的核数（B2 / B3 / B1）

§11.7.4 的结论是：**低载延迟已经被 `TCP_NODELAY` 吃完**，其余 12 项在延迟上无可测收益
（`D→A2` 四个分位全部重叠）。那它们的收益面在哪？—— **每千活跃流的核数**。

从本节起把判决指标从 `gw_oh` 换成**网关进程 CPU**：采样 `/proc/<pid>/stat` 的
`utime+stime` 增量 ÷ 墙钟（100 Hz tick）。载荷仍走 k6（102）→ 网关（101）→ 24 mock（102），跨 1 GbE。

>
> ⚠️ **归因已单独复核过**：首测与复测之间**同时**变了 `nofile` **和** `KEEP_SAMPLE`
> （首测日志的 checks 比是 2.00 = 全量解析，复测是 1.10 = 0.1），所以「+11% 就是 `nofile`」
> 当时并不成立。按 2×2 补齐（1000 VU、同窗口交错两轮）后：`SAMPLE=1` 是 **154.32 / 154.29 qps**、
> `SAMPLE=0.1` 是 **154.59 / 154.63 qps**（差 **0.2%**，cores 完全重叠），两档客户端占用都是
> **91%**；而 nofile=1024 那格是 **138.7** ⇒ **`nofile` 确实是全部原因**，`KEEP_SAMPLE` 在
> 1000 VU 下零效应。完整 2×2 与出处见 §13.6 第 0a 条。

**四条结论：**

1. **CPU 随线程数单调下降**：128 → 2，**2.670 → 1.579 核，省 40.9%**（首测 40.4%，结论不变）。
2. **尾部同时大幅改善 —— 不是拿 CPU 换延迟**：p90 **−17%**、p95 **−45%**、p99 **−51%**；
   代价是 p50 **+14%**（0.5498 → 0.6281 ms）。
3. **吞吐与失败率零变化**；在 1000 路 / ~155 请求/s 这个载荷下，**2 个线程已经不是瓶颈**。
4. **归一化后几乎不动（重要）**：首测 2.93 / 2.87 / 2.70 / 1.74 核/千流，复测
   **2.93 / 2.86 / 2.69 / 1.73** —— 封顶同时压低了分子与分母，所以
   **§12 的归一结论与臂间比较全部成立，只有绝对核数要按复测值读**（见 §12.3(3)）。


机制（**推断，未直接测**）：128 个 worker 服务 1.4–2.4 核的工作量 ⇒ 严重过量订阅，
work-stealing、任务唤醒跨核迁移、缓存行反弹都是纯开销；线程数与真实并行度同阶后这些开销消失。
p50 的小幅上升可解释为 accept / 首字节路径与在飞流争抢仅有的 2 个线程。

> **运维结论：不要把 `TOKIO_WORKER_THREADS` 留在默认（= nproc）。**
> 在 128 核机上等于**白烧 40.9% CPU，还换来更差的尾巴**。
> 应按活跃流规模给一个小值（1000 流量级 2–8），并在部署里显式写死。
> **但"随负载怎么缩放"尚需复测**（1000 流的最优不一定是 4000 流的最优）—— 见 §12.3。

### 12.2 B3：`XLITE_UPSTREAM_MAX_CONNS_PER_HOST` —— 零效应

`acquire()` 排队。单臂 `A2`、`TWT=8`、1000 VU 平推 120s：

| 128 | 2.204 | 0.4866 | 2.273 | 5.308 | 11.573 | 0.00% |

### 12.3 B1：四臂在 4000 VU —— backlog 是一道**硬悬崖**，而 CPU 四臂无差

单臂固定 `TWT=8`、`MAX_CONNS_PER_HOST=32`，**4000 VU** 平推 120s，两轮交错：

| 臂 | backlog | cores（轮1/轮2） | **fail%（轮1/轮2）** | qps |
| --- | ---: | --- | --- | ---: |
| `A0` | 128 | 2.374 / 2.397 | **34.63 / 34.63** | 224.3 |
| `A1` | 128 | 2.330 / 2.341 | **34.65 / 34.65** | 224.2 |
| `D` | 65535 | 2.323 / 2.335 | **0.00 / 0.00** | 146.3 |
| `A2` | 65535 | 2.309 / 2.343 | **0.00 / 0.00** | 146.4 |

**(1) backlog 128 在 4000 VU 下塌了 —— 而且两次复现到小数点后两位**

`A1 → D` 的 diff **只有 backlog 一行**（外加 `set_reuseaddr`，对全新监听套接字无作用）。
它把失败率从 **34.63–34.65%** 变成 **0.00%**，两轮各自复现。
失败是**瞬时**的（`ttft min=0`、`http_req_duration min=0s`、`max` 仅 6.41s），不是超时 ——
即**建连阶段就被拒**。旁证：101 累计 `TcpExtListenOverflows = 188375`。
内核侧 `tcp_abort_on_overflow=0`、`somaxconn=65535`、`tcp_max_syn_backlog=65535` ——
**`somaxconn` 再大也救不了 libc `SOMAXCONN=128` 压进 `TcpListener::bind` 的那个 128。**

> **⚠️ 这条修正 §11.7.4 的 "backlog 零贡献"：那个结论只在 ≤1000 VU 成立。**
> 真实形态是：**backlog 不是延迟杠杆，而是并发上限杠杆** ——
> - ≤1000 VU：accept 队列峰值 17/128，调不调都一样（§11.7.4）；
> - 4000 VU：128 直接溢出到 **34.6% 失败**，65535 为 0.00%。
>
> 这与 §11.4 枚举里 `#1` 的原始描述（"30k-VU ramp 丢 SYN"）一致，也和客户现场
> `0.2.0` 的 RST 现象一致 —— **只是我先前把"低载测不出"误写成了"没有贡献"。**
>
> ⚠️ **但"悬崖"的根因后来查清了：是网关的 `nofile`，不是 `backlog` 本身。**
> 本节那些臂的网关跑在 **nofile=1024** 下（§13.6 0a 才发现），而 `backlog` 只决定这个 fd 封顶
> 以**拒绝**还是以**排队**的形式表现出来。把两件事摆成 2×2 后四格逐项复现了本节与 §13.6 的数字：
> **nofile 1024 + backlog 128 ⇒ 34.49% 失败 / 225 qps**（= 本节 `A0`/`A1` 的 34.63% / 224.3）；
> **nofile 1024 + backlog 65535 ⇒ 0.00% 失败但只有 147.6 qps**（= 本节 `D`/`A2` 的 0.00% / 146.3）；
> **nofile 1048576 + backlog 128 ⇒ 0.00% 失败 / 620.6 qps**（backlog 128 在 fd 够用时**无害**）。
> 所以「4000 VU 下 backlog 128 塌成 34.6%」这句话要加限定：**是在 fd 上限被耗尽的前提下**。
> 完整 2×2 与结论见 §13.6 第 0a 条。

**(2) CPU：四臂没有可测差异**

`A1` / `D` / `A2` 的 cores = **2.330/2.341、2.323/2.335、2.309/2.343** —— 互相在 **0.4%** 内，
远小于臂间应有的效应。`A0` 略高（2.374/2.397，比 `A1` 高 **2.5%**），但 n=2 且在噪声边缘。

⇒ **零拷贝与热路径 CPU 那 12 项在 4000 VU 下同样测不出 CPU 收益。**
结合 §11.7.4（延迟无收益），这批改动的收益面**在现有台架上两头都测不出来**。

**(3) 顺带纠正一个指标口径**

CPU 并不随**并发流数**线性增长：1000 VU（复测 **~911 流 / 154.7 req/s**）用 **2.449 核**
（`TWT=8`），4000 VU（~2670 流 / 146.3 req/s）用 **2.33 核**。
两档的 **请求/s 只差 5%**，CPU 也只差 6% —— **CPU 由请求速率驱动，而不是由并发流数驱动**。
所以「每千活跃流核数」这个说法本身是误导的：更贴切的产能指标是
**每千请求/s 消耗的核数 ≈ 16 核**（本载荷下）。
先前文档里的「~2.1 核/千流」只在"1000 流恰好对应 ~140 req/s"这个巧合下成立，不要外推到别的 token 长度。

### 12.4 交互检验：backlog 悬崖与线程数无关，线程数的 CPU 收益在 4000 VU 同样成立

§12.3 的所有轮次都用 `TWT=8`，所以必须先排除"34.6% 失败是我把线程降下来造成的"。
`A1`（backlog **128**）在 4000 VU 扫 `TOKIO_WORKER_THREADS`：

| `TOKIO_WORKER_THREADS` | backlog | **fail%** | cores |
| ---: | ---: | ---: | ---: |
| 128 | 128 | **34.64%** | 2.563 |
| 32 | 128 | **34.59%** | 2.502 |
| 8 | 128 | **34.59%** | 2.330 |

**两条结论：**

1. **失败率与线程数无关**（34.59–34.64%）。⇒ 4000 VU 的 backlog 悬崖是**纯 backlog 属性**，
   不是降线程引入的。§12.1 的建议在这条轴上安全。
   更硬的一点：**失败的绝对计数也几乎相同**（12 422 / 12 430 / 12 433，分母都约 35 900）——
   这是**确定性容量上限**的特征，不是时序竞态。
2. **`TOKIO_WORKER_THREADS` 的 CPU 收益在 4000 VU 同样成立**：128 → 8 线程 = **2.563 → 2.330 核（−9%）**。
   注意幅度差异：1000 VU 时是 **−40%**（§12.1），4000 VU 时是 **−9%** —— 载荷越高，
   过量订阅的相对浪费越小（真实并行度上去了）。**所以"该给几线程"必须按负载定，不能抄一个常数。**

### 12.6 `RwLock` → `ArcSwap`：读者不再被写者阻塞（**结构性**）；CPU 无收益（假设证伪）；尾部未达门槛

**假设**：`store.rs` 的路由快照是 `Arc<std::sync::RwLock<Snapshot>>`，每个请求都要在这把锁的
原子上做一次读加锁 —— 128 个 worker 就是 128 个核在同一条缓存行上来回弹。
若成立，换成无锁的 `ArcSwap` 应当回收 §12.1 里相当一部分 CPU。

**改动**：`Store.inner` → `Arc<ArcSwap<Snapshot>>`；三个读点改 `load()`，`reload()` 改
「比较 + `store`」。两臂同一父提交 `195418f`，只差这一个改动：

| 臂 | 快照读路径 | 二进制 |
| --- | --- | ---: |
| `L` = 基线（父提交 `195418f`） | `RwLock::read()` | 12 582 352 B，sha256 `736430a5…` |
| `S` = 本改动 | `ArcSwap::load()`（无锁） | 12 588 696 B，sha256 `4cd457d9…` |

（不引用 `S` 的提交哈希：reword/rebase 会让它变，而二进制 sha256 才是身份。）

目录后端 sqlite、`XLITE_CATALOG_RELOAD_SECS=5`、backlog 65535。**3 轮同窗口交错**，
第 3 轮**反序**（先 `S` 后 `L`）以抵消位置效应。

> ⚠️ **本轮没有走到被改的那条路径（读代码即可确认）**：`reload()` 在路由内容不变时提前
> `return`（冻结的 sqlite 目录下每个字段都稳定，channels 还带显式 `ORDER BY`），所以
> 120s 窗口里 `store()` / 写锁**一次都没执行** —— 这份 **CPU 零结果**（以及下面那个未达门槛的
> p99 −7.7% 暗示）只证明**读路径**没有可测成本，**不构成对「写者阻塞读者」这个停顿的量化证据**。要量它必须制造一次真实换快照
> （窗口间改路由再 import），见 [`scripts/loadtest/e2e_reload_swap.sh`](../../scripts/loadtest/e2e_reload_swap.sh)。
> 因此立项口径只能是结构性的：**读者不再被写者阻塞**（`RwLock` 下写者持锁期间读请求要等它，
> `ArcSwap` 下读者继续用旧 `Arc`），而不是"我们测到了停顿"。

**为什么不改成零新依赖的 `mem::replace`**：那把旧快照的析构挪出临界区，但**写者仍要持写锁
完成换指针**，读者依旧会在那一刻等待 —— 与本节要主张的结构性性质不符。`arc-swap` 本来就是
传递依赖（`redis` 带进来，见 `Cargo.lock`），新增的只是一条依赖边。

**工件可复跑**：[`scripts/loadtest/ab_configs.sh`](../../scripts/loadtest/ab_configs.sh)。
第 2、3 轮由它跑出，**第 1 轮用的是同机 inline 脚本**。并且当时的 `ab_configs.sh` 有一个
**已修的缺陷**：`CONFIGS` 的短键 `TWT` 被原样当 env 传下去（网关读的是 `TOKIO_WORKER_THREADS`）
⇒ 那两轮实际用的是**默认线程数**。在 128 核机上默认值恰为 128、与 `TWT=128` 同值，
所以结论不受影响；但**那条复现命令当时并未真的设置线程数**（同类问题见 §13.6）。
现在 `map_cfg_key` 会显式映射、未知键非零退出，并把生效 env 写进 `progress.log`。

1. **它是单样本极值** —— ≈16.6k 个请求里取 1 个最大值，由单个最坏请求支配，天然比中位/分位易被

   一次 GC/调度/内核抖动改写。
2. **该指标极端值有 ±250ms 量级伪影** —— 同族统计里 `min` 常见 −30 ~ −290ms（负值意味着 k6 的

   **同一个伪影既能压低 `min` 也能顶高 `max`**，而 `L` 的 84/247/109ms 正在这个量级 ——
   **其中多少是真停顿、多少是伪影，本设计分不开。**
3. **与上一窗口不一致** —— ab4 那轮 HEAD **也是 `RwLock`**，其 `min/max` 却是 (−32.4, 63.7) 这种紧的；
   乱跳的 (−282.9, 308.7) 反而是 `A0`(0.2.0)。**同一份 `RwLock` 代码在两个窗口给出不同极值形态**
   ⇒ 极值受窗口/环境支配的程度高于受代码支配。

**（3）机制（读代码即可确认，不依赖上面的统计）**

`RwLock` 下 `reload()` 的 `*guard = next` 会**在持写锁时析构旧 `Snapshot`**，期间**所有读锁请求被挡住**。
这是**只在路由内容变化时才取、且一旦取就落在异步热路径上的写锁**（reload 循环每 5s 只做一次读比较，内容不变就早退）—— 代码上确凿，不需要压测成立。

`ArcSwap` 的读不被写者阻塞，所以这一类停顿**从结构上不可能发生**（不是"概率变小"，是不存在）。

顺带修掉一个旧行为：`model_names_for` 原先在锁中毒时静默返回空列表；`ArcSwap` 没有中毒概念。

**（4）结论：立项理由 = 结构性缺陷修复，不是性能**

| 维度 | 结论 | 证据 |
| --- | --- | --- |
| **热路径上的写者阻塞读者** | ✅ **从结构上消除**（写者不再阻塞读者） | **读代码**，不需要统计 |
| CPU / 吞吐 | ❌ **零收益**（原假设"锁争用是 128 线程 CPU 浪费主因"**已证伪**） | 3/3 重叠，均值差 0.15% |
| p50 / p90 / p95 | 无变化 | 3/3 重叠 |
| p99 | ⚠️ −7.7%，**单窗口，未达 §9.1 门槛** | 只能说暗示 |

⇒ **发布口径必须是「去掉异步热路径上会在 reload 时阻塞请求的写锁」，不是"性能优化"。**
`max −74%` 这个数字**不得**写进任何对外材料。

**（5）代价（一并记录）**

1. 新增直接依赖 `arc-swap`（此前已是传递依赖 1.9.2），二进制 **+6 344 B**。
2. **旧快照的释放时机变了**：从「持写锁内析构」变为「最后一个 guard 释放时由某个请求线程 drop」
   —— 回收被推迟且落在不确定线程上。**这是本改动唯一的真实回归风险点，review 时应明确讨论。**
3. 读路径由「取锁→读→放锁」变为「原子读 + 引用计数」；理论更省，但实测 CPU 无差
   ⇒ 反证取锁开销本来就不是瓶颈。

**（6）若要把它做成可量化的性能结论，下一步该做什么**

不要用 `max`。改用**分布统计量**：向 k6 要 `p(99.9)` / `p(99.99)`，或直接**数超过阈值的请求条数**
（<50 / 50–100 / 100–200 / >200ms 各多少）——后者把"最坏那一个请求有多坏"换成
"**有多少个请求被尖刺打到**"，正好能验证"路由变化时取写锁"这个机制预测（频率取决于路由变化次数，不是固定 5s），
且必须**再换一个窗口复现**。本轮未做。

## 13. 把链路从路径上拿掉之后：瓶颈是 **mock 农场**，不是网关

### 13.4 结论

1. **瓶颈是 mock 农场，不是网关。** 农场要 **34–38 核/千请求/秒**，是网关（~7）的**约 5 倍**；
   16000 档它一个人吃 **72 核**（全机 128），网关只要 9.45。此前只是推断的「10 GbE 之后农场先绑死」，
   现在有数了。
   ⚠️ **这条后来被 §14 大幅修正**：这里的绝对数含约七成**台架自身的开销**（batch=1 时每 chunk
   一次 wakeup/syscall）。**同拓扑 + 同档位 + 同喂法**唯一可直接对照的是 B@8000：农场
   **30.9 → 9.54**、网关 **6.2 → 3.54** ⇒ 比分 **4.98 → 2.69**。农场**仍然是**两头里更大的
   那个（相对结论保留），而且**台架不再是天花板**（31000 VU 跑完、fail 0.00%）。
   **`C` 拓扑没有 batch=10 的复测，不要引用具体数字**（见上面 §13.3 的注）。
2. **换掉网卡瓶颈 ≠ 能测到网关的天花板**，只是把瓶颈换成了台架的 CPU。
   ⚠️ **§14 表明这台架 CPU 是可调的**（`batch=10` 让它降 71%）⇒ 换掉之后**能**测到更高档位：
   31000 VU / 4732 qps 跑完且 fail 0.00%。
3. **网关在 4000→16000 VU 全程平在 6.8–7.2 核**，同期 dur p50 从 5.86s 涨到 9.01s、p99 到 1m18s、
   max 2m23s，而 **fail 始终 0.00%** —— 它只是在排队等链路/农场，**且从不拒连**（符合设计承诺）。
4. **每千请求/秒的核数随负载单调下降**（网关 11.7 → 7.4 → 6.9）：低载时固定开销占大头，
   满载时 xlite 很便宜（1236 req/s 只吃 7.66 核）。
5. **把 k6 挪到另一台机（C）反而让 1 GbE 重新咬住**：8000 档起 dur p50 5.89s → 6.48s、p99 → 14.17s，
   qps 1236 → 917。**"把 mock 搬到网关同机"只把链路负载减半，没有消掉它。**

**外推**：网关 ~6.9 核/千请求/秒 ⇒ 128 核大约能撑 **18,000 req/s**；而那时农场需要 **~630 核**。
**要扩的是农场** —— 它的单位成本很高：**同一档位**内算 `农场核数 ÷ (qps × 502 chunk/请求)`：

| 档位 | 农场核数 | qps | ⇒ µs/chunk |
| --- | ---: | ---: | ---: |
| B@4000 | 21.811 | 621.32 | 69.9 |
| B@8000 | 38.196 | 1236.23 | **61.5** |
| C@8000 | 32.394 | 916.84 | 70.4 |
| C@16000 | 33.570 | 990.12 | 67.5 |

⇒ 区间约 **61–70 µs/chunk**。大头是每次 chunk 的 wakeup syscall + 定时器。
一个 batched-write 的 mock（一次 write 发多个 chunk）是这台架子上收益最高的一处改动。

> 这个数被算错过**两次**，记在这里以免再犯：最初写 68 µs —— 它**本来就在区间内，是对的**；
> 评审说应改成 117 µs，我**照抄了没重算**，而 117 µs 是把 B@16000 的核数（72.4）除以
> B@8000 的 qps（1236.2）—— **跨档混算**。教训：别人给的数字也要自己算一遍，
> 尤其当它"刚好支持我要的结论"时。

### 13.6 本轮踩到的台架坑（部分是 inline 脚本踩的，已分别标注是否固化）

**0a（本轮最贵的一个）：网关的 fd 上限 `nofile` —— 会被静默卡住吞吐，且所有常规指标都正常。**

  **已固化**：`ulimit -n 1048576` + 记录网关 `Max open files` + 低于 65536 硬退出
  （`ab_topology.sh`；`ab_configs.sh` 的远端助手同样断言）。

  网关由 harness **直接拉起**，因此继承 shell 的 `nofile`，而 ssh 非交互 shell 默认只有 **1024**。
  表现极具欺骗性：`iteration_duration`、scenario、`vus_max=4000`、`fail=0.00%` **全部正常**，
  但吞吐只有 1/4 —— 实测 4000 VU：

  | 网关 nofile | 网关 fd 数 | 实际承载流 | qps |
  | ---: | ---: | ---: | ---: |
  | **1024**（继承默认） | ~1000（封顶） | ~865 | **147** |
  | 1048576 | 4039 | ~3640 | **621** |

  ⚠️ **后续更正（2026-09-25 晚）：这张表与 §12.3 的「backlog 悬崖」是**同一个机制**，
  不是两件事。** 当时两边各自只看到一半。把 `nofile` 与 `backlog` 摆成 2×2
  （4000 VU / `batch=1` / 单臂 `A1`(backlog 128) 与 `D`(65535)，`nofile` **实测**来自
  `/proc/<pid>/limits`）：

  | 网关 `nofile` | `backlog` | fail | qps | 对应旧记录 |
  | ---: | ---: | ---: | ---: | --- |
  | **1024** | **128** | **34.49%** | 225.3 | §12.3 的 `A0`/`A1`（34.63% / 224.3） |
  | **1024** | **65535** | **0.00%** | **147.6** | §12.3 的 `D`/`A2`（0.00% / 146.3）= 本表第 1 行 |
  | 1048576 | **128** | **0.00%** | 620.6 | 本轮新增 |
  | 1048576 | 65535 | 0.00% | 621.2 | 本表第 2 行 |

  **四格把两处旧记录逐项复现**（34.49↔34.63、147.6↔147、621.2↔621），于是机制清楚：

  1. **根因是 `nofile`**：1024 把并发流封在 ~865，吞吐就上不去（~147–225 qps vs ~621）。
  2. **`backlog` 只决定这个封顶**以什么形式**暴露**：128 时接受队列溢出 ⇒ 连接被**拒**（34.49% 失败，
     且 qps 略高——被拒的连接腾位置快）；65535 时连接**排队**而不是被拒（0.00% 失败，但吞吐仍是 147.6）。
  3. **`nofile` 够了以后，`backlog=128` 是无害的**：0.00% 失败、620.6 qps —— 同机与 split 两个拓扑、
     `batch=1` 与 `batch=10` 都测过（§14.6 那一批也全是 0.00%）。

  ⇒ **部署上两个旋钮要**一起**上，而且因果方向是「先 `nofile`，后 `backlog`」**：
  `nofile` 决定能不能扛住，`backlog` 决定扛不住时是**报错**还是**变慢**。只调 `backlog` 会得到
  「不报错但只有 1/4 吞吐」这种更难察觉的形态；只调 `nofile` 则会在 fd 刚好耗尽时偶发拒绝。

  定位方式是**决定性 A/B**：拿旧的 inline 脚本（有 `ulimit -n`）**重跑**同一档，得到
  90 609 req / gw 7.522 / farm 22.111 —— 与 §13.2 记录的 90 622 / 7.472 / 21.811 同量级
  （差 13 个请求、cores 差 <1%，都在 run-to-run 抖动内），而新脚本只有 23,594 req。
  差异就此锁定在脚本，不在环境。
  ⚠️ **不要再把 `ulimit -n` 当"死行"删掉**：对 k6（在容器里）确实无关，**对网关是要命的**。
  现在脚本恢复 `ulimit -n 1048576`，并把网关的 `Max open files` 打进 `progress.log`；
  **低于 65536 直接非零退出**（把静默封顶变成硬失败）。

  ⚠️ **这条也影响到更早的数据 —— 已经复测，结论不变**：§12.1 / §12.2 / §12.6 的网关是用
  `gwctl*.sh` 起的，而那份脚本**没有** `ulimit -n` ⇒ 那些网关确实跑在 **1024** 下。
  **复测结果（§12.1 表已更新）**：绝对核数从 2.400/2.353/2.213/1.430 升到
  **2.670/2.607/2.449/1.579**（+11%），qps 从 138.7 升到 154.7 —— 而
  **归一的「核/千流」几乎不动**（2.93/2.87/2.70/1.74 → 2.93/2.86/2.69/1.73），
  因为封顶同时压低了分子与分母。所以 §12 的**臂间比较与归一结论全部成立**，
  **只有绝对核数要按复测值读**。§13 的数据不受影响（inline 脚本一直带 `ulimit`）。

  ⚠️ **「+11% 归因于 `nofile`」这个结论单独查过一遍（因为复测同时动了两个变量）**：
  首测与复测之间**不止 `nofile` 变了** —— 首测那份日志的 `checks/http_reqs` 是 **2.00**
  （`KEEP_SAMPLE=1`，全量解析），复测那份是 **1.10**（0.1）。**两个变量一起动，就不能归因。**
  按 2×2 补齐（全部 1000 VU 平推 120s，单臂 `A2`，`TWT` 用默认）：

  | `KEEP_SAMPLE` | 网关 nofile | qps | 网关 cores | 出处 |
  | ---: | ---: | ---: | ---: | --- |
  | 1 | **1024** | 138.69–138.81 | 2.400 | `~/labtest/b2`（§12.1 首测） |
  | 1 | **1048576** | **154.29 / 154.32** | 2.638 / 2.681 | **本轮补测**（`kbs-s1_a` / `kbs-s1_b`，同窗口交错） |

  | 0.1 | **1048576** | **154.59 / 154.63** | 2.675 / 2.660 | **本轮补测**（`kbs-s01_a` / `kbs-s01_b`） |
  | 0.1 | 1048576 | 154.67–154.80 | 2.670 | `~/labtest/ab-v12`（§12.1 复测） |

  **⇒ `nofile` 是全部原因，`KEEP_SAMPLE` 在 1000 VU 下零效应**：同窗口交错的
  `SAMPLE=1` vs `0.1` 是 **154.32/154.29 vs 154.63/154.59 qps（差 0.2%）**、cores 完全重叠
  （2.638–2.681 vs 2.660–2.675），远低于本台架 2% 门槛；两档的客户端占用都是
  **91%（实测 154.6 ÷ 理论 170）、每迭代空档 0.0s** ⇒ **都没碰到 k6 的墙**。
  这解释得通：k6 全量解析的上限约 **315 qps 且与 VU 数无关**，1000 VU 只要 ~155 qps
  （墙的一半），4000 VU 才要 ~600 qps（墙的两倍）。**所以 `KEEP_SAMPLE` 在高载是决定性变量、
  在 1000 VU 不是** —— 但**两个变量都必须显式传**（§13.6 第 1 条）。

  **顺带把 nofile=1024 那一格的机理说准**：`nofile` 封的是**同时可开的连接数**
  （实测 ~1000 就顶住），于是在途流被封到 ~865、请求速率按 Little 定律
  （`qps = 在途流 ÷ dur`）同比例下降，CPU 又随请求速率下降 —— **分子分母一起降 11%**，
  所以归一值（核/千流）几乎不动。这也正是它隐蔽的原因：`vus_max`、`iteration_duration`、
  `fail=0.00%` 全部正常，只有**绝对**吞吐与**绝对** CPU 低了 11%。

**0b（本轮最贵的一个之一）：锁的 fd 会被子进程继承 —— `trap` 必须在启动任何子进程之前注册。**

  **已固化**：`trap` 前移 + 两个子进程 `9>&-`（`ab_topology.sh`）；`run_levels.sh` 的 accept
  采样器同样补了 `9>&-`（它的采样窗 390s，不关就是 6.5 分钟僵尸锁）。

  返工第一版把 `trap cleanup EXIT` 放在**启动网关之后**：命中 `die`（例如 nofile 太小）就直接
  `exit`，cleanup 从不执行 ⇒ 留下**占着端口的孤儿网关**，而它继承了 fd 9 ⇒ **台架锁被永久持有**
  （实测：父进程死后，继承 fd 的子进程仍让 `flock -n` 探测 BLOCKED）。这恰好把「不留僵尸锁」
  做成了它的反面。修法：`trap` 提到启网关之前，并给每个后台子进程加 `9>&-`。
  **凡是用 fd 型锁的脚本都要守这两条。**

  ⚠️ **0b-续（本轮又踩一次 ⇒ 当时那份修得不全）：`ab_configs.sh` 当时根本没有 trap。**
  它只在**正常路径**上 `ab_gw.sh stop`，所以 Ctrl-C / kill / 中途 `exit` 一律留下
  **孤儿网关 + k6 容器 + 被占住的台架锁**（`docker run` 客户端与 `$GW` 起的 ssh 子进程都继承了
  fd 9）。这次是从「kill 掉脚本后 `flock -n` 仍然 BLOCKED」反查出来的，症状与上面 0b 一模一样。
  **关键在于「前台子进程会把 trap 推迟到它结束之后」** —— bash 只在当前前台命令结束后才处理
  已到达的信号。实测：前台 `docker run` 期间发 TERM，30s 后脚本仍活着、网关仍在、锁仍被占；
  改成**后台跑 + `wait`**（`wait` 可被信号立即打断）后，TERM 后 **10s 内**脚本退出、容器已删、
  网关已停、**锁已释放**。配套三处：`trap cleanup EXIT` 提到**任何子进程之前**注册；
  k6 容器固定 `--name ab_configs_k6`（`--rm` 只在正常退出时自删）并加 `9>&-`；
  `START_FAILED` 那条路径**不再清 `CUR_PORT`**（`ab_gw.sh` 先起进程再判 nofile，
  清了就漏掉一个占端口的网关）。

  ⚠️ **一处我自己写错的断言，撤回并订正**：原文写「只挂 `EXIT` 不够 —— bash 对**未捕获**的
  SIGINT/SIGTERM 直接终止、**不跑 EXIT trap**」。**这是错的**，实测（`wait` 期间发信号）：

  | 配置 | 信号 | 退出码 | cleanup | 延迟 |
  | --- | --- | ---: | --- | ---: |
  | 只挂 `trap cleanup EXIT` | INT | 129 | **跑了** | 0.01s |
  | 只挂 `trap cleanup EXIT` | TERM | 143 | **跑了** | 0.01s |
  | 另加 `trap 'exit 130' INT` / `'exit 143' TERM` | INT / TERM | 130 / 143 | 跑了 | 0.01s |

  ⇒ 只挂 `EXIT` 就已经覆盖 SIGINT/SIGTERM，那两个 trap **不需要**（已从脚本删掉）。
  教训：**别把「我推断的 bash 语义」当实测写进文档** —— 这条是复评指出后自己写脚本量出来的。

1c. **客户端饱和必须自己判，不能靠"指标看着正常"。**

   **已固化**：`ab_configs.sh` 每档按 `实测 qps ÷ (VUS ÷ dur_p50)` 算客户端占用，
   低于 **60%** 告警并直接给出改喂法的建议。

   **分母必须是服务时间 `http_req_duration`，不能是 `iteration_duration`** ——
   后者**已经包含客户端自己的空档**，拿它算比值恒等于 ~100%，检测器**永远不响**。
   第一版就是这样：4000 VU 下 `dur=5.85s` 而 `iter=12.23s`，用 `iter` 算得 96% 于是漏报，
   真实比值是 `315 ÷ (4000/5.85) = 46%`。改对之后：正例（`SAMPLE=1`）实测
   **320.19 ÷ 683 = 47%**，告警触发；负例（`SAMPLE=0.1`、`KEEP_BODY=false`）都是
   **~604 ÷ 680 = 89%**、每迭代空档 0.0s，不告警。

   > 这条与「`iter − dur` = 客户端每迭代空档」是同一个量的两种用法：**空档 >0 说明 VU 在等 CPU**，
   > 但**空档 =0 不等于没饱和**（闭式负载下 k6 也可能整体推不动），所以判据用比值为准。

   **耗时是 Go duration 字面量，不是"若干秒"** —— 这是个能**让检测器静默失效**的坑。
   k6 打出来的是 Go 的 `Duration.String()`：`37.83µs` / `3.84ms` / `5.89s` / `1m4s` / `1h2m3s`。
   仓内日志里 `http_req_duration` 行上的分钟级 p50（**`1m4s`…`3m5s`**）就有 **15 处**，
   而那些**正是卡住的轮次**。（注意别混指标：`1m0s` / `1m42s` 那些出现在
   `iteration_duration` 行上 —— 我第一次抓这个数时把两个指标一起 grep 了，范围就串了。）
   第一版提取器只做 `sub(/s$/,"")`，于是 `1m4s` 变成 `1m4`、`2.29ms` 变成 `2.29m`；
   收紧成"只收十进制数字"之后这些一律变成空 ⇒ **整块判定被跳过，而且一声不响** ——
   最需要告警的卡住轮反而没有判定。现在提取后统一过 `secs_of()`（严格解析 Go 单位，
   完全消费不掉就返回空）与 `num_of()`（只收十进制）。

   退化的三种情况**处理得不一样，别笼统写成"都会说无法判定"**（实测）：
   `VUS÷dur` 取整为 0 时会打印「无法判定」；**非数字 `qps` 与"没有指标"则是整块跳过、
   一行都不打印**（无 stderr 噪音，也**不产出假告警**）—— 后两者"什么都不说"是对的，
   因为它们的前提根本不成立。

   ⚠️ **顺带一个 awk 的坑：多字节字面量别写进 awk 的字符串比较。**
   macOS 自带的 BWK awk（`awk version 20200816`）**在 UTF-8 locale 下把 `"µs"` 与 `"s"`
   判为相等** —— 实测 `("µs" == "s")` 在 `LC_ALL=en_US.UTF-8` 下是 **1**、`LC_ALL=C` 下是 **0**。
   于是单位判定**两个方向都会错**：

   - `unit == "µs"` 对 `"s"` 判真 ⇒ `5.89s` 走微秒那一支，算成 **5.89e-06**、
     `1m4s` 算成 **60.000004**；
   - `unit == "s"` 对 `"µs"` 判真 ⇒ `37.83µs` 走秒那一支，算成 **37.83s（137 倍）**。

   ⚠️ **只有字符串比较有此问题，正则字面量是好的**：`("37.83µs" ~ /µs$/)` 在两种 locale 下
   都正确。我第一版笔记写成"正则也会被截断"，那是**错的** —— 复评指出后重测才改过来
   （两个症状其实是同一个机制：比较 + UTF-8 locale）。

   修法：**在 bash 里**把微秒号（`$'\xc2\xb5'`）换成 ASCII `u`，awk 只面对 ASCII ——
   行为与 locale、与 awk 实现（BWK / gawk / mawk）都无关。
   凡是要解析 k6 的耗时文本，都要走这条路（别把 `µ` 写进 awk）。

   自检是**离线复现**出来的（不是"看着对"）：10 个真实 Go 写法 + 11 个必须拒绝的垃圾输入
   全过；端到端 6 例 —— `dur=5.89s`→91% 不告警、`dur=5.85s`/4000 VU→46% 告警、
   `dur=1m4s`→**有判定**（375%，不再静默）、`dur=10m0s` 且 VUS=200→**无法判定**、
   `qps=abc/s`→**不产生假告警**、k6 全挂→整块跳过且无 stderr 噪音。

## 14. mock 的 chunk 合批（`batch`）：§13 那个「农场瓶颈」里**约七成是台架自身的开销**

**动机**：§13.4 第 5 条末尾留了一句「一个 batched-write 的 mock 是这台架子上收益最高的一处改动」。
本轮发现**这个能力根本不用写** —— 农场的 Go mock 早就有 `_config?batch=N`（环境变量 `MOCK_BATCH`），
而 `run_levels.sh` 一直**硬编码 `batch=1`**。所以这轮的任务从「改造农场」变成「量这个旋钮」。

### 14.1 `batch` 的语义（实测，不是从源码读的 —— 农场是**无源码的静态二进制**）

仓库里的 `scripts/stream_mock_server.mjs` 是 Node 版 mock，**不是**实验室跑的那个；实验室是
`mock-llm:h2c`（Go、静态、stripped，`/health` 只回 `{"status":"ok"}`），只有二进制与 usage 文本，
**没有源码**。所以语义只能测出来：

| 量 | `batch=1` | `batch=5` | `batch=10` |
| --- | ---: | ---: | ---: |
| 响应**字节数** | 100 734 | **100 734** | **100 734** |
| `data:` 行数（chunk 数） | 502 | **502** | **502** |
| `[DONE]` | 1 | 1 | 1 |
| 流的总时长（20 chunk @10ms） | 200 ms | 178 ms | — |

⇒ `batch=N` **只改 flush 的粒度**（N 个 chunk 一次 write），**不改载荷一个字节**，
总时长也基本不变（`dur p50` 实测 5.86s → 5.77s）。

### 14.2 A/B：4000 VU 同窗口交错，只改 `batch`

| 1（复） | 7.37 | **21.86** | 19.65 | 621.23 | 5.86s | 0.00% | 70.0 |

`batch=1` 那一格两轮复现（farm 22.52 / 21.86，差 3%），所以效应远在噪声之外：

而 **16000 与 31000 这两个档位以前根本跑不完，现在跑得完**（31000 就是客户压测的上限档）。

**⭐ 这是本轮最有用的一条**：§13 的「换网卡后瓶颈变成了台架 CPU」**不是宿命，是一个旋钮**。
31000 VU 全程 **617 231 个请求、fail 0.00%、dur p50 只有 5.93s**，用的核约
`7.39 + 33.61 + 21.71 ≈ 63 / 128` —— 也就是说**到客户的上限档为止，网关还没见到天花板**，
被约住的是 k6 推 VU 的能力（闭式占用 ≈91%，与 §13.6 1c 的判据一致）。

### 14.4 `batch` 的代价：**首字推迟约 `(batch-1) × 21 ms`**

单请求直测（`ttft=500ms`，`interval=10ms`，3 次均值）：

| `batch` | 1 | 2 | 5 | 10 | 20 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 首字（ms） | 529 | 549 | 614 | **722** | 937 |

所以 `batch` **不是免费杠杆**，它和 `KEEP_BODY` 一样是**两套试验的分界线**：

- **对标 / 延迟类实验** → `batch=1`（**客户就是 1**，且 TTFT 是头条指标，差 193ms 就不能比了）；
- **产能 / 天花板类实验** → `batch=10`（台架 CPU 降约 71%，换来能跑 31000 档）。

**已固化**：`ab_topology.sh` 与 `ab_configs.sh` 新增 `MOCK_BATCH`（**默认留空 = 完全不动农场配置**，
保持原行为；给了值就下发**并回读校验**，生效不满就非零退出 —— `_config` 是静默的，
参数名写错不报错，只会把「我以为我设了 batch」变成假结论）；`run_levels.sh` 的 `MOCK_BATCH`
默认 **1**（对标口径不变），三者都写进日志。

### 14.5 这条修正了什么、**没有**修正什么

**修正的：**

1. **§13 的「农场 34–38 核/千请求/秒」是 batch=1 口径**，其中约**七成**是台架每 chunk 一次
   wakeup/syscall 的开销 ⇒ 换 `batch=10` 后是 **7.1–10.8**。§13.3/§13.4 已按此标注。
2. **「61–70 µs/chunk」同理**：`batch=10` 下是 **14–22 µs/chunk**，而且**随负载单调下降**
   （21.5 → 19.0 → 17.0 → 14.2），说明连剩下的那部分里也有固定开销。
3. **农场与网关的倍数变小**（相对结论保留：农场仍是两头里更费的那个）。按**同拓扑同档位**
   各摆一对（B 拓扑）：4000 档 **2.92 → 2.60**（21.811/7.472 → 6.80/2.62）、
   8000 档 **4.98 → 2.69**（38.196/7.664 → 11.99/4.45）。**不要**写成"从 ~5× 缩到 2.6–4.5×" ——
   「~5×」是 B@8000 的单点、「2.6–4.5」是 batch=10 四个档位的带，两侧口径不同（这类错本节
   已经犯过三次，见 §13.3 注）。
4. **能测到的档位上限**：16000 / 31000 以前跑不完，现在可以。

**没有修正的（重要）：**

- **不能把这读成「xlite 很便宜」**。`batch=10` 是**台架口径**，不是产品口径：客户那份 mock（以及
  真实上游按 token 推送的情形）是**每 chunk 一次 flush**，也就是 `batch=1`。
  **产品相关的绝对核数仍然是 batch=1 那一组。**
- **§12 的结论不受影响**，因为 §12 全部在 `batch=1` 下跑的 —— 而 `batch=1` 恰恰是**更贴近真实上游**
  的那一侧，所以那是**保守/代表**的口径，不是被污染的口径。

### 14.6 顺着 §14.5 想到的产品侧假设 —— **已实现并实测，结论是「证伪」**

`batch` 之所以省这么多，看起来是"每 chunk 一次 write/wakeup"在这条链上被放大了三次：
mock 写、**网关读+转发**、k6 读。而 `src/proxy.rs` 的转发确实是**逐帧**的：

```rust
.body(Body::from_stream(with_head(head, body)))   // src/proxy.rs:232
```

于是很自然的假设：**在转发侧加一个合批缓冲**（把"此刻已经就绪"的几帧排空后再写一次，不额外
等上游），应当能把网关在同一上游口径下的 CPU 往 `batch=10` 那侧推，且不牺牲延迟。

**这个改动做了、也测了 —— 对这个载荷没有效果。** 一共**两次独立运行**，条件不同，分别标注：

**运行 A（CPU/qps/延迟）**：split 台架（网关在 101、mock/k6 在 102），单臂**同一个二进制**，
`COAL` = `XLITE_STREAM_COALESCE_BYTES`，**4000 VU × 120s**（`WARMUP=20s`），两轮**反序交错**：

| `COAL` | 网关 cores（轮1 / 轮2） | qps（轮1 / 轮2） | dur p50 | dur p99 |
| ---: | ---: | ---: | ---: | ---: |
| 0（关） | 9.536 / 9.951 | 601.8 / 604.3 | 5.89s / 5.88s | 7.38s / 7.23s |
| 65536 | 9.837 / 9.554 | 603.1 / 600.4 | 5.88s / 5.89s | 7.38s / 7.47s |

两轮各自有明显的**位置效应**（每轮第一个跑的都更低：轮1 差 0.301 核、轮2 差 0.397 核，即 **3–4%**），
反序之后抵消：均值 **9.74 vs 9.70 = −0.5%**。⇒ 只能说**没测到 ≳3% 的效应**（这个下限由上面那
3–4% 的位置效应决定）——「这条杠杆不存在」的依据是下面的**机制**，不是这两轮的 CPU 数。
延迟侧两档**没有分离**（dur p50 只差 0.01s；p99 两臂各自 7.23–7.38 与 7.38–7.47，在 7.38 相接）。

#### 为什么没有效果（机制，两面都测了）

1. **低载（200 VU，`strace -c`）**：网关 **502.1 次 `writev`/请求** —— 确实一个 chunk 一次写。
   但那种情形下**没有东西可以合并**：mock 按 `token_interval=10 ms` 逐 chunk flush，等第一个
   frame 到达时下一个还要 ~10 ms 才来，`now_or_never` 永远取不到第二帧。（别把这个 10 ms 与
   §14.4 那个 ~21 ms/单位混起来：后者是**首字随 batch 的位移**，不是帧间距。）要合并就必须**等**，
   那就是拿延迟换系统调用 —— 与本改动的第一条不变式（不等待）直接冲突。
2. **高载（4000 VU，`/proc/<pid>/io` 的 `syscw`，零扰动）**：**运行 B** —— 与运行 A 不是同一次：
   **4000 VU × 60s（`WARMUP=10s`）、约 45 000 个请求**，四个格子（0/65536/65536/0）。
   （k6 打印的 `~594 qps` 是按**整段约 76s** 摊的 —— 10s WARMUP + 60s 稳态 + 排空；
   45 075 ÷ 594.25 = 75.9s ✓。所以它比运行 A 稳态那 601–604 qps 低，两者**分母不同**，
   不要直接比。下面算"每请求写次数"用的是**请求总数**，与分母无关。）
   网关**本来就只有 ~266 次写/请求**（COAL=0：266.2 / 264.4）—— 因为高载下它不可能及时 poll
   每条连接，一次读常常带回 ~2 个 chunk。打开合批后是 **257.6 / 259.5（−2.5%）**。
   ⚠️ 这个 −2.5% 是**运行 B** 的数，与运行 A 的 −0.5% CPU 不是同一个窗口，只能说**方向一致、
   量级都很小**，不能当成同一次测量的两个侧面。

⇒ **`batch=1 → 10` 省下来的那 65% 里，网关那一份基本不是"它自己写太多"，而是"上游写得少、于是它
每次读到的更多"** —— 合批本身确实能让网关少写一点（运行 B 的 −2.5%），但那是**零头**，不是那 65%。
在**测过的这两个负载点上**，网关**无法在不等待的前提下**把 502 次写变成 52 次 ⇒
该改动没有进主干（分支 `perf/stream-coalesce` 只留下本节这段记录）。
**这是限定范围的结论**：只测了 200 VU 单流与 4000 VU 聚合两个点，**没有排除**"多连接扇出、
别的请求的帧恰好同时就绪"这种交错 —— 那种情形下网关侧是否还有合并空间，本轮没测。

> 口径说明：`/proc/<pid>/io` 的 `syscr` 在**空载**（间隔 2s 两次读数）与**满载**（200 VU，间隔 5s
> 两次读数）下都**停在 57**，而**同一个文件**的 `syscw` 从 17 涨到千万 —— 按文档 `/proc/io` 是记
> read 族系统调用的，所以这个结果我**没有**查清（我先前猜"这条路径用的读不在 `syscr` 口径内"，
> 但那与文档不符，只能算未解）。
> 所以上面**只引用写侧**；低载那个 502.1 是 `strace -c` 数的。**`strace` 只用于低载**：
> 4000 VU 下即使按本节的 ~266 次写/请求 × ~601 qps 算也有 **~1.6×10⁵ 次写/秒**，`strace` 会把
> 被测进程压垮 —— 那一档的调用次数只能从 `/proc/io` 取。
> 另外，写侧的 266/258 也只有 `syscw` **这一个来源**，没有第二把尺子交叉验证过。

#### 这条"证伪"本身的价值

- 它把 §14.5 之后**最像"下一个大杠杆"的想法**提前掐掉了：不然它会以"§14.6 说值得做"的形式留在
  文档里，下一个人（或下一轮的我）会照着去实现一遍。
- 它把 §13/§14 的结论收紧成一句可操作的：**在测过的这两个负载点上**，要减少整条链的系统调用，
  位置在"上游怎么吐"，不在网关怎么转 —— 网关侧的合并要么没有可合并的（低载：帧间隔 10 ms），
  要么上游早就替你合并了（高载：一次读带回 ~2 个 chunk）。
  （限定的范围与理由见上面结论段末尾那句。）
- 顺带留下一条可复用的测量口径：**`syscw` 数"每请求写系统调用"零扰动、可跑满负载**，
  比 `strace` 高载可用（见上面那条 `syscr` 的保留意见）。
