## 4. 压测宿主证据（XG 侧读数的噪声上界）

11:17:42 `top`（B_45000 起步段）：32 核虚机，`load 51.7/32.7/32.1`，`63.7us + 9.0ni + 8.7sy + 5.2si + 1.3hi + 4.1st`，idle 17.2%；**k6 806%（8 核，RES 26.5G）与 24 个 mock-llm（合计 ≈15.6 核）同宿主**。推论：

1. 30k 档 qps 低谷（935）与 15k/45k/55k 的 ±15% 摆动是**宿主噪声带**，不是容量曲线；该带宽内两侧差异不下结论；
2. k6 被挤会抬高 XG 侧实测 ttft（k6 侧调度延迟计入 waiting）——**XG 的 ttft p50（827~1136ms）是上界读数**；干净 rig 历史对照（0927-vs-0924 文档：XG p50 555~637ms，快 New API 100~150ms）才是该列的公平口径；
3. 每 VU 周期拆解（55k 档）：周期 50.5s 中 HTTP 仅 9.8s，**其余 ~41s 在 k6 非 HTTP 段**——"55k VU" 名义值的大头是压测端等待室，真实并发见 §3。

## 5. 结论

1. **吞吐与真实并发**：XG 单节点多送 37%~42% 请求、承载 2 倍在途流；New API 的 qps 从 15k VU 起钉死在 ~780（网关自限：Go transport 排队 + 单连接窗口），加 VU 不加吞吐。
2. **过载形态**：New API 在 45k+ 的 dur 呈双峰（p50 仍 6.5s 但 p90 34~41s）——放行流全速、排队流涓滴，**排队语义泄漏进 duration**；XG 单峰公平稀释（全员 9.8s p50 / 18s p90）。New API 的 dur p50 更好看是"少跑 40% 的流"换的。
3. **TTFT**：p99 同量级（55k：6.3 vs 5.8s，XG 略优）；p50 本轮 NewAPI 更低（~770 vs ~1140ms）但受 §4-2 污染，不作数。
4. **fail 双零无区分度**：本 rig 农场每口 ≤449 流（舒适区内），两侧都没把下游压到——fail 列的对标价值在 D 组（长流）。
5. **New API"55k VU 0.00%"仍是脱水口径**：真实在途 ~5.0k（利用率 9%），与 0927 报告"60k VU 真实在途 8237、qps 钉 870"同款形态。对标表必须配真实并发列（本表 §3）。
6. **带宽模型结案**：XG 峰值 118 MB/s ≈ 1GbE 实用上限，与 `v88-rig.md` §2 的 112MB/s 账一致；此前 cpu-affinity 文档的 193 MB/s 来自另一台 press NIC，两数不矛盾但易混——已在本文记录，建议 v88-rig 加一行 rig 标注。

## 6. 披露与未结事项

- New API 侧 batch 口径未回读（v88-dual 早于 env.txt 纪律）；两侧 k6.js 版本不同（指标名 `ttft_ms` vs progress 摘要行），p99 口径均为 k6 summary 百分位。
- **XG 12:03 起的全 20 档 B 组**（`20260928T040350Z`）跑完后补低载段（1000~10000）对照——低载段 press 不饱和，ttft p50 才可比。
- `gw_oh` 列口径未确认（本轮 p99 29s vs ttft p99 5.8s 不自洽），归因前列不动用。
- 闸门实验（`XLITE_UPSTREAM_STREAM_CAP`，PR #46）在 B 组不咬合（在途 449/口 < 闸门 1000），**实验场移到 D 组**；前置条件：压测宿主隔离（农场搬离或 cpuset），否则 A/B 被宿主噪声淹没。
