## 1. 结论摘要

1. **尾部延迟 XG 全面领先**：B 组 p99 差 3.4–6.4 倍；D 组差 40–65 倍。多数档位上 XG 的 p99 低于 New API 的 p90。
2. **XG 的实测在飞流到顶更早、更高**：11000 VU 时 XG 已有 **8431**，New API 只有 **2434**（两侧的那个数都受 §7.2 的客户端空档影响）。
3. **名义 VU 与真实在飞流是两件事（两侧都成立）**：New API 名义 60000 VU 时 `qps × dur p50` 只有 **8237**（利用率 14%），XG 在 11000 VU 已有 **8431**（77%）。**但**：这个比值里有一大截是 **k6 客户端自己的开销**（每圈 20–30 s 花在解析 body / GC 上，不是花在请求里），而两轮用的不是同一份喂法，所以它**不能读成"New API 的并发上限是 6000–8000"**——详见 §7.1 的自洽性审计与客户端空档分析。
4. **失败率这一列 XG 吃亏**：XG 在 B 组 44000 VU 之后升到 1.0–2.7%，New API 全程 ≤0.06%。拆开看（见 §6）主因是 **RST 与 502/503**，而 New API 那侧基本没有 RST——所以这是**两侧路径/部署的差别**，不是“快失败 vs 死等”的语义差；但按“连续两档 `fail>1%` 停测”的旧规则，先出局的是 XG。
5. **XG 本轮可信上限约 44000 VU**（45000 之后相邻档自相矛盾），不是 55000。

## 7. 数据边界（引用时必须带上的限定）

1. **每档 n=1，无重复，单窗口**。差异 <20% 不下结论。New API 的 `B_11000`（qps 354）与 XG 的 `B_46000/48000/50000/51000/53000`（qps 374–657）都是塌陷中途的异常点，不是稳态值。
2. **降级重试档不可混算**：XG `B_45000/49000/52000/54000/55000`（0.1 采样，checks 比 1.01）、D 组全部 6 档（0.05 采样，1.05）；其余档为 0.5（1.50）。
3. **New API D 组是两次运行**（首轮 1000–17000 触停，续跑 18000–50000），两段尾部分位量级不一致，不可拼接成一条曲线。
4. **两侧 k6 脚本版本不同**：XG 侧带 `CHUNK_MAX=64` 有界采样，New API 侧无该参数，故两侧的采样与内存行为不可假定一致。
5. **XG 本轮档位覆盖不全**：无低载段（1000–10000），D 组只有 6 档。健康负载下（1000–4000 VU）的首字对比见 [`loadtest-xg-vs-newapi-dual-2026-09.md`](loadtest-xg-vs-newapi-dual-2026-09.md)（0926 轮）。
6. **"在途"是导出量**，由 `qps × dur p50` 得出，未直接采连接数；两侧都没有同时的 ESTAB 采样可交叉验证。

### 7.1 自洽性审计：哪些档的"在途"能用，哪些不能用

对每一档算一个**自洽比**：

```
自洽比 = (VU × 整轮时长 / 总迭代数) ÷ (日志里的 iteration_duration 平均值)
```

干净的闭环应 ≈ **1.0**（分母是「每个 VU 一圈该有多长」，分子是「实测每圈多长」）。大于 1 说明整轮时长里有大量时间 VU 数不在目标值（爬坡 + 收尾拖长），或客户端自身失真 —— **这些档的 VU 与在途不能互相换算**。

| 组 | New API 自洽比 | XG 自洽比 |
| --- | --- | --- |
| B | 1.06–1.11（**11000 档 2.72**） | **1.27–2.22**（50000 档 1.12） |
| E | 1.05–1.07 | 1.05–1.11 |
| D | 1.07–1.09；**8000/15000 档 1.67** | 1.23–1.40 |

⇒ 可用：**New API 的 E 组全部、B 组大部分（除 11000）、D 组低载**；**XG 的 E 组全部**。
⇒ 不可用：**XG 的 B 组 15000 以上**（收尾拖了 1–6 分钟）、**New API 的 `B_11000`**（就是 qps 塌到 354 那一档）、两侧 D 组的中高载。

### 7.2 客户端空档：为什么"利用率"那一列读的是压测端

E 组 31000 VU 这一档**两侧都自洽**（1.06 / 1.11），可以放心对比：

| | VU | `dur p50` | `iter` 平均 | **VU 停在请求里的比例** | 测得在途 | 自洽比 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| New API | 31000 | 5.87 s | 27.75 s | **21%** | 6189 | 1.06 |
| XG | 31000 | 6.42 s | 12.68 s | **51%** | 14114 | 1.11 |

`在途 = VU × dur/iter`，而 `dur/iter` 被 k6 的客户端空档支配：New API 那边每个 VU 每圈有 **22 s** 花在 k6 自己身上（全量解析 body + 保 body 的内存/GC 压力），XG 那边是 6.3 s。

所以：

- 上表 §5 的"利用率"**首先是压测端的利用率**，不是网关的；
- "New API 在飞流只有 6–7 k" 是**那一轮喂法下的观测值**，不能读成**它的并发上限**；
- 要给出可以对外声称的并发上限，只有两条路：(a) 固定其他参数、步进 VU、找 **`dur p50` 开始系统性偏离地板值**的拐点（B 组地板 5.85 s / E 组 5.64 s；这个判据不受 k6 解析开销影响，因为解析只影响 `iter`、不影响 `dur`）；(b) 直接采数（网关侧 h2c 在飞 stream、农场侧每口并发流）。

而且：**两轮打的是同一批 24 口 mock。** 在这个拓扑里，上限由农场（32 核）决定，不由网关决定 —— 所以"谁的并发上限更高"在本台架里问不出网关的差别；能问出的是**谁把农场容量用得更充分、谁的队列化来得更晚**。

---

## 8. 结论

**XG 占优**

1. 尾部延迟：B 组 3.4–6.4 倍，D 组 40–65 倍；XG 的 p99 常低于 New API 的 p90。
2. 单位时间吞吐：B 组 ~1.22 k vs ~0.87 k；E 组 ~2.1 k vs ~1.0 k。
3. 并发扩展性：E 组（两侧自洽）在途 × VU 从 9.8 k 涨到 14.4 k，New API 在 5.9–6.9 k 平台（受该轮喂法限制，非其上限，见 §7.2）。
4. 真实并发到顶更早：11000 VU 时 XG 8431 / New API 2434（同一偏差方向，§7.2）。

**XG 不占优**

1. `fail%`：B 组 44000 VU 之后开始 >1%，New API 全程 ≤0.06%；按停测规则先出局。
2. 45000 VU 之后数据自相矛盾，可信上限 ~44000，不能对外声称 55000。
3. 档位覆盖不全（缺低载、缺 D 组），单凭本轮无法给出完整对标表。

**共同天花板**：在这个台架里，上限由**共享的 24 口 mock 农场**决定，不由网关决定。两侧可测的在飞流都在 **8 k–14 k** 量级，谁也没有真的跑到 3 万条并发流；而每个数的分母（k6 客户端空档）两轮并不相同，所以**不要拿它们直接比大小**。

## 9. 待补

1. 补 XG 的低载档（1000–10000）与完整 D 组，使对标表可闭合。
2. XG 阶梯上限收敛到 44000，45000 以上标"不稳定区"。
3. 报告主推三个指标：**`ttft p99`**、**`qps` 平台**、**`dur` 偏离地板的拐点**；**不要主推 `qps × dur` 那个在途量** —— 它对 k6 客户端空档敏感（§7.2）。
4. `fail%` 一律与 p99、以及**失败分解（非 200 / RST / dial）**成对给出，并在口径里写明 New API 为 600 s 死守、不主动失败。driver 侧已经会每档多打 `reqs=` / `split(t= 502= 503= other=)` / `rst=` / `dial=`，并且**默认不再在 `fail>1%` 处截断**（`STOP_ON_FAIL=0`，跑到 `MAX_VUS`）。
5. 主用 **E 组**做健康负载对标（双方 0 失败），用 **D 组**打尾部（差距最大），B 组讲扩容线性度。
6. **把 k6 从 24 口 mock 所在的机器上挤出来**（现场 `.29` 两者同机）：5 万 VU 下 k6 自己要吃十几到二十核，剩下的核要喂 24 个 mock，它们互相饿死 —— 而 RST 随 VU 线性增长、`dial: i/o timeout` 同时出现，指向的正是资源随并发被慢慢吃光，不是代码 bug。
