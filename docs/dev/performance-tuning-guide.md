# Xlite 高并发与极限负载调优实战指南

> **适用场景**：大规模 LLM 网关压测、百万级并发对话、千级 QPS 吞吐、高低流混合调度、客户现场打擂及生产级高可用部署。  
> **基准来源**：基于 2026-09-24~29 现场全量实测（110 组阶梯、6 大业务场景、50k~60k VU 满载验证）归纳提炼。

---

## 1. 核心架构认知：知己知彼，调优不踩坑

在开始调优前，必须明确以下三个底层铁律：

1. **Xlite 是纯流式透明网关（Rust + Tokio）**：
   - 内存仅几十 MB，CPU 开销微秒级，**网关自身永远不是瓶颈**；
   - 它的性能高低，主要取决于**上游算力（LLM/Mock）**与**下游传输连接池的组织效率**。
2. **VU 闭环机制的“虚假繁荣”陷阱**：
   - 在 k6 等基于固定 VU（如 45k VU）循环压测中：**下游吐字慢/卡顿，客户端发车就慢，后端并发就低，首字看似稳定**；
   - Xlite 吐字极快（29~55ms），客户端发车频率极高（QPS 高出 50%~200%），**会直接将下游 Mock 打入排队区**。
   - **调优目标**：既要保持极限吞吐，又要通过连接治理与流控避免下游被打爆排队。
3. **长流与短流是两套完全不同的物理系统**：
   - **短流（`out ≤ 250`）**：生命周期 5 秒，拼的是**连接池复用率与调度爆发力**；
   - **长流（`out ≥ 3000`）**：单请求霸占连接 60~120 秒，拼的是**连接数容量（Capacity）与防雪崩熔断**。

## 2. 核心参数调优矩阵（一键抄作业）

针对不同业务场景，网关启动环境变量推荐组合如下：

| 参数项 | 默认值 | 黄金推荐值 | 调优场景与核心作用 |
| :--- | :---: | :---: | :--- |
| **`TOKIO_WORKER_THREADS`** | 宿主机 CPU 核数 | **`8`** | **永远不要留空！** 纯 I/O 网关绑 8 核最稳，避免线程过多引发跨核调度与内存争抢。 |
| **`XLITE_UPSTREAM_STREAM_CAP`** | `usize::MAX` (对端通告 250) | **`50`** | **最关键的抗压旋钮！** 强制单条 TCP 连接最大承载 50 个并发流，打散单连接窗口竞争，TTFT 立降 100~200ms。 |
| **`XLITE_UPSTREAM_MAX_CONNS_PER_HOST`** | `32` | **`32 ~ 40`** | 单上游最大长连接数。配合 `STREAM_CAP=50`，单 Mock 承载上限为 `50 × 32 = 1,600` 并发流。 |
| **`XLITE_UPSTREAM_H2C`** | `0` | **`1`** | 内网务必开启 HTTP/2 Cleartext（明文 h2），消除 TLS 握手 CPU 开销与多路复用损耗。 |
| **`XLITE_CATALOG_RELOAD_SECS`** | `5` | **`0` (压测期)**<br>`10` (生产期) | 压测期间设为 `0` 冻结目录快照，完全避免路由查库/Redis 抖动。 |

### 生产标准启动模板（Docker Run）

```bash
docker run -d \
  --name xlite-gateway \
  --network host \
  --restart unless-stopped \
  --ulimit nofile=1048576:1048576 \
  -e TOKIO_WORKER_THREADS=8 \
  -e REDIS_URL=redis://10.56.88.22:6379 \
  -e XLITE_UPSTREAM_H2C=1 \
  -e XLITE_UPSTREAM_MAX_CONNS_PER_HOST=32 \
  -e XLITE_UPSTREAM_STREAM_CAP=50 \
  -e XLITE_CATALOG_RELOAD_SECS=0 \
  -e PORT=8080 \
  xlite:0.5.1
```

## 3. 四层链路端到端协同调优

只调网关不够，必须打通“宿主机内核 → 入口代理 → 网关 → 后端靶机”整条链路：

### 3.1 网关宿主机系统内核调优（Linux Kernel）

在双网关节点（如 `.24` 和 `.26`）执行，解决大并发下的握手丢包与端口耗尽：

```bash
# 1. 调大系统全连接队列与最大连接监听
sysctl -w net.core.somaxconn=65535
sysctl -w net.ipv4.tcp_max_syn_backlog=65535

# 2. 避免空闲连接重新慢启动（让长连接始终处于高吞吐窗口）
sysctl -w net.ipv4.tcp_slow_start_after_idle=0

# 3. 开启 TIME_WAIT 快速复用与调大端口范围
sysctl -w net.ipv4.tcp_tw_reuse=1
sysctl -w net.ipv4.ip_local_port_range="1024 65535"

# 4. 调大系统打开文件句柄上限
sysctl -w fs.file-max=2097152
```

### 3.2 入口负载均衡层（HAProxy）防熔断调优

在极端长流（如 `out=6000`）下，大量长连接滞留极易打满 HAProxy 默认配置，导致客户端出现大量 `503 Service Unavailable`：

```haproxy
global
    # 必须提升全局最大连接数，默认为 50,000，高并发长流极易耗尽
    maxconn 250000

defaults
    mode http
    # 关闭空闲超时，避免长流中途被掐断
    timeout client 10m
    timeout server 10m
    timeout connect 10s
    option http-server-close
    option redispatch

backend xlite_cluster
    balance roundrobin
    # 单节点 maxconn 调大到与网关能力匹配
    server xlite-24 10.56.88.24:8080 maxconn 100000 check
    server xlite-26 10.56.88.26:8080 maxconn 100000 check
```

### 3.3 后端 Mock / 靶机环境隔离（避免“发压端自毁”）

这是现场压测最常见的致命误区：**将 k6 施压机与 24 个 Mock 进程混部在同一台物理机上！**

- **现象**：k6 吃掉 16 核与 80G 内存，导致 24 个 Mock 容器严重欠容，首字延迟直接飙升 200~400ms，产生直连也只有 955ms 的虚高假象。
- **最佳调优法则**：
  1. **物理机独立部署（第一推荐）**：发压端 k6 一台物理机，24 个 Mock 靶机一台独立物理机；
  2. **单机混部时的弹性原则**：若只能单机（如 32 核混部），**不要硬切 16:16 绑核**（会造成 24 个容器抢 16 核的灾难），保持 **全核弹性共享（0-31）** 配合 `STREAM_CAP=50` 是单机混部的最优状态；
  3. **横向扩展靶机**：若压测规模超过 40,000 VU，必须将 24 个 Mock 拆分到两台机器（12 + 12），突破单机 1,500 QPS 的物理上限。

## 4. 业务场景分类调优速查（长流 vs 短流）

根据业务场景的输出 Token 长度，采用分级策略：

### 场景 A：以短文本/搜索/意图识别为主（`out ≤ 250`，如组 A、组 E）
- **特点**：单请求快进快出（~5.5s），吞吐极高（可超 3,000 QPS）。
- **调优策略**：
  - 放宽连接复用：`STREAM_CAP=50 ~ 60`；
  - 调小 Worker 线程：`TOKIO_WORKER_THREADS=8` 足以喂满双千兆网卡；
  - **收益**：轻松跑出单档百万级交付，0% 失败率。

### 场景 B：以大文本/深思报告为主（`out ≥ 3000`，如组 D、组 F）
- **特点**：单流持续 60~120 秒，并发流在网关和代理层长期堆积。
- **调优策略**：
  - 适度收紧单连接流数：`STREAM_CAP=30 ~ 40`，防止单 TCP 链接积压过多长时间未结束的流；
  - 调大最大连接数：`XLITE_UPSTREAM_MAX_CONNS_PER_HOST=64`，给新流提供更多独立连接通道；
  - HAProxy 必须调大 `maxconn` 并开启超时保护。

## 5. 对标实战话术与评测公平性指南

未来若遇到与同行竞品（如 New API 等）同台打擂：

1. **坚持看“全生命周期交付能力”，不被单个虚假 TTFT 误导**：
   - 对方通过内部协程卡顿（400ms 抖动，时长翻倍）强行降低了发车频率，换取空载下的首字延迟；
   - Xlite 在组 A 顶出 **3,355 QPS / 112 万请求**，在组 E 顶出 **1,552 QPS / 70 万请求**，在组 B 顶出 **2.13 倍交付总量**；
   - 证明：**Xlite 交付了翻倍的真业务价值，流式间隔压在 29~55ms，用户体感无卡顿。**
2. **在真实到达率（≤10k VU）下直接比首字**：
   - 拿出我们的 1k~10k 实测数据：Xlite 首字稳定在 **555ms ~ 711ms**，在同等业务流量下**全面快于对手 50ms ~ 460ms**，长尾 p99 更是快对手 **10~40 倍**！
