## 1. 核心结论摘要

1. **≤ 10,000 VU（黄金业务段）：Xlite 首字延迟（TTFT）与吞吐全面碾压 New API**：
   - 在 7k ~ 10k 段，Xlite 的 TTFT p50 稳定压在 **619ms ~ 691ms**（比 New API 的 720ms ~ 738ms 快 **30ms ~ 120ms**）；
   - 10k 时，Xlite 顶出 **1,207.7 QPS** 与 **60.3 万 Token/s** 吞吐量（New API 在 8k~25k 被死死锁死在 780~810 QPS 天花板）。
2. **45,000 VU（超高并发段）：Xlite 展现断层级吞吐量与流式平滑度优势**：
   - **完成请求总量**：Xlite 跑完 **59.2 万个请求**，是 New API（27.7 万个）的 **2.13 倍**；
   - **流式吐字平滑度**：Xlite 吐字抖动（`chunk_int` p99）达 **29 ms**，而 New API 恶化至 **411 ms**（出现严重打嗝卡顿，Xlite 顺滑度领先 14 倍）；
   - **整请求交付耗时**：Xlite p90 仅 **16.23 秒**，而 New API 为 **33.95 秒**（Xlite 快一倍完成全生命周期交付）；
   - **首字延迟 (TTFT p50)**：New API 依靠后续卡顿换来新建请求稀释，保持在 768ms；Xlite 经过 `stream_cap=50` 摊薄后，从初始的 1,016ms 稳步压低至 **931.8ms**（差距收窄至 163ms）。
3. **整机算力物理天花板锁定**：
   - 通过 `farm_ceiling_scan.sh` 实测，32 核机器在 `batch=1` 下的极限产能为 **~48,000 VU / 1,482.8 req/s**（约 1,500 QPS 物理封顶）；
   - 本机算力成本为 **21.6 核 / 千请求/秒**；后续扩容冲更高档位只需按此公式线性增加 Mock 节点。

## 4. 45,000 VU 下 TTFT 差异的深度物理归因

在 45,000 VU 这一档中，表面上看 New API 的 TTFT p50 优于 Xlite（768ms vs 931ms），但结合底层系统状态，原因如下：

1. **k6 虚拟用户循环机制（VU 机制）**：
   k6 采用恒定并发（VU=45000）。虚拟用户在收到前一个请求的完整 500 个 Chunk 之前，不会发起下一个请求。
2. **New API 的“卡顿带来减速”**：
   New API 由于内部协程竞争与缓冲区滞留，`chunk_int` p99 暴增至 411ms，单个请求拖延至 34 秒以上。客户端大量时间在等待后半段接收，导致 5 分钟内仅发出 **27.7 万** 个请求（平均只有 779 QPS 发往 Mock）。下游 Mock 承载的新建连接少，首字较快。
3. **Xlite 的“全速交付带来高压”**：
   Xlite 纯流式透传，`chunk_int` 仅 29ms，单请求 16 秒即可交付。客户端迅速进入下一次迭代，5 分钟内疯狂交付 **59.2 万** 个请求。Mock 农场承受了双倍的新建请求轰炸，导致下游生成首字排队。
4. **`STREAM_CAP=50` 的实测价值**：
   当应用 `stream_cap=50` 强制多开 TCP 连接、将单连接流数限制在 50 以下后，TCP 窗口排队显著减轻，TTFT p50 成功从 1,016ms 压低至 931.8ms，同时保住了 29ms 的流式吐字质量。

## 6. 最终推荐生产与压测部署配置

网关宿主机环境按照如下配置启动，可同时获得最佳 TTFT 与极限高并发稳定性：

```bash
docker run -d \
  --name xlite-gateway \
  --network host \
  --restart unless-stopped \
  --ulimit nofile=1048576:1048576 \
  -e TOKIO_WORKER_THREADS=8 \
  -e REDIS_URL=redis://10.56.88.22:6379 \
  -e XLITE_UPSTREAM_H2C=1 \
  -e XLITE_UPSTREAM_MAX_CONNS_PER_HOST=32 \
  -e XLITE_UPSTREAM_STREAM_CAP=50 \
  -e PORT=8080 \
  xlite:0.5.1
```
