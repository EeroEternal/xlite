## [Unreleased]

- **更正评测数据：网关 `nofile` 被静默封顶**。§12.1 的首测（`TOKIO_WORKER_THREADS` 扫描）里，网关是用不带 `ulimit -n` 的脚本起的、继承了 ssh 非交互 shell 的 **1024**，只承载 ~820 流 / 138.7 req/s。用修好的 harness（会记录网关 `Max open files`、低于 65536 直接非零退出）复测后为 **~911 流 / 154.7 req/s**，绝对核数从 2.400/2.353/2.213/1.430 更正为 **2.670/2.607/2.449/1.579**（+11%）。**结论不变**：128→2 线程仍省 **40.9%** CPU；且**归一的「核/千流」几乎不动**（2.93/2.87/2.70/1.74 → 2.93/2.86/2.69/1.73），因为封顶同时压低了分子与分母。§12.2/§12.6 的对比结论同样成立，仅绝对核数偏低约 11%。**「+11% 归因于 `nofile`」单独验证过**：首测与复测之间**同时**变了 `KEEP_SAMPLE`（首测 1 = checks 比 2.00，复测 0.1 = 1.10），两个变量一起动就不能归因 —— 按 2×2 补齐后（1000 VU、单臂 `A2`、同窗口交错两轮）`SAMPLE=1` 是 **154.32 / 154.29 qps**、`SAMPLE=0.1` 是 **154.59 / 154.63 qps**（差 **0.2%**，cores 完全重叠 2.638–2.681 vs 2.660–2.675），两档客户端占用都是 **91%**（未撞 k6 上限），而 nofile=1024 那格是 **138.7** ⇒ **`nofile` 是全部原因，`KEEP_SAMPLE` 在 1000 VU 下零效应**（它只在撞 k6 解析上限的高载才是决定性变量）。数据见 `docs/dev/loadtest-newapi-controlled-2026-09.md` §13.6 第 0a 条。

- **压测台架：k6 喂法必须显式传，并把「客户端饱和」变成可见**。`scripts/loadtest/ab_configs.sh` 此前写死 `-e KEEP_BODY=true` 却**从不转发 `KEEP_SAMPLE`** ⇒ 喂法由「跑的是哪份 `k6.js`」决定：仓库版默认 **1**（checks 比 2.00，全量解析），客户机上挂的 v3.2-memopt 副本默认 **0.1**（1.10）。日志头写着 `KEEP_BODY=true`、看着就是全量对标喂法，实际跑的是 0.1 —— 4000 VU 下拿到 **601 qps**，而 `iteration_duration`/`vus_max`/`fail=0.00%` **全部正常**，只有 `gw_oh` 悄悄变成 10% 样本。现在 `ab_configs.sh`、`run_levels.sh`、`ab_topology.sh` **三个 harness 都显式传** `KEEP_BODY` 与 `KEEP_SAMPLE`，并打印**生效值**与**那份 `k6.js` 自带的默认值**（两边不一致一眼可见）；文档里原先「对标喂法**不要传** `KEEP_SAMPLE`」的指引（`scripts/loadtest/README.md`、`docs/manual/v88-rig.md` §1.2）已改成「**要显式传 1**」——「不传」等于让文件身份决定喂法，正是这个坑的成因。实测三种喂法的代价（4000 VU，同一网关同一臂）：`KEEP_BODY=true KEEP_SAMPLE=1` → **315.0 / 320.2 qps**（有全量 `gw_oh`，k6 先饱和）、`KEEP_BODY=true KEEP_SAMPLE=0.1` → **603.8 / 604.4 qps**（`gw_oh` 取 10% 样本，仍够出分位）、`KEEP_BODY=false` → **600.3 qps**（无 `gw_oh`）；**全量解析的 ~315 qps 上限与 VU 数无关**，所以 1000 VU（~155 qps）安全、4000 VU（要 ~600 qps）必然撞墙。同时 `ab_configs.sh` 新增**客户端饱和检测**：按 `实测 qps ÷ (VUS ÷ dur_p50)` 判定，低于 **60%** 告警并直接给出改喂法的建议；**分母必须是服务时间 `http_req_duration`** —— 用 `iteration_duration` 会恒等于 ~100%，检测器**永远不响**（第一版正是这个错：4000 VU 下 `dur=5.85s` 而 `iter=12.23s`，用 `iter` 算得 96% 于是漏报，真实比值是 `315 ÷ (4000/5.85) = 46%`）。正负例都验过：`SAMPLE=1` 实测 47% 触发告警，`SAMPLE=0.1` 与 `KEEP_BODY=false` 都是 ~89–91%、每迭代空档 0.0s，不误报。检测器解析 k6 的耗时文本时按 **Go duration 字面量**处理（`37.83µs` / `3.84ms` / `5.89s` / `1m4s`）—— 仓内日志里 `http_req_duration` 行上的分钟级 p50（`1m4s`…`3m5s`）有 15 处，而那些正是**卡住**的轮次；只 `sub(/s$/,"")` 当秒数用会让这些一律解析失败、**整块判定静默跳过**（最该告警的轮反而没判定）。退化情况分三类处理：`VUS÷dur` 取整为 0 时**明说「无法判定」**；非数字 `qps` 与无指标则整块跳过（不打印、无 stderr 噪音，也**不产出假告警**）。附带记录一个 awk 坑：macOS 自带的 BWK awk **在 UTF-8 locale 下把多字节字面量 `"µs"` 与 `"s"` 判为相等**（`("µs"=="s")` 在 `en_US.UTF-8` 下为 1、`LC_ALL=C` 下为 0），于是单位判定两个方向都错 —— `5.89s` 算成 5.89e-06、`37.83µs` 算成 37.83s；**只影响字符串比较，正则字面量是好的**。所以微秒号在 bash 里先换成 ASCII `u`，awk 只面对 ASCII。

- **压测台架：新增同机 loopback 的瓶颈归因 harness `scripts/loadtest/ab_topology.sh`**，并给**三个** harness（`run_levels.sh` / `ab_configs.sh` / `ab_topology.sh`）都加上 `flock` 台架互斥。前者回答「瓶颈落在网关 / mock 农场 / k6 哪一组」，判决指标是**分别采三组进程的 CPU**（`/proc/<pid>/stat`，k6 用 `docker stats` 取真值）；只支持**全同机 loopback** 一种拓扑（k6 + 网关 + 24 mock 都在一台机上，把 1 GbE 从路径上拿掉；脚本不接受 `TOPOLOGY` 之类的开关）；早先草案里的 `split`（k6 跨链路）支路**已删除** —— 它只复现 §13.4 第 5 条（§9 已成立），却要额外背远端锁、远端逐参转发、跨机哈希校验等四处高风险代码。实测结论见 `docs/dev/loadtest-newapi-controlled-2026-09.md` §13：**农场 34–38 核/千请求/秒，是网关（~7）的约 5 倍 —— 瓶颈是农场，不是网关**，网关在 4000→16000 VU 全程平在 6.8–7.2 核且从不拒连。互斥：两个 agent session 共用台架，`flock` 绑在 fd 上，进程退出/崩溃/`kill -9` 均由内核释放，不留僵尸锁（三个 harness 共用 `scripts/loadtest/lib_rig.sh` 的 `lab_lock`）。另外把网关的 `nofile` 纳入护栏：网关由 harness 直接拉起、会继承 ssh 默认的 **1024**，被静默卡住时 scenario/`iteration_duration`/`fail%` 全正常但吞吐只有 1/4（实测 4000 VU：nofile=1024 时 qps **147**，1048576 时 **621**）—— 现在记录网关的 `Max open files`，低于 65536 直接非零退出。

- **压测 rig 的闸门改成「不过就不出报告」，并修掉三处会让它说谎的缺陷**：`report.py` 在闸门不过时**不再写 `meta.json`**（此前是先出表、写文件，只改退出码），指纹不符的档在表里标 **`INVALID`** 且不进对标表、不参与链路预算闸门；`run_levels.sh` 把 `GRACEFUL_STOP` 透传给 k6 **并**作为 `--expect-graceful-stop` 的期望值（此前硬编码 `10m0s`，按文档用 `GRACEFUL_STOP=30s` 跑 A/B 会被误判成「脚本被换过」）；accept 队列采样器不再阻塞命令替换（后台子 shell 未重定向 stdout，会让 k6 在采样窗结束后才开打、`.acceptq` 记的是空载网关、每档白等一个采样窗），没有 `ss` 时记 `unknown` 而**不是 0**（采样器首个有效读数之前也记 `unknown`）；被拒时**删除同目录遗留的旧 `meta.json`**，且删除失败只告警、不改变 0/2/3 退出码契约；`k6` 版本改为 `k6 version` / 镜像自报（此前从运行日志 grep，永远为空）；删掉 xlite 从不发送的 `queue_wait_ms` 死列与不可达的字节回退分支。

- **路由快照改 `ArcSwap`，去掉异步热路径上会阻塞请求的写锁**：`Store` 的快照由 `Arc<std::sync::RwLock<Snapshot>>` 换成 `Arc<ArcSwap<Snapshot>>`，三个读点（`authenticate`/`model_names_for`/`channels_for`）改无锁 `load()`。**立项理由是结构性缺陷修复，不是性能**：`RwLock` 下 `reload()` 的写者在**路由内容变化时**持写锁并在其中析构旧快照（reload 循环每 5s 检查一次、内容相同就提前 return），期间读请求要等它 —— 这是落在异步热路径上的阻塞点（读代码即可确认）；`ArcSwap` 的读不被写者阻塞，这类等待从结构上不可能发生。**实测不支持任何性能主张，而且本轮测量窗口内目录冻结、`store()` 一次都没执行** —— 那份 CPU 零收益（3 轮同窗口交错范围完全重叠，均值差 0.15%）只证明**读路径**没有可测成本，**不构成对写锁停顿的量化证据**；原先"锁争用是 128 线程 CPU 浪费主因"的假设被**证伪**；p99 测得 −7.7% 但只有单窗口、未达 `v88-rig.md` §9.1"换窗口复现"的门槛，只能算暗示；`max` 的差异不可用作证据（单点极值 + 该指标极端值有 ±250ms 伪影 + 与 ab4 窗口不一致）。因果/换代的端到端证据见 `scripts/loadtest/e2e_reload_swap.sh`（同一进程内换路由：旧模型 404 / 新模型 200；并发段期间每 2s 交替 import weight 不同的目录，即在**真的换代窗口内** fail 0.00%）。回归：`reload_swaps_the_snapshot_so_readers_see_the_new_routing`（memory catalog：换代后同一 key 句柄旧路由消失、新路由可见）。代价：新增直接依赖 `arc-swap`（原为传递依赖，`Cargo.lock` 只多一条依赖边），旧快照释放时机由"持写锁内析构"变为"最后一个 guard 释放时 drop"。数据见 `docs/dev/loadtest-newapi-controlled-2026-09.md` §12.6，可复跑 harness 见 `scripts/loadtest/ab_configs.sh`。

- **`GET /health` 带上 `version`**：免鉴权的探活响应从 `{"status":"ok","gateway":"xlite"}` 变为再带一个 `version`（`CARGO_PKG_VERSION`）字段。此前只有要登录的 `GET /api/overview` 才给版本，启动日志之外**无法用一个 curl 确认现场跑的是哪一版**；对标时反复强调要钉 k6 镜像 digest 与脚本 sha256，网关自己却没有可远程核对的指纹。HAProxy `httpchk` 只判状态码，加字段不影响探活。回归：`health_reports_gateway_and_version`。

- **部署参数变更：`TOKIO_WORKER_THREADS` 默认 32 → 8**（`deploy/env.example`、`deploy/docker-compose.yml` 的 `:-32`）。旧值 32、新值 8、理由：裸 `#[tokio::main]` **按核数**起 worker，在 128 核网关机上等于 128 个 —— 实测 1000 VU 下 128 → 8 省 **8.3%** CPU、128 → 2 省 **40.9%**（见 `docs/dev/loadtest-newapi-controlled-2026-09.md` §12.1 复测值）。取 8 而非 2：**8 是唯一在 1000 VU 与 4000 VU 两档都实测过、且都是被测集合里最好的值**；2 在 1000 VU 更优但 4000 VU 未测、且线程过少在高并发下有排队风险。运行时若显式设了环境变量，本次改动不影响（compose 用 `${TOKIO_WORKER_THREADS:-8}`，仍可覆盖）。
- **运维：`TOKIO_WORKER_THREADS` 不要留默认**（实测，见同上 §12）：裸 `#[tokio::main]` 默认按 `nproc` 起 worker。在 128 核的网关机上实测默认值 **白烧约 40.9% CPU 且尾部更差** —— 1000 VU 下 128 → 2 线程为 `2.670 → 1.579` 核，同时 `p90 −17%`、`p95 −45%`、`p99 −51%`、吞吐与失败率不变（代价仅 `p50 +14%`）。**按负载定，别抄常数**：4000 VU 下 128 → 8 线程省 9%（幅度随载荷变小）。同轮实测另两条：`XLITE_UPSTREAM_MAX_CONNS_PER_HOST` 32/64/128 **零效应**（不用调）；**listen backlog 65535 不是延迟优化而是并发上限保障** —— ≤1000 VU 无延迟差别（accept 队列峰值 17/128），但 **4000 VU 下 backlog 128 直接 34.6% 失败、65535 为 0.00%**。

- **可选的上游首字计时头 `XLITE_UPSTREAM_TTFT_HEADER`（默认关）**：置 1 时流式响应带 `x-xlite-upstream-ttft-ms`（发上游请求 → 上游第一个 body 字节的耗时），用来回答「高负载下 TTFT 涨的那一截在上游还是网关」。**默认关**：HTTP 头先于 body 发出，要报上游首字就必须先等那一个字节，对「先发头、后吐字」的上游会把客户端首字推迟到上游首字；关闭时行为与之前一致（只多一层 `stream::iter(None)` 空适配器，字节与顺序不变）。**这个头不进对标表**：New API 不发任何计时头（其二进制里 `x-*-ms` 形态 0 命中），客户原版脚本也不读响应头，该列只能单边填；`queue-wait` 类头**不提供**（无准入闸门，恒 0，是死列）。同时新增 `scripts/loadtest/`（xlite 自己的 rig，读 `x-xlite-*`；默认值按客户对标喂法设：`KEEP_BODY=true` ⇒ 每次迭代全量解析、checks 比 **2.00**，`KEEP_SAMPLE` 默认 **1**，显式传 0.1 才是客户 v3.2-memopt 的采样版 **1.10**，`KEEP_BODY=false` 时仍是 **1.00**）。回归：`with_head_prepends_without_reordering_or_dropping`。

- **受控对照：把客户的 New API 镜像搬到实验台（`docs/dev/loadtest-newapi-controlled-2026-09.md`）**：用客户给的 `new-api:v8-sentinel` 镜像 + 客户自己的 `init-db.sh` 目录配方（Postgres + Redis + `h2c` 通道），在**同一台实验机、同一份 rig（`KEEP_BODY=true` + `-m 45g`，两侧 checks 比均 2.00）、同一批 24 mock、同一天**与 xlite 0.2.0 对跑。结果：**低载（1000 VU）两者 TTFT 无差别**（xlite 501.8ms / New API 504.2ms，mock 自身 500ms），即客户日志里 New API 的 708ms **不是网关开销**；高载段 New API 在「单副本 + 本地 Postgres」下先崩（4000 VU fail 12.4%、10000 VU 99.8%，签名是每请求结算占一条 DB 连接），但客户现场是 2 副本 + HAProxy + 独占 PG，**不可外推**。**后续更正（含一次降级）**：按客户配置（`SQL_MAX_OPEN_CONNS=2000` / PG `max_connections=2000`）时 4000 VU fail 12.4%；把两边放开到 8000/10000 后出现过 **0.57%**，但**同一配置复跑又出现过 12.4% / 12.98%**（波动 20×）—— 所以那一档**不能用来归因**（既不能说"就是 DB 连接数配置"，也不能说"就是 New API 的行为"），要下结论先补 run ledger（每轮记 PG `max_connections` / `SQL_MAX_OPEN_CONNS` / fail%）；能说的只有架构那条：放开连接数后瓶颈上移到 **Postgres CPU**（10000 VU 时 74 核，错误为 `failed to connect to postgres`），因为 New API 每个请求的结算都要与 Postgres 往返一次。同时更正 `v88-rig.md` 对「客户跑的是哪份 k6 脚本」的归属：客户机上被挂载执行的始终是 `/root/loadtest/k6/k6.js`，但那份文件在对标那晚被手改过至少四次，包里两份 `k6.js`（`deploy88/k6.js` 硬编码 `gracefulStop: '10s'`；`loadtest/k6/k6.js` 采样 0.1 → checks 比 1.10，只对上最后一档 E@21000）**都对不上**跑出对标数据的那一版。对标那批（含客户 708ms）的指纹是 checks 比 **2.00** + `gracefulStop: 10m0s` + 有 `gateway_overhead_ms`，判据见 `v88-rig.md` §1.1。

- **h2c 目标预计算**：通道快照带上 `authority` / `path` / `Authorization`，请求路径不再解析上游 URL、不再 `format!("Bearer …")`。
- **Mock-24 与压测环境手册**：实验室 `117.160.123.99:60000/60001`、客户 22/24/26/29 拓扑、k6 组合与 3 万连接对标，见 `docs/manual/lab-loadtest.md`。
- **V88 对标 rig**：`KEEP_BODY=true`、无 think-time、1000 VU 起跳；不 cap / 不提前 200 / 超时 600s 的落地方式见 `docs/manual/v88-rig.md`。
- **压测可冻结目录快照**：`XLITE_CATALOG_RELOAD_SECS=0` 关掉 5 秒 Redis/SQLite 重载；请求路径仍不碰库。HAProxy 探 `/health`。

## [0.3.0] - 2026-09-24

- **热路径零拷贝透传**：`upstream_model` 与请求 `model` 同名（常规情形）时不再 JSON 反序列化/重序列化，原请求字节直接透传（字节透传边界名副其实）；需要改名时才惰性构建 DOM（每请求至多一次）。上游请求体改传 `Bytes`，去掉 h2c `copy_from_slice` 与 reqwest `to_vec` 第三次拷贝。注意：含重复 `model` 键的请求体现在返回 400（原为末键生效）。
- **快照 Arc 化 + 端点预计算**：路由快照里模型/通道改存 `Arc`，每请求排序只克隆指针不克隆 5 个 `String`；通道的 `chat/completions` URL 在快照构建时算好，不在每请求重拼。5 秒重载在路由未变时跳过写锁交换。
- **Key 哈希与 failover 细节**：API key 哈希改手写 hex（免 `format!` fmt 机器）；failover 前的错误体排空封顶 64 KiB，坏上游不再能拖住重试。
- **入站 listen backlog 与 TCP_NODELAY**：监听套接字 backlog 65535（内核按 `net.core.somaxconn` 封顶）。Linux 上 libc `SOMAXCONN` 是 128，默认 `TcpListener::bind` 会在 3 万 VU 爬坡时丢 SYN。每条入站连接打开 `TCP_NODELAY`，10ms SSE 不被 Nagle 合并。（此前误置在 `[Unreleased]`，实际随本版发出：提交 `4876579` 改了 `src/main.rs`。）

## [0.2.0] - 2026-09-24

- **Admin 会话改为无状态签名 Cookie**：`xlite_session` 变为 HMAC-SHA256 签名的 `exp.nonce`（密钥取自 `ADMIN_SESSION_SECRET`，未设则用 `ADMIN_PASSWORD`）。任意网关节点都能独立校验，HAProxy/负载均衡后无需会话粘性，也不再依赖进程内内存；集群各节点设置同一个 `ADMIN_PASSWORD`（或显式 `ADMIN_SESSION_SECRET`）即可共用登录态。
- **示例 YAML 写死压测 Key**：`examples/mock-24*.yaml` 与 `catalog.yaml` 的 `api_keys.loadtest.key` 为 `sk-loadtest`，import 后无需打开 Admin。

## [0.1.0] - 2026-09-24

- **YAML 导入/导出路由目录**：供应商、模型（含通道权重/优先级）、API Key 可用一份 YAML 合并或整表替换。设置页导入导出；命令行 `xlite import file.yaml` / `xlite export`。导出不含用户 API Key 明文；导入未写 `key` 时会生成并把明文返回一次。示例见 `examples/catalog.yaml`、`examples/mock-24.yaml`。
- **配置存储改为 SQLite / 内存 / Redis**：不再使用 PostgreSQL。默认 `DATABASE_URL=sqlite:xlite.db`；压测设 `DATABASE_URL=memory` 走进程内 SQLite；集群设 `REDIS_URL` 后供应商、模型、通道、API Key 写进 Redis（`xlite:catalog`），各节点共享。数据面仍只读内存快照。
- **xlite 初版**：独立仓库的轻量 OpenAI 网关。数据面只做 API Key 鉴权、按权重/优先级选通道、SSE 字节透传；h2c 走原生连接池（对端 `SETTINGS_MAX_CONCURRENT_STREAMS` 满了再拨新连接）。控制面只有供应商、模型与通道、API Key、设置。调度与 New API 相同：同一优先级内按权重随机，首字节前才 failover。
