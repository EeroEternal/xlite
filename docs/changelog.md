- **§8 验收初筛（三轮拉丁交错 × 3 臂）：`TOKIO_WORKER_THREADS=32` 过两道门——XL32 vs XL8 速率 +46%、duration −31%、TTFT 不退化，轮间波动仅 ±0.5%；长流 D/F 形态的对标仍待全量验收**。同喂法同农场同机回环，16k VU、30s 爬坡+300s 稳态（初筛长度，§8.1 的 1800s 全量窗未做），轮间 60s 冷却 + 农场健康检查；New API（`new-api:v8-sentinel`+本地 postgres）24×h2c 渠道直指同一农场、客户同款 4 选项；每轮 preflight=200、`[DONE]` 抽查过。**结果**：XL8 1711/s（±0.4%）、**XL32 2500/s（±0.5%）**、NA 617/s（±0.5%）；TTFT 552/541/12366ms；duration 8.8/6.05/24.0s；失败率 0%/0%/**13.4%**。**判据核算（跑前预注册）**：性能门 XL32 全过（速率 +46.1%、duration −31%、TTFT 亦降、失败 0%）；正确性门 XL 过，**NA 13.4% 失败未过 0% 线**——低载对照（100VU：TTFT 512ms、0% 失败）证明 NA 部署无误，16k 塌陷是其架构在该流形的真实过载（含 503），如实记录；噪声 ±0.5% ≪ 收益，三轮充分。**外推边界（必须披露）**：本实验流形 5.6s/500chunk，而 10-07 的 D/F 是 >60s 长流（逐 chunk 中继与逐请求结算的摊薄完全不同）——**本结果不回答 D/F 差距是否关闭**；按 §8.3 不自动改生产默认值，worker=32 仅作部署建议。另记录 v1 编排的失败：NA 轮后的 XL 轮传输层全败（`status_0_transport`），60s 冷却后消失，成因（疑似临时端口/TIME_WAIT）未证明。详见方案 §8.4。
- **D/F 计划 P3 资源观测（128 核台架，全链路回环）：`TOKIO_WORKER_THREADS=8` 欠配是头号已证杠杆——32 线程完成速率 +44%、排队消失；perf 推翻「应用层自旋」假设**。C0 配置固定、capsweep 同喂法，8k/16k/32k VU 三级采样 + k6→单 mock 直连对照 + perf 双窗：①整机不饱和（~76/128 核），in_flight 1510/addr ≪ 8,000（额度第三次确认不绑定）；②网关 8 个 tokio worker 各 ≈0.99 核封顶且 CPU 不随吞吐变化，perf 判明为内核态每包实工（数据拷贝 5.6%、自旋锁族 ~10%、nft/conntrack ~5%；用户态 Rust 头名仅 `mpsc::Sender::send` 1.8%）——**不是应用层自旋 bug**；③mock 有余量（单 mock 直连对照 4.1 核/72k chunks/s ≫ 农场 2.2 核/32k），k6 非绑定。**线程单因子曲线**（16k VU）：4→965/s、8→1503/s、16→2006/s、**32→2171/s（duration 5.97s=流自然时长，TTFT 528ms）**、64→2094/s 回落——「线程越多越快」不成立，32 为最优点。**建议**：长流高压负载 `TOKIO_WORKER_THREADS=32`（现场现值 8：+44% 速率、duration 8.6s→5.97s）；netfilter 旁路/绑核为次级候选（未做）。**对 D/F**：现场四网关均跑 8；若 10-07 基准同配置，worker 欠配是完成速率差距的头号已证杠杆（+44% 对 11%~55% 差距），但 10-07 配置不可回填（§4.1），此关联是假设，验收以 §8 对标复测（workers=32 vs New API）为准。**边界**：60s 窗非 640s 稳态；T 曲线单轮（±6% 噪声）；全链路回环无真实网卡路径。详见方案 §7.1。

- **h1 池压测：发现并修复一个确定性尾部 regression —— `Notify` 惊群改为 `Semaphore` 公平队列**。台架：k6（101）→ xlite（101，`H1_POOL=1` vs 默认 gate，均 `MAX_CONNS=32`）→ 24 口 Go mock（102，明文 HTTP/1.1）；constant-VU / 30s。**吞吐全程相同**（200 VU 33.4/33.4；1000 VU 105/115；2000 VU 110/110 qps，均 **0 fail**），但 2000 VU 下初版 h1 池的**尾部确定性偏高**：ttfb **p90 18.5s vs 12.2s（+51%）、p95 24–29s vs 12.4s、max 46.8s vs 17.8s**（3 次重复稳定，非噪声）。根因：`Lease::drop` 用 `Notify::notify_waiters()` —— 每口 `waiting_max` 37–91，释放一次**唤醒全部** waiter，只有一个赢、其余重新 park（惊群）；gate 走 tokio `Semaphore` 的公平 FIFO。修法：`crates/xlite-h1-pool` 每 host 改用 `tokio::sync::Semaphore`（permits = `max_conns_per_host`，permit 随 `Lease` 释放；HTTP/1.1 下 permit 数 ≡ 连接数），并去掉 `dialing` 计数（permit 已保证不超拨）。**修复后 2000 VU ttfb p90/p95/max = 12.2/12.4/17.8s，与 gate 完全对齐**（2 次重复）。**验证**：`cargo test -p xlite-h1-pool` 集成测试 **5 项**全过（含 `an_unread_body_retires_the_connection`：半读退役仍成立）；`cargo test -p xlite --lib` 51、`--test upstream_h1_pool` 2；clippy `-D warnings`（两 crate）干净。**边界**：压测仅覆盖 ≤2000 VU（更高档与长时稳定性未测）；idle reaper 仍未做（`reclaimed` 恒 0）。详见 `docs/dev/h1-upstream-pool-architecture.md` §10。

- **修 `http1_gates[].waiting_max` 把「调用过 `acquire`」记成「排过队」（承接 #75 的可见性补强）**。现象：`AdmissionGate::new(4)` + 单次 `acquire`（远未饱和、从未排队）⇒ `/api/pool` 的 `http1_gates[].waiting_max` 报 **1**，而 `waiting=0`。根因：`acquire` 在 `acquire_owned().await` **之前**无条件 `waiting.fetch_add(1)` + `waiting_max.fetch_max(...)`，于是任何一次 acquire（哪怕立即拿到 permit）都把高水位顶到 1 —— 即把「调用过」当成「排过队」。这与 h2 池的 `waiting`（#70 明写「只在慢路径写」）**语义不一致**，同一个 `/api/pool` 里两个队列字段口径不同，探针/运维会误判（属仓库反复强调的「别用假数字」同类）。修法：`acquire` 先走 `try_acquire_owned()` fast path —— 成功即返回、**不碰** waiting 计数；只有 `TryAcquireError::NoPermits`（真要在池里等）才 `fetch_add` + `acquire_owned().await`。tokio `Semaphore` 是公平的（有 waiter 时 `try_acquire` 会失败），故 fast path 不会插队。**验证**：先跑临时探针把 bug 复现成红（`PROBE waiting=0 waiting_max=1 in_flight=1`），修复后在既有用例里加断言「未排队 ⇒ `waiting_max == 0`」并转绿；`cargo test -p xlite --lib` **51 项**、`cargo clippy -p xlite --lib --tests -- -D warnings` 干净。**边界**：纯计数语义修正，**排队行为一行未改**（permit 的获取/释放路径不变）；`waiting_max` 从此只反映真实排队。

- **更正一条部署建议的因果：`backlog` 与 `nofile` 是**同一个机制**，不是两件事**。§12.3 记的「4000 VU 下 backlog 128 塌成 34.6% 失败、65535 救到 0.00%」与 §13.6 0a 记的「网关 nofile=1024 时 qps 只剩 147」当时各自只看到一半。把两个旋钮摆成 2×2（4000 VU、`batch=1`、单臂 `A1`(128) / `D`(65535)、`nofile` 实测取自 `/proc/<pid>/limits`）后四格逐项复现了旧记录：**1024+128 ⇒ 34.49% 失败 / 225.3 qps**（= §12.3 的 34.63% / 224.3）；**1024+65535 ⇒ 0.00% 失败但只有 147.6 qps**（= §12.3 的 0.00% / 146.3，也 = §13.6 0a 的 147）；**1048576+128 ⇒ 0.00% 失败 / 620.6 qps**（新增格）；1048576+65535 ⇒ 621.2（= §13.6 0a 的 621）。⇒ **根因是 `nofile`**（把并发流封在 ~865，吞吐就上不去），**`backlog` 只决定这个封顶以「拒绝」（34.5% 失败）还是以「排队」（0% 失败、1/4 吞吐）的形式暴露**；**fd 够用时 backlog 128 无害**（同机 `A1` 两档 `~/labtest/bl-A1-b1`/`bl-A1-b10` 均 fail 0.00%；split 台架 `bl2-a` 亦 0.00%；`A0` 的 `backlog=128` 在 8000/16000/31000 VU 也全 0.00%，见 §14.7）。**部署上两个旋钮要一起上，方向是先 `nofile` 后 `backlog`** —— 只调 `backlog` 会得到"不报错但只有 1/4 吞吐"这种更难察觉的形态。数据见 `docs/dev/loadtest-newapi-controlled-2026-09.md` §13.6 第 0a 条（含 §12.3 / §12.5 的限定）。

- **压测台架：补上 `ab_configs.sh` 缺失的收尾 trap（孤儿网关 / 僵尸台架锁）**。该脚本此前**没有任何 trap**，只在正常路径上 `ab_gw.sh stop` 网关 —— 于是 Ctrl-C / kill / 中途 `exit` 一律留下**孤儿网关 + k6 容器 + 被占住的台架锁**（`docker run` 客户端与远端 ssh 子进程都继承了锁 fd 9）。这次是从「kill 掉脚本后 `flock -n` 仍然 BLOCKED」反查出来的，与 `ab_topology.sh` 早先修过的僵尸锁是同一类。**关键是「前台子进程会把 trap 推迟到它结束之后」** —— bash 只在当前前台命令结束后才处理已到达的信号，所以前台 `docker run` 期间发 TERM，30s 后脚本仍活着、网关仍在、锁仍被占；改成 **后台跑 + `wait`**（`wait` 可被信号立即打断）后，TERM 后 **10s 内**脚本退出、容器已删、网关已停、**锁已释放**。配套三处：`trap cleanup EXIT` 提到**任何子进程之前**注册；k6 容器固定 `--name ab_configs_k6`（`--rm` 只在正常退出时自删，被 kill 会留下无名容器）并给它 `9>&-`；`START_FAILED` 那条路径**不再清 `CUR_PORT`**（`ab_gw.sh` 会先起进程再判 nofile，清了就漏掉一个占端口的网关）。⚠️ **纠正一个我先前写错的断言并已撤回**：原文说「只挂 `EXIT` 不够，bash 对未捕获的 SIGINT/SIGTERM 不跑 EXIT trap」，**实测是错的** —— 只挂 `trap cleanup EXIT` 时，`wait` 期间收 TERM/INT，cleanup 都会跑（rc 143 / 129，0.01s），与额外挂 `trap 'exit 130' INT` 的延迟相同；那两个 trap 因此**不需要**，已从脚本里删掉。教训两条：「凡是用 fd 型锁的脚本」要按**脚本清单**逐个核，不能只修被发现的那一个；以及**别把「我推断的 bash 语义」当实测写进文档** —— 这条断言是自己写脚本量了才纠正过来的。

- **路由快照改 `ArcSwap`，去掉异步热路径上会阻塞请求的写锁**：`Store` 的快照由 `Arc<std::sync::RwLock<Snapshot>>` 换成 `Arc<ArcSwap<Snapshot>>`，三个读点（`authenticate`/`model_names_for`/`channels_for`）改无锁 `load()`。**立项理由是结构性缺陷修复，不是性能**：`RwLock` 下 `reload()` 的写者在**路由内容变化时**持写锁并在其中析构旧快照（reload 循环每 5s 检查一次、内容相同就提前 return），期间读请求要等它 —— 这是落在异步热路径上的阻塞点（读代码即可确认）；`ArcSwap` 的读不被写者阻塞，这类等待从结构上不可能发生。**实测不支持任何性能主张，而且本轮测量窗口内目录冻结、`store()` 一次都没执行** —— 那份 CPU 零收益（3 轮同窗口交错范围完全重叠，均值差 0.15%）只证明**读路径**没有可测成本，**不构成对写锁停顿的量化证据**；原先"锁争用是 128 线程 CPU 浪费主因"的假设被**证伪**；p99 测得 −7.7% 但只有单窗口、未达 `v88-rig.md` §9.1"换窗口复现"的门槛，只能算暗示；`max` 的差异不可用作证据（单点极值 + 该指标极端值有 ±250ms 伪影 + 与 ab4 窗口不一致）。因果/换代的端到端证据见 `scripts/loadtest/e2e_reload_swap.sh`（同一进程内换路由：旧模型 404 / 新模型 200；并发段期间每 2s 交替 import weight 不同的目录，即在**真的换代窗口内** fail 0.00%）。回归：`reload_swaps_the_snapshot_so_readers_see_the_new_routing`（memory catalog：换代后同一 key 句柄旧路由消失、新路由可见）。代价：新增直接依赖 `arc-swap`（原为传递依赖，`Cargo.lock` 只多一条依赖边），旧快照释放时机由"持写锁内析构"变为"最后一个 guard 释放时 drop"。数据见 `docs/dev/loadtest-newapi-controlled-2026-09.md` §12.6，可复跑 harness 见 `scripts/loadtest/ab_configs.sh`。

- **`GET /health` 带上 `version`**：免鉴权的探活响应从 `{"status":"ok","gateway":"xlite"}` 变为再带一个 `version`（`CARGO_PKG_VERSION`）字段。此前只有要登录的 `GET /api/overview` 才给版本，启动日志之外**无法用一个 curl 确认现场跑的是哪一版**；对标时反复强调要钉 k6 镜像 digest 与脚本 sha256，网关自己却没有可远程核对的指纹。HAProxy `httpchk` 只判状态码，加字段不影响探活。回归：`health_reports_gateway_and_version`。

- **部署参数变更：`TOKIO_WORKER_THREADS` 默认 32 → 8**（`deploy/env.example`、`deploy/docker-compose.yml` 的 `:-32`）。旧值 32、新值 8、理由：裸 `#[tokio::main]` **按核数**起 worker，在 128 核网关机上等于 128 个 —— 实测 1000 VU 下 128 → 8 省 **8.3%** CPU、128 → 2 省 **40.9%**（见 `docs/dev/loadtest-newapi-controlled-2026-09.md` §12.1 复测值）。取 8 而非 2：**8 是唯一在 1000 VU 与 4000 VU 两档都实测过、且都是被测集合里最好的值**；2 在 1000 VU 更优但 4000 VU 未测、且线程过少在高并发下有排队风险。运行时若显式设了环境变量，本次改动不影响（compose 用 `${TOKIO_WORKER_THREADS:-8}`，仍可覆盖）。
- **运维：`TOKIO_WORKER_THREADS` 不要留默认**（实测，见同上 §12）：裸 `#[tokio::main]` 默认按 `nproc` 起 worker。在 128 核的网关机上实测默认值 **白烧约 40.9% CPU 且尾部更差** —— 1000 VU 下 128 → 2 线程为 `2.670 → 1.579` 核，同时 `p90 −17%`、`p95 −45%`、`p99 −51%`、吞吐与失败率不变（代价仅 `p50 +14%`）。**按负载定，别抄常数**：4000 VU 下 128 → 8 线程省 9%（幅度随载荷变小）。同轮实测另两条：`XLITE_UPSTREAM_MAX_CONNS_PER_HOST` 32/64/128 **零效应**（不用调）；**listen backlog 65535 不是延迟优化而是并发上限保障** —— ≤1000 VU 无延迟差别（accept 队列峰值 17/128），但 **4000 VU 下 backlog 128 直接 34.6% 失败、65535 为 0.00%**。

- **可选的上游首字计时头 `XLITE_UPSTREAM_TTFT_HEADER`（默认关）**：置 1 时流式响应带 `x-xlite-upstream-ttft-ms`（发上游请求 → 上游第一个 body 字节的耗时），用来回答「高负载下 TTFT 涨的那一截在上游还是网关」。**默认关**：HTTP 头先于 body 发出，要报上游首字就必须先等那一个字节，对「先发头、后吐字」的上游会把客户端首字推迟到上游首字；关闭时行为与之前一致（只多一层 `stream::iter(None)` 空适配器，字节与顺序不变）。**这个头不进对标表**：New API 不发任何计时头（其二进制里 `x-*-ms` 形态 0 命中），客户原版脚本也不读响应头，该列只能单边填；`queue-wait` 类头**不提供**（无准入闸门，恒 0，是死列）。同时新增 `scripts/loadtest/`（xlite 自己的 rig，读 `x-xlite-*`；默认值按客户对标喂法设：`KEEP_BODY=true` ⇒ 每次迭代全量解析、checks 比 **2.00**，`KEEP_SAMPLE` 默认 **1**，显式传 0.1 才是客户 v3.2-memopt 的采样版 **1.10**，`KEEP_BODY=false` 时仍是 **1.00**）。回归：`with_head_prepends_without_reordering_or_dropping`。

- **受控对照：把客户的 New API 镜像搬到实验台（`docs/dev/loadtest-newapi-controlled-2026-09.md`）**：用客户给的 `new-api:v8-sentinel` 镜像 + 客户自己的 `init-db.sh` 目录配方（Postgres + Redis + `h2c` 通道），在**同一台实验机、同一份 rig（`KEEP_BODY=true` + `-m 45g`，两侧 checks 比均 2.00）、同一批 24 mock、同一天**与 xlite 0.2.0 对跑。结果：**低载（1000 VU）两者 TTFT 无差别**（xlite 501.8ms / New API 504.2ms，mock 自身 500ms），即客户日志里 New API 的 708ms **不是网关开销**；高载段 New API 在「单副本 + 本地 Postgres」下先崩（4000 VU fail 12.4%、10000 VU 99.8%，签名是每请求结算占一条 DB 连接），但客户现场是 2 副本 + HAProxy + 独占 PG，**不可外推**。**后续更正（含一次降级）**：按客户配置（`SQL_MAX_OPEN_CONNS=2000` / PG `max_connections=2000`）时 4000 VU fail 12.4%；把两边放开到 8000/10000 后出现过 **0.57%**，但**同一配置复跑又出现过 12.4% / 12.98%**（波动 20×）—— 所以那一档**不能用来归因**（既不能说"就是 DB 连接数配置"，也不能说"就是 New API 的行为"），要下结论先补 run ledger（每轮记 PG `max_connections` / `SQL_MAX_OPEN_CONNS` / fail%）；能说的只有架构那条：放开连接数后瓶颈上移到 **Postgres CPU**（10000 VU 时 74 核，错误为 `failed to connect to postgres`），因为 New API 每个请求的结算都要与 Postgres 往返一次。同时更正 `v88-rig.md` 对「客户跑的是哪份 k6 脚本」的归属：客户机上被挂载执行的始终是 `/root/loadtest/k6/k6.js`，但那份文件在对标那晚被手改过至少四次，包里两份 `k6.js`（`deploy88/k6.js` 硬编码 `gracefulStop: '10s'`；`loadtest/k6/k6.js` 采样 0.1 → checks 比 1.10，只对上最后一档 E@21000）**都对不上**跑出对标数据的那一版。对标那批（含客户 708ms）的指纹是 checks 比 **2.00** + `gracefulStop: 10m0s` + 有 `gateway_overhead_ms`，判据见 `v88-rig.md` §1.1。

- **h2c 目标预计算**：通道快照带上 `authority` / `path` / `Authorization`，请求路径不再解析上游 URL、不再 `format!("Bearer …")`。
- **Mock-24 与压测环境手册**：实验室 `117.160.123.99:60000/60001`、客户 22/24/26/29 拓扑、k6 组合与 3 万连接对标，见 `docs/manual/lab-loadtest.md`。
- **V88 对标 rig**：`KEEP_BODY=true`、无 think-time、1000 VU 起跳；不 cap / 不提前 200 / 超时 600s 的落地方式见 `docs/manual/v88-rig.md`。
- **压测可冻结目录快照**：`XLITE_CATALOG_RELOAD_SECS=0` 关掉 5 秒 Redis/SQLite 重载；请求路径仍不碰库。HAProxy 探 `/health`。

## [0.3.0] - 2026-09-24

- **热路径零拷贝透传**：`upstream_model` 与请求 `model` 同名（常规情形）时不再 JSON 反序列化/重序列化，原请求字节直接透传（字节透传边界名副其实）；需要改名时才惰性构建 DOM（每请求至多一次）。上游请求体改传 `Bytes`，去掉 h2c `copy_from_slice` 与 reqwest `to_vec` 第三次拷贝。注意：含重复 `model` 键的请求体现在返回 400（原为末键生效）。
- **快照 Arc 化 + 端点预计算**：路由快照里模型/通道改存 `Arc`，每请求排序只克隆指针不克隆 5 个 `String`；通道的 `chat/completions` URL 在快照构建时算好，不在每请求重拼。5 秒重载在路由未变时跳过写锁交换。
- **Key 哈希与 failover 细节**：API key 哈希改手写 hex（免 `format!` fmt 机器）；failover 前的错误体排空封顶 64 KiB，坏上游不再能拖住重试。
- **入站 listen backlog 与 TCP_NODELAY**：监听套接字 backlog 65535（内核按 `net.core.somaxconn` 封顶）。Linux 上 libc `SOMAXCONN` 是 128，默认 `TcpListener::bind` 会在 3 万 VU 爬坡时丢 SYN。每条入站连接打开 `TCP_NODELAY`，10ms SSE 不被 Nagle 合并。（此前误置在 `[Unreleased]`，实际随本版发出：提交 `4876579` 改了 `src/main.rs`。）

## [0.2.0] - 2026-09-24

- **Admin 会话改为无状态签名 Cookie**：`xlite_session` 变为 HMAC-SHA256 签名的 `exp.nonce`（密钥取自 `ADMIN_SESSION_SECRET`，未设则用 `ADMIN_PASSWORD`）。任意网关节点都能独立校验，HAProxy/负载均衡后无需会话粘性，也不再依赖进程内内存；集群各节点设置同一个 `ADMIN_PASSWORD`（或显式 `ADMIN_SESSION_SECRET`）即可共用登录态。
